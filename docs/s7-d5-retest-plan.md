## 試験前にそろえるもの

- 専用の Hub profile・設定 DB・データフォルダ・空きポート、専用の Sink 設定、実 PostgreSQL の空の試験用スキーマとテーブル。Hub と Sink は試験用のコンソールで起動する。SCM の既存サービス、運用 profile、既存の `tag_history` は使わない。S7 と同じく DB Source とブリッジの読み取り経路も含める。書き込みだけを遮断できる試験用プロキシを Sink の接続先に置き、読み取り経路と Hub–Sink の接続は維持する。
- 各ケースで別の空テーブルと試験番号を使う。シミュレーションタグに加え、DB Source の 104〜107 相当と、追加してから外すブリッジの 110 相当を用意する。更新する試験値に小さな整数の通し番号を付け、タグと入力更新に対応づける。入力番号だけでは保存行を一意に識別できないので、個別照合に使う行は保存列の組が実際に一意か確かめる。一定値や同じ元データ時刻が続く区間も設ける。
- 試験ビルドでは、対象グループだけのキューを、設定反映時のキューのロック内で正確に採取できるようにする。各行のキュー識別子とキュー内 ID、保存列 `ts, tag_id, external_name, value, quality` を記録する。送信中バッチのうちキューに残る行もスナップショットに含め、バッチ開始・ACK・結果不明・破棄を同じ ID で追う。追加・削除の前後に新規投入された行は、設定世代・producer の採取周期の識別子・投入時刻とともに別に記録する。入力更新と購読の再確立も記録する。
- 状態画面の `queued`、`dropped`、引き継ぎログから個々の行は復元できない。実機前に隔離した短いリハーサルで、トレースの欠落やキューあふれがなく、試験用データだけを採取できることを確かめる。認証情報は採取しない。

### 試験用 Sink でのキュー採取

2026-11-03 オーナー決定。行トレースは試験・調査用ビルドに残し、通常の配布版には含めない。配布用のビルドは `d5-trace` を有効にしない。

通常の配布物とは別に `cargo build -p banto-hub-sink --locked --features d5-trace` で試験用の Sink を作る。隔離した Hub のループバック専用ポート（8722 以外）と試験用キーを設定し、保護済みの設定ファイルを `%ProgramData%\BantoHub` の外に置く。採取対象の Sink グループ ID と新しい出力先を渡す。出力にはタグ名と値が入るため、試験者だけが読めるディレクトリを使う。

```powershell
$env:BANTO_HUB_SINK_CONFIG = 'D:\d5-test\sink\banto-hub-sink.toml'
.\target\debug\banto-hub-sink.exe run-d5-trace 1 'D:\d5-test\evidence\case-a.jsonl'
```

Ctrl-C で停止し、JSONL の末尾に `complete` イベントがあることを確認する。記録の欠落、上限超過、異常終了で `complete` が無い場合は照合に使わない。試験はキューとバッチの採取を各 4,096 行以内、ファイルを 64 MiB 以内に収める。`batch_outcome` イベントの `outcome` に `unknown` があれば、そのケースの厳密一致は保留する。

下記の実施ログは JSONL 形式 1 で、破棄行を `discarded` イベントの `row_id` に1行ずつ記録している。現在の形式 2 は、一度のキュー破棄を一つの `discarded` イベントにまとめ、`row_ids` に全行の ID を記録する。照合時は ID ごとに展開する。

この採取はキューへの投入、設定反映時の残行、バッチの送信結果と破棄を対象にする。入力更新、producer の周期、購読の再確立を相互に照合する記録は別途用意する。

## ケースと判定

遮断する A・B・D では、試験プロキシの既存 PostgreSQL 接続を、送信中の INSERT がないことをトレースで確認してから閉じる。その後はすべての新規接続を認証前で止め、復旧まで旧 DB に INSERT が通っていないことを確認する。遮断時に送信結果が不明なバッチがあれば、行の厳密照合は中止する。

| ケース                            | 操作と観測                                                                                                                                                                       | 合格条件                                                                                                                                                                                                               |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. 同じ書き先・タグ追加           | 試験プロキシで新規 PostgreSQL 接続を認証前に止め、古い接続から試験データを送れていないことと、キューに対象行が積まれたことを確認。タグを追加し、反映前後の行を採取して復旧する。 | 反映前のキューを同じ ID で引き継ぎ、復旧後に全行の保存を確認。追加タグの行は反映後に生産された行と照合。`dropped` の増分は 0。                                                                                         |
| B. 同じ書き先・タグ削除           | A とは別の試験で、外すブリッジタグの行が積まれたことを確認してから、同じ書き先でタグを外し、復旧する。                                                                           | 反映前にキューにいた削除タグの行も保存される。反映後にそのタグの新規行が積まれず、残るタグは A と同じ条件を満たす。                                                                                                    |
| C. 書き先変更・旧 DB が応答       | 旧グループが `running`、旧 flusher が生存し、旧キューが空でないことを確認してテーブル名を変更。上限内に旧側の書き込みを通す。                                                    | 設定反映前の行は旧テーブルに保存。反映後の新規行は新テーブルに保存。旧行が新テーブルに出ず、残りを破棄しなければ `dropped` は増えない。                                                                                |
| D. 書き先変更・旧 DB が応答しない | 旧側の書き込みを認証前に遮断。旧キューの残りと設定反映時のグループ状態を採取してテーブル名を変更し、復旧後に両テーブルを読む。                                                   | `running` でない場合は待たず、待てる状態でも `shutdown_flush_secs` は旧キューを流す待ち時間の上限。旧側で保存できた行と破棄行を分け、破棄の warn と `dropped` の増分がキューの破棄行と一致。旧行は新テーブルに出ない。 |

1. 反映境界のスナップショットと反映後の投入記録に、表のケース別の合格条件を適用し、書き先ごとに保存すべき 5 列の行を組み立てる。実績の件数や ACK 数から期待値を逆算しない。同じキュー ID をスナップショットと投入記録から二重に数えない。事前疎通で保存した行がある場合は、試験開始前に 5 列と多重度を採取して実績から除く。復旧後は試験用 producer を止めてキューが空になるのを待ち、旧・新テーブルから同じ型で実績を採取する。
2. 各書き先で `expected EXCEPT ALL actual` を欠落、`actual EXCEPT ALL expected` を余分として出す。列は同じ順の `ts, tag_id, external_name, value, quality` とし、両方が空なら一致。`DISTINCT` や `(ts, tag_id)` の集計だけでは判定しない。完全に同じ 5 列の行を区別するキュー ID は DB に保存されないため、個別照合は一意な試験値の行で行い、同じ値が続く区間は多重度とトレースで確認する。
3. 入力・採取時刻の間隔は周期のずれ、同じタグの一度の採取から出た複数のキュー ID は二重投入、同じキュー ID の複数バッチ試行は再送の手掛かりになる。`interval` では別周期で同じ値と `ptime` を保存しうる。`on_change` では値・品質の変化と再購読前後の採取を突き合わせる。復旧後に COMMIT の結果不明があれば、その試行の行を記録し、厳密一致の判定は保留してやり直す。S7 当時の 21:16:33.678 のような候補は当時のトレースがなく、今回の再現だけで原因を確定できない。

## 実施の承認と後始末

次に承認を取る範囲は、オーナー同席で、合意した試験ビルド・専用 profile・専用 PostgreSQL スキーマを使い、試験プロキシの遮断と復旧、試験グループの設定変更、照合結果の採取と試験資材の後始末まで。共有 DB や LAN の停止を含める場合は別に操作範囲と復旧手順を合意する。

運用先との混同、試験対象外への影響、トレース欠落、キューあふれ、復旧失敗があれば中止する。まず試験経路の遮断を解除し、試験用 producer とプロセスを停止。開始前に記録したサービス状態と運用設定に変化がないことを確認してから、試験専用のキー・設定・DB 資材を片付ける。残す証拠は試験番号、コミット、時刻、行差分、設定反映・接続状態・`dropped` の推移、未判定の理由。自動テストの結果と分けて R-5 の後続記録に残し、D-5 と #229 の判定はオーナーが行う。

[既存 CI](https://github.com/tyaro/banto-industrial/actions/runs/41596974242/job/125786608602) ではキューに直接投入した行の追加・削除時の保持、旧 DB が応答する場合の旧テーブルへの flush、上限後の残りの破棄の 3 テストが成功した。実機での購読、producer、書き込み経路の遮断・復旧を通した証拠は本手順で別に採る。
