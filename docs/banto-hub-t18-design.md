**実装メモ（2026-08-27、6a/6b/6c マージ時点）**:

- **連番プリフィルは「最大値+1」ではなく「歯抜けを埋める最小の正整数」**とした
  （`connection1`・`connection3` があれば `connection2`）。接続を作り消ししても番号が
  無闇に大きくならない方が実運用に合うという判断。採番ロジックは 6b で
  `lib/banto/sequentialName.ts::nextSequentialName` へ切り出し、接続とグループで共有する
  （`nextConnectionName` は挙動・シグネチャ不変の薄いラッパー）。
- **既定ポート**は `modbus-tcp` = 502（旧実装の踏襲）、`slmp` = 5007
  （`crates/banto-plc/src/slmp/mod.rs` の `SlmpConfig::default()` と一致）。テスト機の
  `192.168.11.200:5200` は実機固有値なので既定にしない。プロトコル切替時の追従は
  `portTouched` で制御し、ユーザーがポート欄を編集した後は上書きしない。
- **6c で `calc`/`mem` の末尾バッジは廃止した**。`CALC_CONNECTION_NAME = 'calc'` のとおり
  接続名自体が `calc`/`mem` なので、行頭アイコン（🧮/💾）を入れた上でテキストバッジを
  残すと「calc calc」と二重になるため。`⚠ SIM` は種別ではなく状態を表すのでバッジのまま維持。
- **6c の階層別背景**はルート行に `--banto-surface-subtle`、子行は基準面が透ける形。新しい
  hex は追加せず既存トークンのみで表現し、`glass` preset の選択スタイルも壊していない。
- 202（`QueuedWhileRunningError`）は両 Drawer とも失敗ではなく `toastStore.push('info', …)` の
  案内として出し、Drawer を閉じずフォームを保持する。
- **6d の削除は両 Drawer の既存 `handleDelete` を再利用する**（削除影響エラー
  「収集グループが N 件あるため削除できません」の扱いを重複させないため）。`requestDelete`
  prop を立てて再設定モードで開いた直後に1回だけ呼ぶ方式で、二重発火は `lastOpenKey`
  ガード、フラグの残留はページ側のリセット、開いている間の再操作は Drawer の
  `aria-modal` 全面オーバーレイでそれぞれ防いでいる。**削除を選ぶと再設定 Drawer が開いた
  上に確認ダイアログが出て、キャンセルするとその再設定フォームに留まる**のは意図した
  フォールバック（削除ロジックを重複させない代償）。
- **6d の virtual（calc/mem）除外は新しいガードを書いていない**。既存の
  `resolveTagTreeContextMenuAction` が virtual に対して `null` を返す性質をそのまま活かし、
  `resolveTreeContextMenuItems` は `[]` を返してメニュー自体を出さない。

実行順は 6a → 6b → 6d、6c は並行で実施した（すべて 2026-08-27 にマージ済み）。いずれも自走可能な
フロント実装で、実機は不要。

## 4. 決定事項（2026-08-12 オーナー決定）

1. **TAG-UX-E / TAG-UX-G の扱い** → **既定案採用**: E（検索/一覧）は T18-3/T18-4 に統合、
   G（アクセシビリティ/狭幅）は各機能スライスの受け入れ条件へ織り込む。
2. **BantoGrid セル編集/TSV（T18-3e）** → **既定案採用**: 独立スライスへ切り出す
   （全構成 preflight・all-or-nothing・停止中ロックを整備してから接続）。
3. **性能閾値の対象 PC 基準** → **Intel Core i5 第11世代・メモリ 8〜16GB** を基準マシンとする。
   「10,000 タグ・500 グループで初期操作可能まで 2 秒 / 検索 p95 100ms / 1,000 件 dry-run・適用 5 秒」を
   この基準機で満たすことを T18-5a の性能目標とする。
4. **一括削除** → **バックログ据え置き（承認）**。実装する場合の代案は以下（着手判断は将来）:
   - **代案 B（可逆な既定・推奨）**: 一括「無効化」（T18-3b）を「収集から外す」主操作として前面に出す。
     無効化は収集停止のみで破壊せず**可逆**なので、多くの用途は削除不要で済む。
   - **代案 A（真の削除が要る場合）**: 単票削除（TAG-UX-C）が持つ「演算タグ等の参照影響＋完全外部名の表示」を
     一括へ拡張。選択セット全体の参照影響を集約表示し、参照タグがあれば警告/ブロック、明示確認を必須にして削除。
     復旧は undo ではなく「削除前の差分プレビュー＋事前 CSV エクスポートでのバックアップ」で代替。
5. **着手範囲** → **T18-2 全体を 1 群として着手可**。実装は a→b→c→d→e のサブ PR で刻んでレビュー可能に保つ。
6. **T18-5a 第2段の方式（2026-08-13 オーナー決定）** → **実測ファースト方針を採用**。
   全面 windowed 化（案A）・閾値ハイブリッド（案B）は見送り、以下の2点を先行する:
   - **薄い部品の先行配線**: `POST /api/tags/list`（`write_audit_list` 同型の `ListParams`
     パススルー）とグループ別タグ件数集計 API。どの案に転んでも必要な共通部品のため。
   - **性能計測ハーネス**: 10,000 タグ・500 グループを seed し、決定 3 の性能目標
     （初期操作可能 2 秒 / 検索 p95 100ms / 1,000 件 dry-run・適用 5 秒）を実測する
     opt-in の計測 spec（CI 対象外）。
     実測が目標を満たせば「全タグのクライアント保持（設計上限 10,000 タグ）」を正式仕様として
     記録し、windowed 化はバックログへ降格。未達の場合のみ、未達箇所に絞って対処する。
     判断材料（2026-08-13 調査）: 全タグ保持に依存する機能は 7 箇所（CSV 更新突合・Tree 件数・
     検索・一括操作・セル編集 preflight・複製名採番・削除影響）で、windowed 化はこれらの
     都度取得化を要する大工事。かつ `ListParams` のフィルタは AND のみで現行検索
     （name **or** address）を表現できず、サーバー拡張も必要。10,000 タグ（概算 JSON 3〜5MB・
     ローカル接続）なら現行方式で目標達成の見込みが高い、という費用対効果評価による。

   **追記（2026-08-14 オーナー判定）**: 先行配線=PR #153、計測ハーネス=PR #154 としてマージ済み。
   開発機での実測（§2 T18-5a の判定欄参照）は3項目とも目標内で、基準機との CPU 差を考慮しても
   マージンをもって**目標達成と判定**する。よって:
   - **「全タグのクライアント保持（設計上限 10,000 タグ）」を正式仕様とする**。10,000 タグ超の
     要件が将来生じた場合に windowed 化（案A 相当）をバックログから再起票する。
   - **windowed 化はバックログへ降格**。PR #153 の `POST /api/tags/list`・`GET /api/tags/group-counts`
     は配線のみ（UI 未使用）のまま維持し、再起票時の土台とする。
   - **保険**: 検索 p95 のみマージンが薄い（80ms vs 100ms。ただし計測値は Playwright アサーション
     往復を含む過大評価側）ため、T18-5c 同席時に基準機で1回実測して本書へ記録する。仮に基準機で
     100ms を超えても対処は検索経路のみに絞る（全面 windowed 化には戻らない）。
