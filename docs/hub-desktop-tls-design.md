## 1. 目的と範囲

#644 で、ChronoGazer は同じ PC の Hub と **https と証明書の pin** でしか話さなくなった（2026-11-13 オーナー決定）。TLS を待ち受けるのは Hub の **Windows サービスだけ**で、一般の利用者で動く **Hub のデスクトップ版は平文の 8722 だけ**。そのため、今の main では **Hub のデスクトップ版と ChronoGazer が繋がらない**。

Store での最初の公開は、Hub と ChronoGazer のデスクトップ版になる（別リポジトリのフォーク、2026-11-14 オーナー）。この設計は、その前提となる「デスクトップ版の Hub も TLS で待ち受け、ChronoGazer が pin する」仕組みを、このリポジトリで作るためのもの。

- **範囲**: Hub のデスクトップ版の TLS の待ち受け、その鍵と証明書の置き場と作り方、ChronoGazer（デスクトップ）の pin、Hub シェルの Desktop モードの表示。
- **範囲外**: LAN の平文（#644 と同じ）、サービスの TLS の待ち受けそのもの（#1116・#1117 で済。ただし §4.4 の失効の記録のため、サービスの Hub の周期ごとの露出の確かめ・サービスの記録・elev が記録を作ることは**この設計で足す**）、MSIX での置き場の実際の見え方（フォーク側の作業。§4.1 で差し替えられる形にだけしておく）。

## 3. 守るものと信頼の範囲

- **守るもの**: ChronoGazer の API キー（Hub の `read` などのスコープ）と、Hub シェルの管理画面のパスワード・セッション。どちらも、Hub を閉じている間に 127.0.0.1 のポートを先取りした相手へ送られうる。
- **相手**: 同じ PC の**別のアカウント**で動くプロセス（共用の現場 PC の別の利用者、別のアカウントのサービス）。
- **信頼の範囲は「同じ利用者」**: 同じ利用者のプロセスは信頼する。そのプロセスは ChronoGazer のキーのフォルダも読めるので、先取りを防いでも守る意味が無い（#1121 本文）。
- **管理者・SYSTEM は信頼する**: サービスの `tls\` と同じ。管理者は、先取りしなくても鍵もキーも読める。
- **Hub のデータの置き場（判断 7）**: デスクトップ版の Hub は `%ProgramData%\BantoHub\<profile>\` を締めずに使う。`%ProgramData%` の既定の ACL では、別のアカウントがその DB を読める、または初回の起動より前にフォルダを作って持てる可能性がある（**実際の ACL は未確認**。PR1 の前に確かめる）。そうなら、この設計で「別のアカウントから ChronoGazer のキーを守る」一方、Hub の DB（接続先の資格情報など）は同じ相手に開いたままになる。
  - 本設計の範囲はキーと管理画面の送り先だけで、データの置き場は守らない、と明記するか、デスクトップ版のデータの置き場も利用者ごと（または締める）にするかを決める。後者は Store 版の前に効くので、別 Issue にする案を推す。
- **妨害（判断 8）**: 別のアカウントは、8723 を握るだけで ChronoGazer の接続を妨げられる（秘密は漏れない）。`Global\BantoHub.*` の mutex も、既定の記述子では「開けない」を「保持中」と読むので、同じ相手が Hub の起動を妨げられる。妨害は受容し、管理画面だけは §4.5 で守る案を推す。

## 4. 提案

### 4.1 置き場: 利用者ごとの `tls\`（差し替えられる形）

- **既定の置き場**: `%LOCALAPPDATA%\BantoHub\tls\`（`hub-cert.pem`・`hub-key.pem`）。パスは環境変数ではなく既知のフォルダ（`FOLDERID_LocalApplicationData`）から組み立てる。理由は `banto-hub-tls-trust` の `%ProgramData%` と同じで、環境変数で別の場所へ向けられないようにするため。
- **差し替えの口**: 置き場を `banto-hub-tls-trust` の 1 つの trait（例: `UserTlsPlace`）に閉じ込める。trait は「ルートのパス」だけでなく、**期待する所有者と確かめの方針**も返せる形にする（MSIX の publisher cache folder は所有者と ACL が違いうるため）。フォークはこの trait を差し替える（2026-11-14 オーナー補足）。パスを決め打ちする箇所は既定の実装 1 つだけ。
- **確かめること**（サービスの置き場の確かめを利用者向けに読み替える）:
  - 所有者が**今のプロセスのトークンの利用者 SID**、SYSTEM、Administrators のどれか。
  - その 3 者以外に、書き込み・削除・ACL の変更・所有者の変更の許可が無い（`%LOCALAPPDATA%` 自身、`BantoHub\`、`tls\`）。
  - 鍵のファイルは、その 3 者以外が読めない（露出の確かめ）。
  - リンク・リパースポイントを辿らない（今の pin した handle の仕組みを使う）。`%LOCALAPPDATA%` が既知のフォルダの値と一致すること。
  - 最終パスがローカルの固定ドライブであること（ネットワークや別ボリュームへの転送を断る。VDI のフォルダの転送を考えて）。
- `%LOCALAPPDATA%` の既定の ACL（利用者・SYSTEM・Administrators だけ）なら、この確かめは何もしなくても通る。

### 4.2 作り方と作り直し

- **作る人**: Hub のデスクトップ版自身が、起動のときに置き場を確かめ、**無いときだけ**作る。昇格は要らない（利用者の場所なので）。`generate_identity`・`inspect_identity` をそのまま使い、書き込みは今と同じ「一時ファイル → 置き換え」。**作る前に、失効の記録を整える**（§4.4.1 の手順。利用者の記録が 2 つとも `確定` になってから証明書を作る）。整えられなければ証明書を作らず、TLS 無しで起動して理由を出す。
- **直列化**: 名前付き mutex ではなく、**`tls\` の中のロックファイルの排他の open** で直列化する。`Local\` の mutex はセッションごとなので、同じ利用者の別のセッション（RDP とコンソール、`runas`）を直列化できない。`Global\` に SID を入れる形は、別のアカウントが先に作れる。ロックファイルは置き場の ACL で守られ、セッションに依らない。書き終えた後に `inspect_identity` で鍵と証明書の対を確かめ直す。
- **期限**: サービスと同じ 10 年。
- **作り直しの口**: Hub シェルのトレイのメニューに「TLS の証明書を作り直す」を足す（確認の画面付き）。作り直したら、Hub の TLS の待ち受けを張り直す（または Hub を再起動する）。ChronoGazer は見張り（#1120）が証明書の変化を見て、操作なしで張り直す。
- **作り直しの前にも置き場を確かめる**: 手の操作でも、書き込む前に §4.1 の確かめ（所有者・ACL・露出・リンク・ローカルの固定ドライブ）をやり直す。通らなければ**作り直さない**（新しい鍵を書くと、別のアカウントに読まれた後で ACL を直しても安全にならないため）。シェルには理由と、安全な置き場に戻す手順を出す: Hub を閉じる → `%LOCALAPPDATA%\BantoHub\tls\` の中身を確かめてフォルダごと消す（`BantoHub\` の所有者・ACL が壊れていればそれも直す）→ Hub を起動し直すと、確かめに通る新しい置き場に作り直される。`BantoHub\` ごと消してもよい（失効の記録の片方も消えるが、もう片方から直る。§4.4.2 の場面 22）。サービスの `prepare-hub-tls --renew` が露出を確かめてから作るのと同じ考え。
- **作り直しと失効の記録**: 作り直しは、置き場の確かめの次に、失効の記録を整える手順（§4.4.1）を走らせ、利用者の記録が 2 つとも `確定` で整っているときだけ先へ進む。記録の欠け（片方が消えた・壊れた）は、整える手順が見つけた時点で直してある（残った拇印を**すべて引き継ぎ**、古い証明書の拇印を失効に入れて、2 か所とも作り直す）。そのため、作り直しの中に記録だけの特別な直し方は持たず、記録の消失で止まっていた場合も、ふつうの作り直しで戻る。整えられないとき（記録の置き場が確かめに通らない・書けない）は作り直さず、理由と直し方を出す（新しい証明書を作っても使えないため）。
- **作り直しの順序と、その間の切断**: Hub は「新しい鍵と証明書を一時ファイルに作る → 確かめる → 待ち受けの証明書を新しいものに差し替える → ファイルを置き換える」の順にする。待ち受けを先に替えるので、ChronoGazer が新しいファイルを読むときには、Hub はもう新しい証明書を出している。それでも、ChronoGazer が古い pin で張った接続は、次の再接続で新しい pin に替わるまで（見張りの 1 周期、30 秒まで）切れることがある。作り直しはまれな手の操作なので、この短い切断は受容し、古い・新しいの pin の併用はしない（pin の 2 件の枠はサービスと利用者で使うため。§4.4）。
- **作り直しに失敗したときの戻し方**: 鍵と証明書は**一組として**扱い、「待ち受けの証明書」と「ファイルの組」が食い違ったままにしない。
  - 待ち受けの差し替えに失敗したら、ファイルには触らず古いまま残し、シェルに理由を出す。
  - ファイルの置き換えは、**今の組を退けるのではなく写す**: 今の組を `*.pem.old` に写し、写した組を読み直して組として合うことを確かめ、ディスクへ書き切ってから（flush）、新しい組で今のファイルを置き換える。今の組は置き換えるまで手を付けないので、写す途中で止まっても今の組は揃ったまま残る。置き換えの途中（片方だけ置き換わった、など）で止まった・失敗したときは、確かめ済みの `*.pem.old` の組から元に戻し、**待ち受けも古い証明書に戻す**。戻せたら理由を出し、戻せなかったら 8723 の TLS を止めて（壊れているときと同じ扱い）理由と直し方を出す。
  - 起動のときに `*.pem.old` や一時ファイルが残っていたら、途中で止まった作り直しとみなす。**今の組（`hub-cert.pem`・`hub-key.pem`）が揃っていて組として合えば、必ずそれを使う**（置き換えが終わった直後に止まった場合も、新しい組が正しい）。`*.pem.old` から戻すのは、今の組が欠けているか組として合わないときだけ。どちらの場合も、使わなかったほうと一時ファイルを片付ける。
  - **失効している古い組へは戻さない**: 戻す先の `*.pem.old` の証明書が失効の記録にあるとき（露出や記録の消失が理由の作り直し）は、戻しても使えない。そのときは戻さずに 8723 の TLS を止め、作り直しを案内する（「戻せなかったとき」と同じ扱い）。
- **壊れているとき**（所有者が違う・露出・鍵と証明書が合わない）: 作り直さずに TLS 無しで起動し、Hub シェルに理由と直し方を出す（サービスの決定 A と同じ。勝手に消して作り直すと、乗っ取られた置き場を正規の物として扱う恐れがあるため）。理由と直し方は、TLS の待ち受けに頼らない**シェル自身の画面**（今の Service モードの Fallback と同じ、シェルに同梱した画面）とトレイの通知で出す。

### 4.3 ポート: サービスと同じ 8723（推奨）

- デスクトップ版も **127.0.0.1:8723** で TLS を待ち受ける。
- デスクトップ版とサービスは同じプロファイルで同時に動かない（`Global\BantoHub.{profile}` の mutex）。そのため、同じポートでぶつからない。
- **ChronoGazer の接続先は `https://127.0.0.1:8723` の 1 つのまま**、Hub をデスクトップ版とサービスの間で切り替えられる。利用者が両者を容易に行き来できる、という前提（2026-10-18 オーナー）に合う。
- 8723 が埋まっていれば、サービスの決定 B と同じく **8723 の TLS は無しで**起動し、シェルに理由を出す。OS が選ぶポートへは逃げない（ChronoGazer が追えないため）。管理画面は §4.5 の口で開く。
- 複数のプロファイルを同時に動かすと、2 つ目は 8723 を取れない。今の運用（既定のプロファイル 1 つ）では起きないので、案内の文言だけ用意する。
- 平文の 8722 は今のまま残す（LAN の平文は範囲外）。ただし、同じ PC のシェルと ChronoGazer は 8722 を使わない。8722 が埋まったときに OS が選ぶポートへ逃げる仕組み（`port_fallback_applies`）は、シェルの表示に要らなくなるので、残すか外すかを PR2 で決める。

### 4.4 ChronoGazer の pin: 2 つの置き場を両方読む（推奨）

- `SystemHubCert` を「サービスの `tls\` と、今の利用者の `tls\` の両方を読む」読み手に替える。確かめが通った証明書（1 つか 2 つ）を pin にする。
- **「無い」と「あるが通らない」を分ける**: デスクトップだけの PC ではサービスの置き場が無いのが普通なので、「無い」は黙って外す。「あるが通らない」（露出・所有者が違うなど）は pin に入れず、**接続できても**画面とログに警告を出す（片方が良いとき、もう片方の問題が誰にも見えなくなるのを防ぐ）。
- 両方とも使えなければ、今と同じ `HubTls` の誤りで断る。直し方の案内は、Hub の動かし方（デスクトップ版・サービス）ごとに分けて出す（今の `remedy_text` は「サービス＋ `prepare-hub-tls`」前提）。
- **pin の上限**: サービス 1 ＋利用者 1 で 2 件の枠を使い切る。ChronoGazer は毎回いまの証明書を読み直すので、証明書の切り替えの対（古い・新しい）を持つ必要が無い。上限は 2 のままにし、その旨を `pinned_tls.rs` の doc に書く。
- **見張りの目印**（`marker_for`）は、置き場ごとの hash の組（サービス・利用者、無いときは無いと分かる値）にする。PEM の連結の hash にしない（順序や有無の変化を取り違えないため）。
- **毎周期、確かめ直す**: 目印を作るたびに、PEM を読むだけでなく、置き場の所有者・ACL・露出の確かめをやり直す（今の `HubTlsPolicy::decide` も呼び出しのたびに `load_pinned_hub_cert` で確かめている。その形を保つ）。確かめに通らなくなった置き場は「通らない」の値として目印に入れるので、PEM が同じでも目印が変わり、その証明書を pin から外して張り直す。ACL だけが書き換えられた（鍵を別のアカウントが読めるようになった）ときも、次の周期（30 秒まで）で外れる。
- **露出を見た証明書は二度と使わない**: 鍵がほかのアカウントに読める状態だったなら、その間にコピーされたかもしれない。ACL を直しても、コピーされた鍵は無効にならない。そこで、露出を見た証明書は、ACL が直っても**再び pin に入れず、Hub も待ち受けに使わない**。戻す条件は鍵と証明書の作り直し（§4.2）だけにする。
  - 露出を見た側（デスクトップ版の Hub・サービスの Hub・ChronoGazer のどれでも）が、その証明書の拇印を**失効の記録**に書き足し、拇印が記録にある証明書を pin にも待ち受けにも使わない。記録の置き場・形・整え方・照合・保証の範囲は §4.4.1 に、場面ごとの振る舞いは §4.4.2 にまとめる。
  - **目印に失効の状態も入れる**: 見張りの目印には、置き場ごとの証明書と確かめの結果に加えて、その証明書が失効の記録にあるかを入れる。記録だけが足された場合も目印が変わり、次の周期で pin から外して張り直す。
  - **受容する残りのリスク**: 確かめと確かめの間（30 秒まで）だけ ACL が緩められて元に戻された場合は見えず、失効の記録にも残らない。ACL を緩められるのは置き場の所有者（同じ利用者）か管理者だが、緩めた ACL で別のアカウントに ACL の変更の許可（`WRITE_DAC`）まで与えていれば、**そのアカウント自身が元に戻せる**。この場合は「信頼の範囲の中の操作」とは言えないので、保証はせず、受容する残りのリスクとして扱う（周期の確かめで見つかる露出だけを防ぐ）。記録そのものについての残りのリスクは §4.4.1 の末尾。
- **別の案（採らない）**: 「待ち受けている相手がサービスかデスクトップ版かで、どちらの pin を使うか決める」。相手の種類を知る確かな方法が無く（ポートの持ち主の確かめは #644 の受入条件 1 で退けた形）、決め方を誤ると繋がらない。両方を pin にしても、別のアカウントのプロセスはどちらの鍵も持たないので通らない。

#### 4.4.1 失効の記録の決まり

2026-11-14 に、場面を並べて総点検し（§4.4.2）、決まりを組み直した。考え方は 3 つ。

1. 利用者の記録を整える手順は **1 つだけ**。同じ利用者のどのプロセス（デスクトップ版の Hub・ChronoGazer デスクトップ）が何度走らせても、同じ結果になる。
2. 拇印は**増えるだけ**で、減らさない。2 つの記録は和で照合する。
3. 記録が欠けていたら、**その場で**「今ある利用者の証明書を失効に入れて、記録を直す」。「記録が欠けたまま止まっている」という特別な状態を残さない。そのあとは、ふつうの「失効した証明書」と同じく、作り直し（§4.2）で戻る。

**置き場と書き手**

| 記録           | 置き場（例。正確な名前は PR1・PR4）                      | 書くもの                                                     | 読むもの                                                         | 入る拇印                                                                |
| -------------- | -------------------------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 利用者の記録 A | `%LOCALAPPDATA%\BantoHub\revocations\`（`tls\` の外）    | 同じ利用者のデスクトップ版の Hub と ChronoGazer デスクトップ | 書くものと同じ                                                   | 利用者の証明書と、その利用者の ChronoGazer が露出を見たサービスの証明書 |
| 利用者の記録 B | `%LOCALAPPDATA%\BantoHubRevocations\`（A と親が違う）    | A と同じ                                                     | A と同じ                                                         | A と同じ内容                                                            |
| サービスの記録 | `%ProgramData%\BantoHub\tls-revocations\`（`tls\` の外） | **サービスの Hub と elev（`prepare-hub-tls`）だけ**          | サービスの Hub、すべての利用者の ChronoGazer、chronogazer-server | サービスの証明書                                                        |

- A と B は親の違う 2 か所に置く。片方の親（例えば `BantoHub\`）の ACL が緩んでいる間に、別のアカウントが片方を消したり古い内容に戻したりしても、もう片方が残る。ChronoGazer の置き場には頼らない（ChronoGazer を入れていない PC でも 2 か所になるように）。
- すべての利用者が書ける報告の置き場は作らない（別のアカウントがサービスの証明書を勝手に失効させ、止められるため）。
- どの記録も、置き場が §4.1 と同じ確かめ（所有者・ACL・リンク・ローカルの固定ドライブ）に通るときだけ「読めた」として扱う。サービスの記録は、サービスの `tls\` と同じく SYSTEM・Administrators だけが書けることを確かめる。
- **形**: 状態（`準備中` か `確定`）と、拇印の並び（拇印・どの置き場の証明書か・書いた時刻）。`準備中` になるのは A だけ（下の手順）。
- **書き方**: 必ず「同じフォルダの一時ファイルに書く → 書き切る（flush）→ 置き換え」。途中で止まっても、前の内容か新しい内容のどちらかが残る。残った一時ファイルは読まずに片付ける。
- **直列化**: 利用者の記録の判定と書き込みは、記録 B のフォルダの中のロックファイルの排他の open で直列化する（§4.2 と同じ理由で、名前付き mutex は使わない）。ロックを取ってから 2 つの記録を**読み直して**判定する。照合のために読むだけならロックは要らない（置き換えで書くので、読めるのは常に揃った内容）。`tls\` のロックと両方を取るときは、`tls\` → 記録の順にする。

**利用者の記録を整える手順**

走らせるのは、デスクトップ版の Hub（起動のとき、証明書を作る・作り直す前、動いている間の周期ごと）と ChronoGazer デスクトップ（起動のとき、見張りの周期ごと）。デスクトップ版の Hub だけの PC でも、サービスの Hub と ChronoGazer だけの PC でも、先に動いたほうが記録を作る。

| A                | B      | 判定                   | すること                                                                          |
| ---------------- | ------ | ---------------------- | --------------------------------------------------------------------------------- |
| 無い             | 無い   | 未初期化               | A を `準備中` で作る → B を `確定` で作る → A を `確定` に書き換える              |
| `準備中`         | 無い   | 初期化の途中で止まった | 続きから: B を `確定` で作る → A を `確定` に書き換える（A にある拇印は引き継ぐ） |
| `準備中`         | `確定` | 初期化の最後で止まった | 和を取って両方に書き、A を `確定` に書き換える                                    |
| `確定`           | `確定` | 整っている             | 和を取り、片方にしか無い拇印をもう片方へ書き戻す                                  |
| 上のどれでもない |        | **消失**               | 下の「消失の直し方」                                                              |

- 「上のどれでもない」は、片方が `確定` で相手が無い・読めない・形が壊れている・置き場が確かめに通らない、B が `準備中`、両方とも読めない、など。
- **記録を新しく作るときの決まり**: 未初期化・途中からの続き・消失の直しで記録のファイルを新しく作るとき、利用者の `tls\` に証明書が**すでにあれば、その拇印を必ず失効として入れる**。正しい順序（記録を 2 つとも `確定` にしてから証明書を作る。§4.2）では「記録が欠けているのに証明書がある」は起きないので、起きていれば記録を消されたとみなす。証明書がまだ無い初回は、空の記録になる。
- **消失の直し方**: 読めた記録の拇印の和を取る（置き場が確かめに通らないほうも、形が読めれば和に入れる。和は増えるだけなので、安全側にしか動かない）→ 利用者の証明書があればその拇印を足す → **先に、残っているほう**を書き換える → 欠けたほうを `確定` で作り直す。両方とも読めないときは、利用者の証明書の拇印だけ（無ければ空）の記録を、未初期化と同じ順で作る。途中で止まっても、次の回が同じ判定で同じことを繰り返す。画面とログに「失効の記録が消された・壊れた」を出す。
  - 置き場が確かめに通らないほうは、通るようになるまで作り直さない（書いても別のアカウントに書き換えられるため）。その間は毎回「消失」として扱い、警告を出し続ける。
- **利用者の証明書を使ってよいのは、整える手順の結果が「整っている」のときだけ**（Hub の待ち受けも、ChronoGazer の pin も、証明書を作る・作り直すのも）。
- **整えられないとき**（書けない・ロックが取れない・置き場が確かめに通らない）: 利用者の証明書を作らず、使わない（Hub は 8723 の TLS 無しで理由を出し、ChronoGazer は pin に入れない）。サービスの証明書は、サービスの記録と、読めた利用者の記録で照合を続け、警告を出す。露出を見たのに書けなかった場合の残りは §7。
- **`準備中` を続きとして扱ってよい理由**: 「`確定`・`確定`」から「`準備中`・無い」や「無い・無い」を作るには、A と B の**両方**の親に書ける必要がある。片方の親だけが緩んでいるなら、どう書き換えても「消失」か「整っている（和で元に戻る）」のどちらかに落ちる。そのため、「`準備中`・無い」を初期化の続きとして扱っても、片方だけを触れる相手には失効を消す道にならない。

**サービスの記録**

- elev の `prepare-hub-tls` が、証明書を作る・作り直す前に、無ければ空で作る。サービスの Hub も、起動のときに無ければ作る（#1116 で作った証明書だけがある PC のため）。
- 置き場に書けるのは SYSTEM と管理者だけ（§3 の信頼の範囲）なので、対の記録も `準備中` も持たず、「無い」は空として扱う。消失の判定はしない。
- 置き場が確かめに通らない・形が壊れているときは、サービスの証明書を使わない（サービスは 8723 の TLS 無しでログ、ChronoGazer は pin に入れず警告）。`prepare-hub-tls --renew` が、読めた拇印と古い証明書の拇印を引き継いで記録を作り直してから、新しい証明書を作る。

**照合する時点**

- **デスクトップ版の Hub**: 待ち受けに使う前と、動いている間の周期ごと（ChronoGazer の見張りと同じ 30 秒）に、整える手順 → 置き場の確かめ → 利用者の記録（A と B の和）との照合、の順に行う。露出を見たら記録に書く。失効していたら、8723 の待ち受けを止め、その証明書で張られている接続も切って、シェルに作り直しを案内する。
- **サービスの Hub**: 起動のときと周期ごとに、自分の `tls\` の露出（今の決定 A の確かめ）とサービスの記録を確かめる。露出を見たら記録に書く。失効していたら、8723 の TLS を止めて接続を切り、ログに出す。
- **ChronoGazer デスクトップ**: 起動のときと見張りの周期ごとに、整える手順を走らせたうえで、利用者の証明書は利用者の記録と、サービスの証明書は**サービスの記録と利用者の記録の両方**と照合する。
- **chronogazer-server**: サービスの置き場とサービスの記録だけを読む（§4.6）。利用者の記録は持たず、サービスの記録にも書かない。露出を見たら、そのプロセスが動いている間はその証明書を pin に入れず、ログに出す。
- 記録は再起動の後も残るので、ACL が直された後に再起動しても、同じ証明書を受け入れない。

**保証の範囲と、受容する残りのリスク**

- **利用者の証明書**: 同じ利用者の Hub と ChronoGazer の間で、失効が必ず伝わる（次の周期、30 秒まで）。片方の親の ACL だけが緩んだ間の、記録の削除・破損・古い内容への巻き戻しでは、失効は消えない。
- **サービスの証明書**: サービス自身が露出を見たときに、サービスとすべての利用者へ伝わる。ChronoGazer デスクトップだけが見たときは、その利用者の記録に残り、その利用者の ChronoGazer は以後使わないが、サービスとほかの利用者には伝わらない（画面で、管理者に `prepare-hub-tls --renew` を頼むよう案内する）。chronogazer-server だけが見たときは、そのプロセスの間しか覚えない。どちらも、サービスが見る前に ACL が直された場合だけの窓で、サービスの `tls\` の ACL を変えられるのは管理者だけ（所有者が Administrators）なので、窓を作れるのは信頼の範囲の管理者に限られる。受容する。
- **2 つの親の ACL が同時に緩んだ場合**: 両方の記録を消された・両方とも古い内容に戻された場合は見えない。ただし、両方を消されても利用者の証明書が残っていれば、上の決まりでその証明書は失効になる。利用者の記録にだけあったサービスの証明書の拇印は失われる。受容する。
- **妨害**: 緩んだ側の記録に別のアカウントが拇印を書き足す・記録を消して作り直しを強いる・ロックファイルを握る、はどれも接続を止めるだけで、秘密は漏れない。§3 の妨害と同じく受容する。
- **書けないとき**: 上の「整えられないとき」と §7。

### 4.5 Hub シェルの Desktop モード

- Desktop モードも pin した https で開く。**pin の出どころはディスクではなく、同じプロセスの Hub が実際に載せた証明書（メモリ上）**にする。作り直しとの競合や置き場の差し替えの影響を受けない。
- **管理画面の妨害への備え（判断 8）**: 8723 を別のアカウントに握られても管理画面を開けるよう、シェルの webview は、プロセスの中の TLS の待ち受けへ、その証明書で pin して開く。シェル専用の待ち受けは**いつも OS が選ぶ別のポート**に bind し、8723 には bind しない（8723 を先に握ると、ディスクの証明書で ChronoGazer のために待ち受ける口が開けなくなるため）。8723 はディスクの証明書の待ち受け専用で、ChronoGazer のための口として扱う。採らない場合は「8723 を握られたら管理画面も開けない」を受容として判断に書く。
  - さらに進めた案: シェル専用の待ち受けは、**プロセスの起動ごとにメモリの中だけで作る使い捨ての証明書**で待ち受ける（ディスクに書かない）。管理画面がディスクの鍵の状態（無い・壊れ・作り直し中）に左右されなくなり、鍵が壊れて 8723 の TLS が無いときも管理画面は開ける。ディスクの鍵は ChronoGazer のための 8723 だけに使う。判断 8 でこちらを推す。
- 鍵が壊れている・8723 が取れないときの理由と直し方は、§4.2 のとおりシェル自身の画面とトレイの通知で出す（webview が Hub を開けなくても見える）。
- `capabilities/default.json` の `http://127.0.0.1:*/*` を外す。#644 の留保（`remote.urls` の http は Desktop 用に残る）がここで閉じる。外す前に、`tauri dev`・E2E・開発用の http の口が invoke を失わないか確かめる。
- **シェル専用の待ち受けの Tauri の権限と遷移**: シェル専用の待ち受けは OS が選ぶポートなので、静的な `capabilities/default.json` には書けない。`https://127.0.0.1:*/*` のようにポートを広げて書くと、シェル以外のポートにも capability の権限（プラグインのコマンドを含む）が及ぶので、**そう書かない**。
  - **実行時に、その origin だけの capability を足す**: 待ち受けを bind してポートが決まった後で、`https://127.0.0.1:<そのポート>/*` だけを `remote.urls` に持つ capability を、Tauri 2 の実行時の capability の追加（`Manager::add_capability`）で登録する。権限は管理画面が実際に使うコマンドだけに絞った、シェル用の別の権限の組にする（今の Service 用の `default.json` と分ける）。実行時の追加が使えない・origin を正確に書けない場合は、PR3 の最初に確かめて設計に戻す（静的に広げる案は採らない）。
  - そのうえで、次の 3 つで絞る。
  - 遷移: シェルが navigate するのは、自分のプロセスが今開いている待ち受けの origin（`https://127.0.0.1:<そのポート>/`）だけ。webview の中からほかの `127.0.0.1` のポートへ移る遷移は断る（navigation の handler で origin を照合する）。
  - 証明書: WebView2 の `ServerCertificateErrorDetected` で許すのは、その origin で、メモリ上の使い捨ての証明書と一致するときだけ（Service モードの `allowed_certificate` と同じ仕組み）。ほかのポートで同じ利用者の別のプロセスが出す証明書は通らない。
  - **このイベントは、WebView2 が証明書を検証できなかったときにしか来ない**（OS が信頼する証明書なら一致の確かめを通らずに表示される）。そのため、シェルの管理画面の相手の正しさは **pin ではなく「相手が自分のプロセスの socket であること」で保証する**。pin は、その上の二重の守りとして扱う。社内 CA などで別のアカウントが 127.0.0.1 の信頼される証明書を持っていても、その証明書を出すには、シェルが開くポートで待ち受ける必要がある。それは次の 1. と 2. で塞ぐ。
    1. **socket の寿命と表示の寿命を揃える**: シェル専用の待ち受けの socket は、シェルのプロセスが終わるまで握り続け、途中で閉じない（Hub の再起動・作り直しでも、この socket は閉じずに中身だけ替える）。webview がこの origin を表示している間に socket を手放すことはない。どうしても閉じるとき（待ち受けが失敗したなど）は、**先に webview をシェルに同梱した画面へ移してから**閉じる。
    2. シェルが開くのは、**自分のプロセスが bind して握っている**待ち受けのポートだけ。ただし Windows では、ほかのプロセスが `SO_REUSEADDR` で同じポートに bind できる場合があるので、シェル専用の待ち受けは **bind の前に `SO_EXCLUSIVEADDRUSE` を必ず付ける**（8723 の待ち受けも同じ）。付けていれば、握っている間はほかのプロセスがそのポートで待ち受けられず、相手を取り違える先取りが起きない（8723 の先取りの問題は、Hub が閉じている間に起きる）。今の Hub の待ち受けが付けているかは PR2 の最初に確かめる。
    3. （1. と 2. が主で、これは補い）別の利用者（管理者でない）が、127.0.0.1 について OS に信頼される証明書を用意する道は、ふつうは無い。公開 CA は予約 IP に証明書を出さず、ルートのストアに足せるのは LocalMachine なら管理者、CurrentUser なら本人だけ。#1122 の Service モードで同じ指摘を P3 として受容した判断（2026-11-14、#1122 の会話のコメント）と同じ線引き。
  - 同じ利用者のプロセスが CurrentUser のルートに CA を足す場合は、§3 の信頼の範囲（同じ利用者は信頼する）の中として扱う。
  - invoke: 実行時の capability が許すのはその origin だけなので、プラグインのコマンドも含めて、ほかの origin からは呼べない。アプリのコマンドの側でも呼び出し元の origin を照合する（二重の守り）。
- origin が `http://127.0.0.1:8722` から `https://127.0.0.1:8723`（または別のポート）に変わるので、利用者は 1 度ログインし直す。#1123 の loopback の規則（「ログイン状態を保持」を出さない）がそのまま効く。

### 4.6 組み合わせごとの扱い

| ChronoGazer \ Hub              | サービス       | デスクトップ版（同じ利用者）   | デスクトップ版（別の利用者） |
| ------------------------------ | -------------- | ------------------------------ | ---------------------------- |
| デスクトップ                   | 今どおり繋がる | **繋がる（本設計）**           | 繋がらない（狙いどおり）     |
| サービス（chronogazer-server） | 今どおり繋がる | **繋がらない（推奨、判断 4）** | 繋がらない                   |

- **chronogazer-server** はサービスの置き場だけを読む読み手にする（「今の利用者」＝サービスのアカウントのプロファイルを読まない）。デスクトップ版の Hub と組もうとしたら、今と同じ `HubTls` の誤りで理由を出す。
- **別の管理者として実行した Hub**（標準ユーザーが「管理者として実行」で別の管理者の資格情報を使う）: その管理者の `%LOCALAPPDATA%` に鍵を作るので、元の利用者の ChronoGazer とは繋がらない。同じ利用者の昇格なら繋がる。案内の文言を用意する。
- **高速ユーザー切り替え・RDP**: 利用者 B の Hub が 8723 を握っている間、A の ChronoGazer は断る（A とサービスの証明書だけを pin するため。正しい）。A の Hub はプロファイルの排他で起動できない。
- **`HubHostKind::Console`**（開発用の `banto-hub.exe`）: 既定の TLS を持たない（今どおり、明示の環境変数でだけ TLS）。判断 2 の範囲に含めない。
- **Sink**: 設定に利用者の証明書を手で貼れば、デスクトップ版の Hub と組めてしまう。「手順書に載せない（サポートしない）」にとどめるか、「利用者の置き場の証明書と同じなら断る」まで止めるかを判断 6 で決める。

## 6. 実機確認の観点（PR5）

- 一般の利用者でデスクトップ版の Hub を起動すると、`%LOCALAPPDATA%\BantoHub\tls\` ができ、8723 で TLS を待ち受ける。返る証明書の拇印が置き場の証明書と一致する。
- 同じ利用者の ChronoGazer デスクトップが `https://127.0.0.1:8723` で繋がる。Hub をサービスへ切り替えても、接続先を変えずに繋がる（両方の pin）。
- サービスへ切り替えた直後、8723 が空くまでの間の振る舞い。デスクトップ版の Hub が動いている間にサービスを開始したときの振る舞い。
- **別のアカウント**で、Hub を閉じている間に 8723 を先取りする（squat.py）。ChronoGazer は握手で断り、何も届かない。そのまま Hub のデスクトップ版を起動したとき、シェルの管理画面は開ける（判断 8 の口を採った場合）。
- 別の利用者の Hub が動いている間、ChronoGazer は断る。
- Hub が動いている間に、**別のアカウント**から、シェル専用の待ち受けのポートと 8723 に `SO_REUSEADDR` で bind を試みる。どちらも断られる（`SO_EXCLUSIVEADDRUSE`）。
- 失効の記録（§4.4.2 の場面）: ChronoGazer を入れていない PC でも 2 か所に作られる（場面 1）。サービスの Hub だけの PC では ChronoGazer が作る（場面 3）。初期化の途中で止めても、次の起動で続きから仕上がる（場面 4）。片方だけを消すと、証明書があれば失効して止まり、作り直しで戻る（場面 13）。証明書が無ければ、ふつうの起動で戻る（場面 14）。Hub が動いている間に ChronoGazer が失効を記録すると、Hub は次の周期で 8723 の待ち受けを止める（場面 7）。
- 同じ利用者の昇格・別の管理者として実行した Hub の振る舞い。
- サービスの置き場が無い PC で、案内がデスクトップ向けになる。
- トレイの「作り直す」で、ChronoGazer が操作なしで張り直す。作り直しの最中に ChronoGazer が読んでも壊れない。
- 置き場の ACL を壊す（別の利用者に書き込みを許す）と、Hub は TLS 無しで起動して理由を出し、ChronoGazer もその証明書を pin にせず警告を出す。

## 7. 残る留保

- MSIX での置き場の実際の見え方（publisher cache folder など）はフォーク側で確かめる。
- 妨害（8723・プロファイルの mutex の先取り）は、判断 8 の口で管理画面だけを守り、ChronoGazer の接続の妨害は受容する案。
- **失効の記録の名前と形は実装（PR1・PR4）で決める**: 置き場・状態（`準備中`・`確定`）・整える手順・照合の時点・書けないときの扱いは §4.4.1 で決めた。フォルダとファイルの名前、記録の形の細部（拇印の並びの書式）は、置き場の確かめと一緒に実装で決める（2026-11-14、#1127 の Codex CLI の指摘）。
- **失効の記録がどこにも書けないまま再起動された場合**: 露出を見たのに記録が書けず（ディスクが一杯など）、その後に ACL が直されて再起動されると、露出の証拠が残らず、同じ証明書を再び使いうる（2026-11-14、#1127 の Codex の指摘）。記録が書けない状態で証拠を残す手は無いので、本設計では受容する。その間は §4.4 のとおり pin に入れず「作り直してください」を出し続けるので、利用者が ACL だけを直して作り直さないまま再起動したときだけ起きる。実装（PR1・PR4）で、記録を書く前に置き場の空きと書き込みを確かめる・書けなかったことを Windows のイベントログにも残す、といった補いを検討する。
