## 1. 前提と機材

| 項目        | 内容                                                                                                                                                                                                                                                                                                                    |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PostgreSQL  | 15 以上。ローカル smoke は `127.0.0.1:5432`（テスト用、`postgres/postgres`）。S7 は **別マシン（LAN 越し）**の PostgreSQL                                                                                                                                                                                               |
| DB ユーザー | Source 用: `SELECT` のみの読み取り専用ユーザー。Sink 用: 保存先テーブルへの `INSERT` と `SELECT`（`SELECT` は起動時の検査と、グループが `error` になった後の 30 秒ごとの再検査 `SELECT ... LIMIT 0` に要る。稼働中の INSERT には要らない。2026-10-17 訂正、#616）。**Hub とサイドカーは DDL を発行しない**（設計 §5.3） |
| Hub         | `v0.2.0-alpha.1` 以降の main（S0〜S6 込み）。収集は Running にできる状態（PLC 接続は無くてもよい）                                                                                                                                                                                                                      |
| サイドカー  | `banto-hub-sink.exe`（`cargo build --release -p banto-hub-sink`）と、保護された置き場 `%ProgramData%\BantoHub\sink\banto-hub-sink.toml`（#630 以降は exe 隣を読まず、あると起動しない。置き場は `banto-hub-elev.exe prepare-sink-config` で作る）                                                                       |
| Hub の TLS  | Hub のサービスに `BANTO_HUB_TLS_PORT`・`BANTO_HUB_TLS_CERT`・`BANTO_HUB_TLS_KEY`。サイドカーは loopback の `http://` を断る（#644、§3.3 の前提・P-5）                                                                                                                                                                   |
| API キー    | サイドカー用に **`admin` + `read`** の両スコープ（設計 §5.2 訂正、2026-09-06）。API キー画面のプリセット（sink 画面のリンク）で発行できる                                                                                                                                                                               |
| 注意        | Windows のプロファイルロックはマシン全体（`Global\BantoHub.<profile>`）。評価用 Hub が動いているマシンで別 Hub を起動しない                                                                                                                                                                                             |

Source 側のサンプル（読み取り専用ユーザーで参照できるビュー）:

```sql
CREATE TABLE machine_status (machine_id int PRIMARY KEY, temperature float8, pressure numeric(8,2), running bool, updated_at timestamptz);
INSERT INTO machine_status VALUES (1, 41.5, 101.30, true, now());
```

Sink 側のサンプル（サイドカーが推奨 DDL として表示するものと同じ）:

```sql
CREATE TABLE tag_history (ts timestamptz NOT NULL, tag_id bigint NOT NULL, external_name text NOT NULL, value double precision, quality text NOT NULL);
```

## 3.1 DB ブリッジ（取り込み口 `push`、R2a）の実機確認

R2a-3c（2026-10-21）で追加。**オーナー同席で行う（未実施）**。§2・§3 と同じ機材で、Hub 内の DB Source（A-1〜A-5 の接続・グループ・タグ）を残したまま、同じ SQL を読む DB ブリッジの `push` 接続を並べ、両方のタグが同じ値・同じ品質を出すことを確かめる（自動テストは `apps/banto-hub-sink/tests/bridge_parity.rs`、[banto-hub-ingest-design.md](banto-hub-ingest-design.md) §10.4 の 11 場面。実機ではネットワーク越しの DB・サービスとしてのサイドカー・画面を確かめる）。運用の手順は [banto-hub-operations.md](banto-hub-operations.md) §12「DB ブリッジ（取り込み口 `push`）」。

| #    | 手順                                                                                                                                                                                                                                        | 期待                                                                                                                                                                                                                 |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| B-16 | 接続を作成: protocol `push`、受信のタイムアウト 10 秒、ブリッジの区画で読み取り先 = A-1 の接続、クエリ = A-3 と同じ SQL・周期 1000ms、列 = 4 列（キー = 列名）。この接続の下にグループを作り、A-5 と同じ型で 4 タグ（address = キー）を登録 | 量の見積もり（約 1 メッセージ/秒・4 件/秒）が上限の 8 割以内と表示されて保存できる。再設定のドロワーに送り手向けの URL（`/api/v1/ingest/{id}/…`）とスコープ `ingest:#{id}` が出る                                    |
| B-17 | API キー画面で `admin` + `read` + `ingest:#{B-16 の id}` のキーを発行 → `banto-hub-sink.toml` の `api_key` を差し替え → `prepare-sink-config` → 管理者のコンソールで `banto-hub-sink.exe run`（収集は停止中）                               | ログに「ブリッジ {名前}（#id）を開始します」「送信口に繋がりました（… 収集 停止）」。パスワード・キーがログに出ない。DB の `pg_stat_activity` に `banto-hub-sink-bridge {名前}` の接続が**無い**（停止中は繋がない） |
| B-18 | 収集を開始し、DB Source の 4 タグと B-16 の 4 タグをタグ一覧（または `GET /api/v1/values`）で並べる                                                                                                                                         | 1〜2 周期で両方 Good、**同じ値**（numeric の pressure・bool の running = 1・timestamptz の updated_at = epoch ミリ秒も一致）。状態画面の B-16 の接続は「受信中」、ドロワーの送り手にキーの名前と接続元が出る         |
| B-19 | A-7（`UPDATE ... temperature = 42.0`）・A-8（`pressure = NULL`）・A-9（`DELETE`、0 行）を順に行い、それぞれ戻す                                                                                                                             | どの段も両方のタグが同じ品質で追従する（A-8 は pressure だけ Bad、A-9 は 4 タグとも Bad で Stale を挟まない）。0 行の間、ドロワーの送り手の状態に「結果が 0 行です」                                                 |
| B-20 | DB 側で `ALTER TABLE machine_status RENAME TO machine_status_x`（クエリの失敗）→ 10 秒後に名前を戻す                                                                                                                                        | 両方とも 1 周期だけ前の値で Stale、その後 Bad。名前を戻すと設定の変更なしで Good（DB Source は 5 秒以内）。送り手の状態に「クエリが失敗しました」                                                                    |
| B-21 | PostgreSQL を停止して 1 分、再起動                                                                                                                                                                                                          | 両方 Bad、送り手の状態に「DB に接続できません」（パスワードは出ない）。B-16 の接続は「受信中」のまま（サイドカーと Hub は繋がっている）。再起動で両方とも自動で Good                                                 |
| B-22 | 収集を停止 → 停止中に `UPDATE ... temperature = 43.0` → 収集を開始                                                                                                                                                                          | 停止で両方 Bad、`pg_stat_activity` にブリッジと DB Source の接続が無い。開始の直後に停止前の 42.0 が Good で出ない（トレンド・記録にも出ない）。最初の問い合わせの後で両方 43.0 の Good                              |

| B-25 | サイドカーを Ctrl+C（サービスなら `Stop-Service BantoHubSink`）で止めて 30 秒、再開                                                                                                                                                         | 止めてから約 10 秒（受信のタイムアウト）は直前の値で Good、その後 4 タグ Bad・「送り手待ち」・接続イベント `plc_disconnected`（「送り手からの通信が … 秒ありません」）。再開で Good。DB Source は影響を受けない      |
| B-26 | B-17 のキーを `admin` + `read` だけのキーに戻して起動                                                                                                                                                                                       | ログに「ブリッジ … は動かしません: 権限なし」が 1 回。DB に繋がず、B-16 の接続は「送り手待ち」。Sink（B-4）は動き続ける                                                                                              |
| B-27 | Hub を再起動（B-17 のキーに戻した後）                                                                                                                                                                                                       | サイドカーは落ちずに 1 秒 → 30 秒のバックオフで再接続し、Hub の収集が Running に戻ると Good。Sink の購読も再開                                                                                                       |
| B-28 | **S7 本番**: B-13 の 24 時間に B-16 のブリッジを含める（同じ DB を DB Source とブリッジの両方で読む）                                                                                                                                       | 24 時間の間、両方のタグの値と品質が一致し続ける。状態画面の取り込み口の `rateLimited`・`tooManyItems`・`rejected` が 0。切断・再接続・DB 再起動の後も両方が同じ状態に戻る                                            |

## 3.2 R2b-1 の移行と秘密値の封印（v0.2.0-alpha.34）の実機確認

R2b-1f（2026-10-22）で追加。**オーナー同席で行う（未実施）**。alpha.34 は DB を戻せない形に作り直す（migration 0025・0026、運用ガイド §1「alpha.34 への更新と、移行・戻し方」）ので、**必ずオーナーの実運用の DB の複製**で確かめ、本番の DB には触らない。PostgreSQL は §1 の機材（postgres 接続が 1 件以上ある複製が要る）。Windows 実機が 2 台要る（C-11・C-12 の「別の PC」は、DPAPI のマシンの鍵が違う別の Windows。同じ PC の別アカウントでは確かめにならない）。

準備: alpha.33 の Hub が動く PC で、停止して `banto-hub.sqlite3`（`-wal`・`-shm` ごと）を複製に取る。複製は alpha.33 のインストーラで入れた検証用の profile に置く（`BANTO_HUB_PROFILE`）。複製の接続・タグ・承認待ちのキュー（パスワードを含む変更を 1 件積んでおく）の件数を控える。

| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C-1  | alpha.33 の複製を、alpha.34 の Hub（検証用 profile）で**初めて**起動する                                                                                                                                                                      | 起動する（ログに `[WARN]` 以外の失敗が無い）。接続・タグ・グループ・キーの件数が C 準備の控えと一致する                                                                                                                   |

#### P-1・P-5・P-7 の決定（2026-10-28 オーナー決定、下の推奨案どおり）

**P-1 LAN を切る方法**: **PostgreSQL の PC とスイッチの間のケーブルを抜く**ことを勧める。抜いた・挿した時刻を R-4 に書く。

R-3 欠落と重複の照合（D-3 の後に 1 回。mode `interval` 1000ms の前提。`<開始>`・`<終了>` は D-3 の時刻）:

```sql
-- 欠落: タグごとに 2.5 秒を超えた間隔を一覧にする
SELECT tag_id, prev_ts, ts, ts - prev_ts AS gap
FROM (SELECT tag_id, ts, lag(ts) OVER (PARTITION BY tag_id ORDER BY ts) AS prev_ts
      FROM tag_history WHERE ts BETWEEN '<開始>' AND '<終了>') t
WHERE ts - prev_ts > interval '2.5 seconds'
ORDER BY ts;

-- 重複: 同じタグ・同じ ts・同じ値の Good の行（再送による重複の候補、設計 §5.4）
SELECT tag_id, ts, value, quality, count(*)
FROM tag_history WHERE ts BETWEEN '<開始>' AND '<終了>' AND quality = 'good'
GROUP BY tag_id, ts, value, quality HAVING count(*) > 1;
```

`ts` は値の取得時刻（ptime）で、DB Source の 1 秒の周期と Sink の 1 秒の記録の周期は独立に回る。そのため事象が無くても、同じ `ts` の 2 行（見かけの重複）とおよそ 2 秒の空き（見かけの欠落）が周期的に出得る。値が Stale の間も `ts` は進まない。**主な指標は R-2 の時間ごとの行数**とし、上の 2 つの SQL の結果は**候補の数**として記録し、R-4 の事象と突き合わせて、事象で説明できない候補を別に数える。同じ値の正常な定周期の再採取と再送による重複は同じ行になり得て、1 行の欠落と 1 行の重複が相殺されれば時間ごとの行数も一致するので、**この記録だけでは本当の欠落・再送による重複の有無を確定しない**（保存済みの重複を独立に確かめられないときは「確定できない」と書く）。Sink のログの「保存結果は不明です。行は再送します」は、BEGIN・INSERT・COMMIT のどこでの期限切れでも出て、保存されたかは分からないままなので、確定の根拠にしない。候補を R-4 の事象と突き合わせるときの補助として時刻を控えるだけにする。
