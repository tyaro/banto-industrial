## 1. 実装をサブエージェントに委譲する前（指示書に必ず書く）

- [ ] **ブランチを最初に切らせる**（`git checkout main && git pull --ff-only origin main` → `git switch -c ...` → `git status -sb` で確認）。main を汚させない。
- [ ] **入れ子のサブエージェント禁止**と明記（Agent ツールを呼ばせない）。
- [ ] **`.claude/worktrees` に入らない**と明記（メイン checkout で作業させる）。
- [ ] **検証コマンドを順序つきで全部書く**（下の §2 をそのまま貼る）。書かなかったコマンドは実行されない。
- [ ] **やらないこと**を列挙する（スコープ外の改善を勝手にやらせない）。
- [ ] **「指示に答えが無い分岐は、変更せずに選択肢と推奨を報告して止まる」**と明記。
- [ ] 報告してほしい項目（PR 番号・判断表・迷った点）を列挙する。
- [ ] 難易度でモデルを選ぶ（機械的 = haiku / 標準 = sonnet / 並行・安全・横断 = opus・fable）。CLAUDE.md の分担に従う。

## 2. 検証の順序（この順番で、全部）

1. [ ] **`cargo fmt --all --check`** — **一番忘れる。#385 はこれだけで CI が落ちた。**
2. [ ] `cargo test -p <触ったクレート>`
3. [ ] `cargo clippy -p <触ったクレート> --all-targets -- -D warnings`
4. [ ] **`pnpm exec eslint <触った src と e2e>`** — **`pnpm --filter <app> check`（svelte-check）は ESLint を回さない。** CI には両方ある。
5. [ ] `pnpm --filter <app> check` → `pnpm --filter <app> test`
6. [ ] `pnpm exec prettier --write <編集した md/ts/svelte 全部>` → **整形後にもう一度 test と eslint**（整形が壊すことがある）
7. [ ] E2E の前に必ず: `pnpm --filter <app> build` → **`cargo build -p <core> --bin <bin> --features embed-ui`**（**`--features embed-ui` を落とすと smoke が全滅する**）
8. [ ] E2E は **1 回だけ**。実行前に `Get-Process <bin>` が 0 で、ポートが空いていることを確認。**同時に 2 つ走らせない**。失敗の詳細は `e2e/test-results-*/<test>/error-context.md`
9. [ ] `cargo deny check`（CI にある）

## 3. E2E の罠（全部踏んだ）

- [ ] `BantoGrid` は行を仮想化していて **CI の描画窓は 20 行**。行を名前でクリックする前に検索ボックスかツリーで絞る。
- [ ] フィクスチャは `beforeAll` の先頭と `afterAll` の両方で掃除する（banto-hub は `banto-hub-fixture-cleanup.ts` の `cleanupFixtures`）。
- [ ] **スペックのファイル名は辞書順が実行順**。初回セットアップを行う `*smoke*` より後に来る名前にする（`workers: 1` / `fullyParallel: false`）。
- [ ] 狭幅の検証は `400x800`（ツリー退避）と `880x800`（ペインが出る狭幅）を使い分ける。
- [ ] **E2E だけ落ちるときは実装のバグを疑う**（過去 2 回とも実バグだった）。テストを緩めない。

## 5. 設計の規律（レビューで繰り返し出た指摘）

- [ ] **エラーを「空」に潰さない**。「0 件でした」と「読めませんでした」を別の状態にする（#332 の 6 状態）。
- [ ] **1 件の事故で全体を止めない**。選んだタグの 1 つが消えた・名前が使えないなら、**それを一覧に出して残りは動かす**（#385 で 3 回出た）。
- [ ] **状態を別軸に保つ**。下位の失敗（購読）で上位の状態（接続の 6 状態）を書き換えない。ただし**ユーザーの導線は合流させる**（認証エラーなら手動キー入力に辿り着けること）。
- [ ] **「自動で再試行します」と書いたら、本当に再試行する経路があるか確かめる**（#385: 終端状態が再試行対象から漏れていて文言が嘘になった）。
- [ ] **「起こす条件」と「実際にやる条件」を 1 つの述語にする**（#385: `needs_retry` は起こすのに `must_restart...` が張り直さず空振り）。別々に状態を列挙しない。
- [ ] **判断は純関数に出して、状態の総当たりを表でテストする**（モックの足場が重い経路ほど効く）。
- [ ] **ロック順序を一方向に固定**し、doc に書く（#385: 操作ロック → 購読ロック。読み取り専用のポーリング経路はロックを取らない）。
- [ ] **バックグラウンドの見張り・ポーリングを足したら、次を必ず設計する**: 二重起動の防止 / 停止条件（親が落ちたら止まる）/ 停止と再開の競合 / **無駄撃ちの抑制**（変わりようのない安定状態で外部を叩かない）/ **飛行中の応答が新しい状態を巻き戻さない**こと。
- [ ] **非同期の書き戻しは、途中で割り込まれても消えないか**を確かめる（#385: 見張りの `hydrate` が未 flush の変更を握り潰した）。
- [ ] **平文の資格情報は、それを持つ層の外に出さない**（`SecretApiKey` より外へ `String` を返す口を作らない）。
- [ ] 回帰テストを書いたら、**直した箇所を戻すと本当に落ちるか**を 1 回確かめる。

## 6. PR とマージの運用

- [ ] PR を作ったら **Copilot のレビューを要求**し、**check-run が queued/in_progress で登録されたことを確認**する（登録されないまま待ち続けた事故あり。登録が無ければ再要求）。
- [ ] 指摘は **採る**か、**理由を書いて採らない**かのどちらか。却下はコミットメッセージと PR 本文に理由を残す。
- [ ] **CI 全緑 + 最新 head への指摘ゼロ**でマージ（squash）。指摘が残っている head でマージしない。
- [ ] PR 本文の「変更ファイル」表は**実際の差分と一致**させる（レビュー対応で増えたファイルを書き足す）。
- [ ] マージしたら: issue にコメント（完了範囲と残り）、docs の `状態:`、メモリの索引行を更新。
