## 2. 検証の順序（この順番で、全部）

1. [ ] **`cargo fmt --all --check`** — **一番忘れる。#385 はこれだけで CI が落ちた。**
2. [ ] `cargo test -p <触ったクレート>`
   - [ ] **CI の rust ジョブはテストを `cargo nextest run`（テスト 1 件 = 1 プロセスで並列）で走らせる**（2026-10-16、doctest だけ `cargo test --doc`）。ローカルでも `cargo nextest run` が使える。**`static LOCK: Mutex` の「同じプロセス内の直列化」はプロセスが別になるので効かない**。プロセスをまたいで共有するもの（名前付き mutex・固定ポート・固定パス）を使うテストを足したら、`.config/nextest.toml` の test-groups に入れる（洗い出した範囲と理由もそこ）。
   - [ ] **容量を空けるための `target` 掃除は cargo/rustc/linker が動いていないことを確かめてから行う**。#201 の検証中、別リポジトリと共有した target の `debug/examples` をリンク中に削除し、必要な object がなくなってテストのリンクが失敗した（2026-10-16）。
3. [ ] `cargo clippy -p <触ったクレート> --all-targets -- -D warnings`
4. [ ] **`pnpm exec eslint <触った src と e2e>`** — **`pnpm --filter <app> check`（svelte-check）は ESLint を回さない。** CI には両方ある。
5. [ ] `pnpm --filter <app> check` → `pnpm --filter <app> test`
   - [ ] `@banto/*` を上げた・足したら `node scripts/check-banto-optimize-deps.mjs`（`.svelte.ts` を持つパッケージが `vite.config.ts` の `optimizeDeps.exclude` から漏れていないか。漏れは `pnpm dev` だけが壊れ、build・E2E では出ない。CI の frontend-hub / frontend-chronogazer も実行、#478）
6. [ ] `pnpm exec prettier --write <編集した md/ts/svelte 全部>` → **整形後にもう一度 test と eslint**（整形が壊すことがある）
   - [ ] **`prettier --check .` をリポジトリ全体にかけない**（**`prettier --write .` は絶対にかけない**）。Windows の作業ツリーは CRLF なので、**main が CI で緑でもローカルでは 340 件の「差分あり」が出る**（CI は Linux/LF）。これを整形漏れと誤認して `--write .` を実行すると、**全ファイルの改行を書き換えた巨大な差分**になる。対象は**編集したファイルだけ**に絞る。全体を比べたいときは **`--end-of-line auto` を付ける**（2026-09-20: prettier 3.9.8 が整形結果を変えるかを調べて 340 件に当たった。**現行版で同じコマンドを回す対照**を取ったら同じ 340 件で、原因は版ではなく改行だった。**依存を上げる前後の比較は、必ず同じ条件で対照を取る**）。
   - [ ] **`npx sv migrate ...` は最後にルートの `pnpm run format`（= `prettier --write .`）を自分で走らせる**（`--no-install` でも止まらない）。2026-10-05 の banto-hub の SvelteKit 3 移行で、移行対象外の `.github/scripts/*.mjs`・`scripts/*.mjs` 4 ファイルが改行だけの差分になった。実行後は `git status --short` で対象アプリ外の変更を `git checkout --` で戻してからコミットする。
   - [ ] **新しいディレクトリやファイルを追加したら `git add` 後に `node --test .github/scripts/ci-changes.test.mjs` を実行する**。全ファイル網羅テストは `git ls-files` の一覧を判定するため、未追跡ファイルは見えず、ステージ後に初めて失敗する（#632 の `interop/opcua/`）。
7. [ ] E2E の前に必ず: `pnpm --filter <app> build` → **`cargo build -p <core> --bin <bin> --features embed-ui`**（**`--features embed-ui` を落とすと smoke が全滅する**）
   - [ ] **`cargo test -p chronogazer-core` の後は `banto-serve` を `--features embed-ui` で建て直してから E2E**。`cargo test` は統合テストのために同じ `target/debug/banto-serve` を **embed-ui なしで**作り直す（2026-10-09、R1-D の D-4: `cargo test` の後の `pnpm e2e` が「フロントエンドが埋め込まれていません」で smoke から全滅した）
   - [ ] **chronogazer の E2E（`pnpm e2e`）は、加えて `cargo build -p chronogazer-core --example dev_plc`**（2 つ目の `webServer` = 開発用 PLC。R1-C の C-4 で追加。ビルドし忘れると `webServer` の起動で全体が落ちる）
   - [ ] **chronogazer の閲覧公開 E2E（`pnpm e2e:public-viewer`、#507）は `banto-serve` だけ**（上の chronogazer ビルドで足りる。`dev_plc` は不要。`BANTO_VIEWER_PUBLIC=1` の 2 台目をポート 8804 で起動）
8. [ ] **緑の確認は 1 回だけ**（通るまで回し直さない）。**反証（修正を戻して落ちるかの確認、§5）は、理由を書けば別に回してよい**。`describe.serial` は最初の失敗で以降を skip するので、反証が複数本あると 1 回では取れない（#409 で 3 回実行した。2026-09-23 オーナー決定）。反証の実行は PR 本文に「何を戻して、どのテストが落ちたか」を書く。実行前に残プロセスが 0 で、ポートが空いていることを確認（Windows: `Get-Process <bin>` / POSIX: `pgrep -f <bin>`）。**同時に 2 つ走らせない**。**E2E は worktree やエージェントが違っても同時に 1 本だけ**（同じ固定ポートを取り合う。2026-09-23 オーナー指示）。**リポジトリをまたいでも**（banto の E2E は 8798 / 8799 / 4173、banto-industrial の E2E は 8798（chronogazer）/ 8805（banto-hub、2026-10-09 に 8799 から移した - オーナーが 8799 を別の作業で使うため）/ 8802 / 8803 / 8806（chronogazer の断線 E2E がスペックの中で起動・停止する開発用 PLC、2026-10-09）を使い、8798 が重なる。banto-industrial には閲覧公開の `pnpm e2e:public-viewer`（8804、2026-10-07 #507）もあり、`pnpm e2e` や他の E2E と同時に走らせない。2026-09-24 に #234 と #429 の作業でぶつかった）。失敗の詳細は `e2e/test-results-*/<test>/error-context.md`
9. [ ] `cargo deny check`（CI にある）
   - [ ] **banto の版を上げるときに `cargo update -p banto-core -p banto-storage -p banto-server -p banto-admin-services` を使わない**。タグを付け替えるだけのつもりでも、cargo は同時に無関係な crate を**再解決して降格する**（2026-10-04 の v3.0.0 追従で `windows-sys 0.61.2 → 0.60.2`・`socket2 0.6.4 → 0.5.10` が 10 か所以上付け替わった。#450/#465/#484 と同じ型）。`Cargo.lock` の banto 4 crate の `version`/`source`（コミット SHA はタグの `git rev-parse <tag>^{commit}`）を**手で書き換え**、`cargo metadata --locked` が通ることで確かめる。
   - [ ] **`@banto/*` の git 依存を上げるとき `pnpm-lock.yaml` を手で書き換えない**（Cargo.lock と逆）。SHA・specifier だけ直すと `packages:` の `version:` が旧版のまま残り、pnpm は「lock は最新」と判断して再解決しない。ストアを再利用する `pnpm install --frozen-lockfile`（CI のキャッシュ復元・別 checkout）が `ERR_PNPM_UNEXPECTED_PKG_CONTENT_IN_STORE`（lock の 5.0.0 と実 manifest の 5.1.0 の食い違い）で落ちる。#515 のオーナーレビュー P2、2026-10-07。対処: `packages:`/`snapshots:` の `@banto/*` 項目を消してから `pnpm install --no-frozen-lockfile` で再生成し、各 `version:` が取得元の実 `package.json` と一致することを確認する。
10. [ ] **push したら、その head に対して CI の run が実際に起動したか確認する**（`gh run list --branch <branch> --limit 5`）。**PR がコンフリクトしていると GitHub はマージ ref を作れず、`on: pull_request` の CI / Supply Chain は起動しない**（Copilot のレビューは別イベントなので走り続け、気付きにくい）。起動していなければ `gh pr view <n> --json mergeable` を疑い、main を取り込んで解決する。**ローカルで緑でも、CI が走っていなければ緑ではない。**
11. [ ] **実機で Tauri のシェル（`src-tauri`）を動かす確認は、試験専用の identifier でビルドし、`CHRONOGAZER_ROOT` を作業用のフォルダに向ける**。`APPDATA`・`LOCALAPPDATA` の環境変数を差し替えても、Tauri の `app_local_data_dir()`・`app_data_dir()`・WebView2 のデータは Windows の既知のフォルダの API で解決されるので**隔離されない**（2026-10-15、#392 B2-4b の実機確認: 試験が旧データの案内の既読の印をオーナーの実際の `%LOCALAPPDATA%\dev.tyaro.chronogazer` に作った。オーナー許可で削除済み）。identifier はビルド時に `TAURI_CONFIG='{"identifier":"dev.tyaro.chronogazer.<試験名>"}'` で上書きする（#585 の A2 の実機確認と同じ）。終わったら試験用の identifier のフォルダ（`%APPDATA%`・`%LOCALAPPDATA%` の下）と作業用のルートを消す。

- [ ] **CI でだけ落ちるフレークは、まず失敗時のアーティファクト（`error-context.md` の DOM・`test-failed-1.png`・trace）で「落ちた瞬間の状態」を見る**。#399 は「共有 page の幅の戻し忘れ」と見立てられていたが、trace のビューポートは 400x800 のままで、実際は**製品のバグ**だった: サイドバーの `visibility` を**開く側でも** 0.2s 遷移させていたため、開いてから最初のアニメーションフレームが進むまで計算値が `hidden` のままになり、Esc の層判定（`escLayering.ts`）がサイドバーを見落とした。遅いランナーでしか踏まず、ローカルのキー入力では 20/20 通る。**開く遷移に `visibility` を載せない**（閉じる側だけ）。再現は「クリック → DOM 反映 → キー」を `page.evaluate` の 1 タスク内で行うと決定的に取れる（テスト 31b）。

## 5. 設計の規律（レビューで繰り返し出た指摘）

- [ ] **エラーを「空」に潰さない**。「0 件でした」と「読めませんでした」を別の状態にする（#332 の 6 状態）。
- [ ] **1 件の事故で全体を止めない**。選んだタグの 1 つが消えた・名前が使えないなら、**それを一覧に出して残りは動かす**（#385 で 3 回出た）。
- [ ] **状態を別軸に保つ**。下位の失敗（購読）で上位の状態（接続の 6 状態）を書き換えない。ただし**ユーザーの導線は合流させる**（認証エラーなら手動キー入力に辿り着けること）。
- [ ] **「自動で再試行します」と書いたら、本当に再試行する経路があるか確かめる**（#385: 終端状態が再試行対象から漏れていて文言が嘘になった）。
- [ ] **「起こす条件」と「実際にやる条件」を 1 つの述語にする**（#385: `needs_retry` は起こすのに `must_restart...` が張り直さず空振り）。別々に状態を列挙しない。
- [ ] **判断は純関数に出して、状態の総当たりを表でテストする**（モックの足場が重い経路ほど効く）。
- [ ] **ChronoGazer のシェルの終了・切り替え・復旧の判断は、ライフサイクルの表（`apps/chronogazer/src-tauri/src/lifecycle.rs` の `step`）を通す。入り口を足したら表に行を足す**（`Event` に 1 つ・`step` に判断・テストの `transition_table` に全列の期待値を書き下した行・`all_events` に 1 つ）。入り口の側でその場で別の印を読んで確かめ直さない。PR #608 では判断が `QuitGate`・`ShellGate`・`RecoveryGate`・待ちの上限・`RunEvent::Exit` の扱いに散っていて、入り口を足すたびに確かめ方を書き直し、終了 × 移り変わり × 復旧の競合の指摘が 1 件ずつ出続けた（2026-10-15 オーナー決定で 1 つの状態機械に畳んだ）。
- [ ] **ロック順序を一方向に固定**し、doc に書く（#385: 操作ロック → 購読ロック。読み取り専用のポーリング経路はロックを取らない）。
- [ ] **バックグラウンドの見張り・ポーリングを足したら、次を必ず設計する**: 二重起動の防止 / 停止条件（親が落ちたら止まる）/ 停止と再開の競合 / **無駄撃ちの抑制**（変わりようのない安定状態で外部を叩かない）/ **飛行中の応答が新しい状態を巻き戻さない**こと。
- [ ] **見張りの「放置してよい状態」を状態名だけで決めない**。下位ライブラリは同じ状態名に別々の意味を載せる（`banto-tagclient` の `Reconnecting` は「transport の backoff 中」と「**要求セットが catalog と食い違ったまま**待ち続けている」の両方）。**分類（`last_error`）まで見る**。#383 実機: タグを 1 つ消したら購読全体が二度と戻らなくなった。
- [ ] **非同期の書き戻しは、途中で割り込まれても消えないか**を確かめる（#385: 見張りの `hydrate` が未 flush の変更を握り潰した）。
- [ ] **平文の資格情報は、それを持つ層の外に出さない**（`SecretApiKey` より外へ `String` を返す口を作らない）。
- [ ] **書いた分岐が実際に到達するか確かめる**（#385: キー不在用の理由を書いたが、上流の `refresh_catalog()` が先に `AuthFailed` を返すため本番では一度も表示されなかった）。エラーの分類を足したら、**その分類が返る経路を 1 つ挙げられること**。
- [ ] **読み取りと操作で同じキューを共有しない**。読み取りに待ち時間の上限を掛けても**キュー内の要求数は減らない**ので、閲覧（viewer）のポーリングが操作（editor）の受付を塞ぐ（#408。C-2 の「投入に上限」と C-3a の「読み取りに上限」が結合して生まれた）。枠が空くのは**処理側が取り出したとき**だけにする。
- [ ] **時間切れで見捨てた非同期処理の副作用は残る**。`Promise.race` で上限を掛けても元の要求は続き、遅れて届いた応答の副作用（`AuthProvider.check()` は `401` で**その時点の**トークンを消す）は起きる。見捨てる処理は**副作用を持たない形**にし（読むだけの照合を自分で呼ぶ）、**その処理の中で `await` する要求すべてに**同じ `AbortSignal` を渡して止め（再レビューで、先に呼ぶ `/api/commissioning/status` に渡し忘れて、応答しない要求が確認のたびに積み重なった。テストで取得関数を丸ごと差し替えていたので見えなかった。本物の HTTP ヘルパーを通して `signal.aborted` を確かめる）、開始時の前提（トークン）が変わっていたら結果を使わない。#445（PR #447 のオーナーレビュー）: 遅れた `401` でトークンだけが消え、ログイン画面へ移らずに待ち続ける・ログインし直した新しいトークンまで消す、の 2 つ。
- [ ] **DB を触る背景タスクを `abort()` で止めない**。sqlx の `pool.acquire()` が新しい接続を開いている途中で future を落とすと、その接続は pool の外で生き残り（`Pool::close()` は待たない）、後で `sqlite3_close` が WAL を本体へ書き戻す。止めるのは合図で、DB 操作の途中では止めず、終わりを待つ。**待ちを時間切れで落とすときは `JoinHandle` を取り出して手放さない**（`&mut` で待ち、終わりが取れるまで持ち主に残す。取り出した handle を `timeout` ごと落とすとタスクが切り離され、もう一度の終了が掃除の途中でも「止まった」と素通りする。#597 の Codex レビュー P2）。2026-10-13、`startup_recovery` のテストで、終了の後に退けた DB の中身が SQLite に戻っていた（負荷時だけ。ChronoGazer の保持期間の掃除を終了で abort していた。`chronogazer_core::retention` の「止め方」）。
- [ ] **handler の中で `await` をまたぐ副作用は、接続の切断で捨てられる**（hyper 1.x は応答を待つ間に相手の FIN を読むと、service の future を捨てる。`half_close: false`）。完結させたい後処理（listener の入れ替え・保存・失効・監査）は `tokio::spawn` して切り離し、handler は `JoinHandle` を待って結果を返す（`JoinHandle` の drop はタスクを止めない。panic は `500` に）。#600 の全体監査（2026-10-14）: `PUT /api/settings/server` が古い LAN の listener を止めた後に切られると、slot が空のまま保存値は「公開」・監査の行も無く、setup の後の失効も飛びえた（`chronogazer_core::local_grant::run_detached`）。テストは「lock を外から持って処理を決定的に止める → 書き込み側を閉じる → 応答なしで閉じられたのを確かめる → lock を放す → 結果を上限つきで待つ」の形にすると時間に頼らない。
- [ ] **時間切れになったテストの非同期処理は、次のテストへ漏れる**。vitest はテストを時間切れで失敗にしても、その中の `await`（`vi.resetModules()` 後の動的 `import`、偽のタイマーで予約した再試行）を止めない。負荷で動的 `import` が 5 秒を超えると、1 件目が時間切れになり、残った再試行が 2 件目の呼び出し回数を狂わせて連鎖で落ちる（全体実行のときだけ落ち、単独では通る）。動的 `import` するテストは `beforeAll` で一度温めて猶予を延ばし、`afterEach` で記録した `import` の決着を待ってからタイマーを消す。**「全体実行でだけ落ちる＝負荷のせい」と決めつけず、前のテストからの漏れを疑う**（#559。#554・#555 の作業で 2 回見て「負荷による一時的な失敗」と片付けていた）。
- [ ] **非有限の浮動小数点（NaN・±∞）は JSON で `null` になる**。品質フラグと食い違うので、**公開する形へ変換するときに正規化する**（#408）。
- [ ] **SQLite で、書き込みの前に読み取りを挟むトランザクションは `begin_with("BEGIN IMMEDIATE")` で始める**。素の `begin()`（`BEGIN DEFERRED`）は、読み取りでスナップショットを張った後に別の接続が書き込みを確定すると、WAL では書き込みが待たずに `SQLITE_BUSY_SNAPSHOT`（"database is locked"）で失敗し、REST は 500 になる。`busy_timeout` を長くしても効かない。別の行への書き込みでも起こる（#527 のオーナーレビュー P2、2026-10-08。理由の詳細は `apps/banto-hub/core/src/sink/service.rs` のモジュール doc、未対応の箇所は #528）。回帰テストはファイルの DB で接続を 2 つ開き、片方が書き込みを持ったままもう片方を始める形にすると決定的に落とせる。
- [ ] 回帰テストを書いたら、**直した箇所を戻すと本当に落ちるか**を 1 回確かめる（E2E での反証は §2-8 の「緑の確認」の回数に数えない）。
  - [ ] **反証の書き換え・書き戻しの後は、触ったファイルを `touch` してから cargo を回す**。退避した元のファイルを `cp` で書き戻した直後の `cargo test` が、作り直さずに**反証の版のまま**テストを走らせたことがある（#586: 書き戻した後も同じテストが落ち続け、`touch` してから回すと通った。原因は特定していない。cargo は更新時刻で作り直しを判断するので、その周辺と見ている）。逆向きに起きると「戻しても落ちない（= 反証にならない）」と誤読する。
- [ ] **キー・トークン・ID の失効や再利用は、必ず「同じ接続先のものか」を確かめてから**。連番 ID は接続先ごとに独立なので、別の接続先へ投げると無関係な第三者のものを失効させる。**#382（製品）と #387（確認ハーネス）で同じ間違いを 2 回した。**
- [ ] **`PlcConnection` に列を足すときは、`banto-tags` の `COLUMNS` だけでなく `banto-collect` の `RegistrySnapshot::load_connection` の SELECT も合わせる**。`FromRow` は名前で列を引くので、テーブルに列があっても SELECT から落とすと、preflight が「no column found for name」で 422 になる（#605。`load()` はサービス経由なので通り、トランザクション内の `load_connection` だけが落ち、hub の REST テストが 58 件落ちた）。
- [ ] **並行テストの時間切れは、書き手が終わっていないことと読み手の欠落とを分ける**。`banto-tsquery` の `concurrent_reads_during_writes_never_corrupt_or_error` は、読み手が壊れていなくても 50 flush が 10 秒に収まらないと「46 件で打ち切り」になる（windows-latest、#605 の CI run 38620658017）。上限はハング用にし、書き手が終わったあとの読みで全件が見えることを確かめる。
- [ ] **外から来た名前（profile-id など）をパスに join する前に、Windows で別の場所を指しうるものを断る**。Windows の `Path::join` は**ドライブの接頭辞を持つ要素（`C:`・`x:y`）で前を捨てる**ので、`root.join("profiles").join("C:")` は `C:`（C: の今のフォルダ = ドライブ相対）になる。`/`・`\`・`..` を断るだけでは足りない。`:`（代替データストリームも）・予約デバイス名（`NUL`・`COM1`、`nul.txt` も）・末尾の `.` と空白（Win32 の正規化で落ちる）も断り、昇格の境界では許可リスト（英数字・`_`・`-`）にする（#626、2026-10-16: `grant-profile-acl <user> C:` が昇格したプロセスの C: の今のフォルダを再帰で書き換えうる経路だった。`profile_paths::validate_profile_id`・`profile_grant::validate_strict_profile_id`）。
- [ ] **OPC UA の listener の起動は時間がかかる場合がある（初回 10 秒超）。起動の完了は `GET /api/opcua-status` で待つ**。`opcua_admin_settings_round_trip_and_reconfigure_listener` は Windows CI で初回 listener 起動が 10 秒を超えた（PR #627、run 38871877894）。起動経路には一時 RSA 鍵生成も含まれるが、タイムアウトの直接原因と確定したわけではない。#634（2026-10-17）で `PUT /api/opcua-settings` は保存して起動を始めたらすぐ返る形にしたので、**PUT の上限は他と同じ 10 秒**にし、起動済み（`running`）を状態の API のポーリングで待つ。その待ちにだけ長めの有限上限（60 秒、ハング検出用）を与え、`failed` なら理由を出して落とす。PUT の 200 を「listener が待ち受けている」と読まない（interop の `smoke.py` も同じ）。

## 6. PR とマージの運用

- [ ] **当面（2026-09-19 オーナー指示）、レビューはオーナーが行う。Copilot のレビューは要求しない。**クォータ上限で当面使えないため。**PR を出したら、CI 全緑と自分の監査結果を報告してオーナーのレビューを待つ**（マージ可否も同じくオーナー判断。この節の末尾を参照）。Copilot が復帰したら、下の 3 項目（要求・登録確認・push のたびに要求し直す）を戻す。
- [ ] **Copilot が「レビューした」かどうかは `state` ではなく本文で判断する**。クォータ上限のときも `state: COMMENTED` のレビューが 1 件付き、指摘 0 件に見える（本文が「unable to review ... reached their quota limit」）。`reviewRequests` も提出後は空になるので、要求が登録できなかったのか提出済みなのか区別できない。**`gh api repos/<owner>/<repo>/pulls/<n>/reviews --jq '.[].body' の先頭を必ず読む**。#394〜#397 の 4 本が、外部レビュー 0 のまま「Copilot レビュー済み」に見えていた（2026-09-19）。
- [ ] （Copilot 復帰後）**suppressed（折りたたみ）指摘も開いて読む**。#385 で見送った 1 件が、そのまま実機で再現した（#383 の `Reconnecting` 固まり）。
- [ ] （Copilot 復帰後）**push したら、CI の起動確認と一緒にレビューも要求し直す**（新しい head にはレビューが自動で付かない。要求を忘れて 45 分ポーリングした事故あり）。
- [ ] **オーナーに渡す前の自分の監査では、これまで漏れた層を必ず当たる**: **失敗経路での状態の落とし方**（成功を確かめる前にフラグを降ろしていないか）/ **識別子が変わったときの持ち越し**（別の接続先・別の対象に編集中の下書きを持ち込んでいないか）/ **「返ってこない」障害**（reject ではなく無応答。上限が無ければカウンタもループも止まる）。#397 のオーナーレビューで、この 3 つがそれぞれ 1 件ずつ出た（2026-09-19）。

- [ ] 指摘は **採る**か、**理由を書いて採らない**かのどちらか。却下はコミットメッセージと PR 本文に理由を残す。
- [ ] **CI 全緑 + 最新 head への指摘ゼロ**でマージ（squash）。指摘が残っている head でマージしない。
- [ ] PR 本文の「変更ファイル」表は**実際の差分と一致**させる（レビュー対応で増えたファイルを書き足す）。
- [ ] **マージの成立を確かめてからブランチを消す**。`gh api` は `unexpected EOF` で落ちることがあり、結果を見ずに削除すると **PR が未マージのままクローズされる**（2026-09-17 に #389 で実際に起きた）。`gh pr view <n> --json state,mergedAt` が `MERGED` であることを確認してから削除する。取り違えたときは、ローカルにコミットが残っていれば `git push origin <sha>:refs/heads/<branch>` → `gh pr reopen` → マージのやり直しで復旧できる。
