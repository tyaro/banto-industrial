## 1. 製品コンセプト

**ペーパーレスレコーダ（デジタル記録計）のソフトウェア版**。
既設 PLC（三菱 MELSEC、MC/SLMP）からタグ値を周期収集して時系列保存し、
リアルタイム/ヒストリカル/ハイブリッドトレンドと計器表示を提供する。

- 実機レコーダ（数十万円・チャネル数固定・専用ハード）に対し、
  **既設PLC + 現場PC（またはミニPC1台）でチャネル数自由**を武器にする
- banto テンプレート由来: デスクトップ（Tauri）+ LAN ブラウザ配信の二形態。
  現場の壁掛けモニタ（キオスク、認証無効モード）と事務所ブラウザ閲覧
  （viewer ロール）を同一プロセスで賄う
- **記録計であって SCADA ではない**: 読み取り専用・表示は固定パターン。
  スコープの護りは §7

### 対象環境

| 項目              | v1                                                                                                                                                                                                                     |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OS                | Windows 10/11（デスクトップ + LAN サーバ）                                                                                                                                                                             |
| PLC               | **Modbus TCP を先行対応**（2026-07-12 決定: シミュレータ/ツールが豊富でデバッグ容易なため開発初期はこちら）→ 三菱 MELSEC（MC/SLMP）を v1 リリースまでに追加（本命ターゲット）。プロトコルは trait で差し替え可能に設計 |
| 同時接続 PLC 台数 | 4 台まで                                                                                                                                                                                                               |
| クライアント      | デスクトップ 1 + LAN ブラウザ数台（banto 準拠）                                                                                                                                                                        |

## 2. 用語

| 用語     | 定義                                                                  |
| -------- | --------------------------------------------------------------------- |
| タグ     | 収集点。名前 + PLC アドレス + データ型 + スケーリング + 単位 + 小数桁 |
| グループ | 表示の単位。最大 **8 ペン**（タグ参照）を束ね、表示種別を持つ         |
| ペン     | グループ内のタグ参照 + 表示属性（色は banto チャート系列色を既定）    |
| 品質     | サンプル毎の Good / Bad（通信エラー）/ Stale（更新停止）              |

## 3. 機能要件

### 3.1 タグ・収集（I1〜I3 に委譲、記録計はその利用側）

- タグ定義 CRUD（editor 以上）: 名前、PLC 接続、デバイス（D/W/R/X/Y 等）、
  データ型（ビット/16bit/32bit 符号有無/実数）、スケーリング
  （生値レンジ→工学値レンジの線形変換）、単位、小数桁
  - **2026-09-08 追補（issue #325、R0 確定後の共有スキーマ変更）**: タグ定義は
    I1（`banto-tags`）に委譲しているため、Modbus TCP 接続配下のタグに限り
    64bit 型（`i64`/`u64`/`f64`）が追加登録できるようになった（4 レジスタ占有、
    `i64`/`u64` は 2^53 超で精度低下）。R0 本文が挙げる型一覧はこの追加を
    反映していないが、実装スコープの変更ではなく I1 側の型拡張の反映のため
    本文は書き換えず、ここに追補する。詳細は
    [tag-server-design.md](tag-server-design.md) §6.3。
- 収集周期はタグ毎ではなく**収集グループ毎**（PLC 一括読み出しの単位）。
  標準 1s / 選択肢 100ms・200ms・500ms・2s・5s・10s・1min。
  **最短 100ms を性能目標とする**（2026-07-12 決定）。I2/I3 の実測で
  達成可否を検証し、未達構成（タグ数×PLC台数）では設定バリデーションで
  下限を引き上げる
- **2026-09-23 オーナー決定（#413）: 接続単位シミュレーションを開ける**。
  PLC 接続ごとに「実機の代わりにプロセス内シミュレータへ接続する」切替
  （banto-tags の `simulation` 列。banto-hub の接続単位シミュレーションと同じ
  収集層の仕組み）を、タグ設定画面から設定できるようにした。R1-B では
  banto-hub 固有機能として閉じていたが、「実機が無いときに設定できないのは
  使い物にならない」ため開けた。**シミュレーション接続の値は現在値・しきい値
  イベントには出るが、時系列ファイルには記録しない**（本書の「保存」の対象は
  実 PLC の値だけ - 収集層 `banto-collect` の約束で banto-hub と共有）。画面は
  そのことを常に表示し、切替は「収集を再起動」で反映する。詳細は
  [r1-plan.md](r1-plan.md) の R1-B の節。R0 の要件・スコープ自体は変えていない
  （開発・試運転の補助で、記録計としての保存対象は増えない）。
- **2026-09-23 オーナー決定（#414 段階2）: 開始時に不正な設定だけを外し、
  残りを動かす**。収集の開始時に、読めないタグ（アドレス・データ型・ビット
  指定）・使えない収集グループ（収集周期）・使えない PLC 接続（プロトコル・
  ポート・ユニット ID）だけを外し、正常なものは収集する（それまでは 1 件でも
  不正があると何も収集しなかった）。**不正なものがあることは必ず分かるように
  する**（収集の設定画面の「除外あり（N 件）」と一覧、タグ設定画面の一覧。
  **収集イベントには記録しない**）。外したタグの値は**保存しない（DB 上は
  null）**で、現在値は「値なし・品質 invalid」（通信エラーの Bad とは別）。
  詳細は [r1-plan.md](r1-plan.md) の R1-C の節。R0 の要件・スコープ自体は
  変えていない（正常なタグの保存は従来どおり）。
- **2026-10-10 オーナー決定（#383 段階3）: Hub 経由のタグは「Hub」という接続種別のタグとして
  `banto-collect` が収集・保存する**（決定のみ、未実装）。`plc_connections.protocol` に `hub` を足し、
  Hub から登録したタグは `tags` の行になる（ペン・しきい値・履歴・除外が SLMP / Modbus のタグと同じ
  タグ ID で動く）。Hub は 1 つで、接続先とキーは `hub.record` のまま。タグ定義（名前・データ型・単位）は
  登録時に Hub のカタログから複製し、同一性は外部名（scada-design.md §9.6）。収集開始時にカタログと
  突き合わせ、消えた・型が変わったタグは外す（#414 と同じ）。Hub が Live でない間は全タグ `bad` で
  `null` を記録し、イベントは `plc_connected` / `plc_disconnected` を Hub の接続キーで再利用する。
  Hub の `stale` は Stale、`bad`・不明は Bad、`value_source = simulation` の値は記録しない（#413）。
  記録時刻はこの PC の時計で、Hub の `t` は鮮度の判定にだけ使う。Hub 経由の書き込みはしない（§7）。
  ChronoGazer 内に別の recorder を持って読み出し時に合流する案は、履歴・保持・イベントが二重に
  なるため却下した。決定の詳細と手順（P2〜P6）は [plan.md](plan.md) §5。
- 品質フラグ付きで保存。PLC 断で Bad を記録し続け、**復旧後に自動再接続**
- タグ数上限（v1 目標）: **256 タグ**
- **2026-10-08 オーナー決定（#532・#533）: しきい値はタグ定義に含めない**。タグ定義
  （上の項目）は、データ点の性質（名前・アドレス・型・スケーリング・単位・小数桁）だけ
  を持つ。しきい値 H / HH / L / LL は**使う側（記録計・SCADA）が持つ設定**で、
  ChronoGazer では**記録計の側のタグごとの設定**（§3.2）に置く。
  - タグ定義の共有元（`banto-tags`）と Hub はしきい値を持たず、Hub は警報を判定しない
    （Hub はデータを集めて配る役。#533 で除去済み、2026-10-09）。
  - **警報の判定の正は PLC**。PLC 経由でつなぐ接続では、記録計のしきい値は表示と
    記録の補助になる。**Modbus で計器に直接つなぐ接続は、判定する PLC が無い**ので、
    記録計（または SCADA）のしきい値の判定が警報の役を担う。
  - SCADA は記録計の機能を含むので、同じ計器を記録計と SCADA の両方で判定する
    ことは無い。それぞれのアプリが自分のしきい値を持つ。
  - ドライバの種類（SLMP / Modbus / Hub 経由、#383）にかかわらず、同じ方法で点を指して
    しきい値を持てる。Hub 経由のタグも、記録計の側でしきい値を持てる。
  - しきい値のイベント（§3.5）には、**判定に使ったしきい値（その段の値）を残す**。
    警報の記録として、後から「どの値で判定したか」が分かるようにする。

### 3.2 表示グループ

グループは以下の表示種別を持つ。**レイアウトは固定パターン**
（画面エディタは作らない。§7）:

| 種別     | 内容                                                 | banto 資産      |
| -------- | ---------------------------------------------------- | --------------- |
| トレンド | 8 ペンの時系列（下記 3.3）                           | M13 LineChart   |
| デジタル | 現在値の数値大表示（グリッド配置、単位・品質色分け） | 新規（軽量）    |
| バー     | 縦バーメータ + 目盛 + しきい値色                     | 新規（軽量）    |
| 計器     | 円形ゲージ                                           | 既存 Gauge 拡張 |

- **2026-09-23 オーナー決定（#414 段階2）: 値が無いことを 0 と区別する**。
  4 種すべてで、値が無いこと（欠測・現在値の null・§3.1 で外したタグの品質
  invalid）を 0 と区別して表示する（「null と分かればよい」）。R1-D の要件
  （[r1-plan.md](r1-plan.md) の R1-D の節）。
- **2026-10-09 オーナー決定（#551、R1-D の実機の目視で）: bit のタグは既定で
  `True` / `False` と表示する**。デジタルは 0 / 1 の数値ではなく `True` / `False`
  （品質・しきい値の段の出し方は他のタグと同じ）。バー・計器は、bit のタグに工学値レンジが
  無くても 0〜1（`False`〜`True`）を既定のレンジとし、「レンジ未設定」にしない（目盛は
  `False` / `True` の 2 本）。トレンドは線を 0 / 1 の段差のままにし、グループの**全ペンが bit**
  のときは縦軸の目盛を `False` / `True` にする。bit とほかのタグが混ざるグループでは縦軸は
  全ペン共通の数値のまま（0 と 1 だけ True / False にすると、ほかのタグの 0 / 1 まで
  読み違えさせるため。この場合の bit の値は説明文で `0 = False、1 = True` と補う）。
  **ツールチップだけは縦軸と別の書式**（2026-10-10、tyaro/banto#376）: bit のペンは混在でも
  `False` / `True`、履歴の区間の中点は `False / True`（その区間に両方あった）で出す。
  文言（True / False）は既定の表記で、日本語（オン / オフ など）へ切り替える設定は
  必要になった時に足す（今は作らない）。表示グループ設定のプレビュー（§3.7.4）は同じ
  部品なので揃う。
- グループ数上限（v1 目標）: **16**。グループ切替はタブ or コマンドパレット
- しきい値（**記録計の側のタグごとの設定**。H/HH/L/LL、任意、**既定は設定なし**。

### 3.4 保存・保持

- SQLite + WAL、バッチ INSERT。**日単位のファイル分割**（plan.md §5）。
  実装は banto-tstore（I3a）: **日次ファイル + スキーマ凍結**方式
  （2026-07-12 決定。§8 参照）— ファイルは作成時にスキーマ確定・以後
  `ALTER` せず、タグ構成変更は新ファイルへの強制ローテーションで吸収する
- 保持期間既定 **90 日**（設定可）。期限超過ファイルの自動削除
  （**実装済み**、#538。`chronogazer_core::retention` が、起動時と日付が変わる
  たびに 1 回 `banto_tstore::prune_files` を呼ぶ。今日のファイルは日数に関わらず残し、書き手が今開いている日付のファイル（書き込みの失敗で
  日付の切り替えができていない間の古い日付）も残す（書き手のロックの下で消す）。設定を読めない
  ときも消さず、次の確認でやり直すす。
  無制限・想定外の値のときは削除せず飛ばす。保持日数は掃除のたびに設定から読み直す
  ので、変更は次の掃除（次の日付の変わり目か再起動）から効く。結果はログに出す。
  banto-hub も同じ考え方）
- **書き込みの失敗で行を失わない**（実装済み、#538）。flush が失敗しても溜めた行は
  バッファに残り、次の flush でもう一度書く。失敗が続いてバッファが上限（既定
  8,000,000 セル ≒ 128MB）を超えたら `ptime` の古い行から捨て、捨てた件数を数えて
  （`TsWriter::dropped_rows`）ログに出す。複数行 INSERT は 1 文のバインド数の上限
  （32,766）に収まるよう、行数を `32766 / (列数 + 1)` 以下に区切る。
  **日付の切り替えの flush が失敗している間**（#542、実装済み）も、新しい日付の行は
  捨てずに日付ごとに分けてバッファに溜め（書き込みの失敗は収集側へ返し続ける）、前の
  日付が書けた時点で日付ごとにそのファイルへ切り替えながら書く。上限は全日付を通した
  合計で、超えたら全日付を通して `ptime` の古い行から捨てて数える。保持期間の削除は、
  未書き込みの行がある日付のファイルをすべて残す。終了時の最後の flush も失敗したら、
  書けなかった行を同じ件数に足してログに出す
- **2026-09-24 オーナー決定（#424 案 A、実装済み）: 記録時刻とデータファイルの
  日付の契約**。データファイルはファイル名の日付（ローカル日付）で選ばれる
  （読み出しの候補選び、保持期間の削除のどちらも、ファイルを開かずに名前の
  日付だけで判断する）。そのため**行の記録時刻は、ファイルの日付から ±24h 以内**
  （正確には、その日付の UTC 0 時を `start` として
  `start - 24h <= 記録時刻 < start + 48h`）でなければならない。banto-tstore の
  書き込み（`TsWriter::append`）は、読み出し（banto-tsquery）の候補選びと
  **同じ述語・同じ余白の定数**
  （`ptime_is_findable_in` / `MAX_OFFSET_PAD_MS`）でこれを判定し、外れた行を
  エラーで拒否する（契約の外の行は、その時刻だけを含む狭い検索範囲だと
  ファイルが候補から外れて取りこぼされる。ファイルの日付も含む広い範囲なら
  読めるが、範囲の取り方で結果が変わる）。これで、受け付けた行は、その時刻を
  含むどの検索範囲でもファイルの選択から漏れない。収集の記録時刻はファイルの
  日付を決めるのと同じ時計から取るので、通常の収集（日付の変わり目、夏時間、時計の巻き戻し）は拒否されない。
  拒否されるのは、記録時刻を取ってから書き込むまでの間に時計が大きく
  （24h − |UTC オフセット| 以上）飛んだ瞬間の 1 サンプルだけで、これは
  **割り切って捨てる**（収集は既存の「書き込み失敗」として記録し、次の書き込み
  から戻る）。ファイルに記録時刻の最小・最大を持たせる案（案 B）は、PLC 側の
  時刻や過去データの取り込みが必要になったときに設計する
- banto M17 バックアップは設定 DB（タグ・グループ定義）に適用。
  時系列データファイルは分割単位でのコピー運用（バックアップ対象外）

#### 3.7.1 決まっていること（2026-10-08 オーナー決定、[plan.md](plan.md) §5）

- **目的は、ユーザーの負荷を極力減らすこと**。本節の要件はすべてこの目的に
  照らして読む。たとえば、承認は 1 回の操作で済ませる。AI が作った下書きは
  プレビューを用意した状態で渡す。手動で編集するときより手順を増やさない。
- トレンドのグループ表示構成と帳票テンプレートは、**再ビルドなしに変えられる
  シリアライズ可能な宣言データ**として DB に持つ。
- **PLC 接続・収集グループ・タグ定義（I1）も同じ扱いにする**（2026-10-08
  オーナー決定。plan.md §5 の同日の決定を広げたもの）。しきい値（H/HH/L/LL）
  はタグ定義に含めず、**記録計の側のタグごとの設定**として同じ宣言データの範囲に
  入れる（同日のオーナー決定、§3.1。AI の対象には入る）。
- AI アシスタントが対話で作れる範囲は、**この宣言データの範囲と一致させる**
  （banto ADR-0009 の宣言境界と同じ線）。
- 生成した定義は必ず **検証 → プレビュー → 承認 → 保存（監査付き）** を通す。
- **承認した AI の変更は、人が同じ変更を手動で適用したときと同じ動作をする**。
  AI 経由だからといって、反映のしかたを変えない（3.7.3 の「適用の動作」）。
- **汎用画面エディタは入れない**（§7）。固定グループパターンの語彙を広げて賄う。

  [banto-hub-mcp-reference.md](banto-hub-mcp-reference.md) §6）。本節は
  ユーザーの role（viewer / editor / admin、§3.6）に縛られたトークンと、
  承認の段を求める。流用できるのは「既存 REST の検証・保存・監査の経路を
  共有して抜け道を作らない」作法と、「保存せずに検証だけする口」
  （`check_expression`）・保存前の疎通確認（`test_connection`）の形。
  - hub の構成 MCP も接続・グループ・タグを編集できるが、それは **hub 自身の
    DB** である。ChronoGazer の接続・収集グループ・タグは ChronoGazer の DB
    （同じ `banto-tags` のスキーマを持つ別のファイル）にあり、hub の MCP からは
    触れない。本節が指すのは後者だけ。
- 監査は banto M14 の `audit_log` に、変更操作を記録している（読み取りは
  記録しない。閲覧は admin。`apps/chronogazer/core/src/rest.rs` の doc）。

#### 3.7.3 宣言データの範囲

宣言データは「値の集まり」で、実行できるものを含まない。要件の水準で次の
項目を持つ（DB スキーマは後続の設計で決める）。

**(0') PLC 接続・収集グループ**（§3.1）

- PLC 接続: 名前、プロトコル（`modbus-tcp` / `slmp`）、ホスト、ポート、
  プロトコルごとの設定（ユニット ID（Modbus）、ワード順）、有効 / 無効、
  接続単位シミュレーション（§3.1、#413）。
- 収集グループ: 名前、PLC 接続への参照、収集周期（§3.1 の選択肢から 1 つ）、
  有効 / 無効。
- 今の ChronoGazer の CRUD が落としている banto-hub 固有の項目（`virtual` /
  `postgres` 接続、DB 連携の問い合わせ、書き込みの既定値）は持たない。
- データの置き場所は今と同じ `banto-tags`。**関所と検証は既存の CRUD の経路を
  そのまま使う**（3.7.4）。

**(0) タグ定義**（§2・§3.1）

- 項目は §3.1 のタグ定義 CRUD と同じ: 名前、所属する収集グループへの参照
  （PLC 接続はタグが直接持たず、収集グループが参照する）、デバイス / アドレス、データ型、スケーリング（生値レンジ →
  工学値レンジ）、単位、小数桁、有効 / 無効。
- **しきい値 H / HH / L / LL は、タグ定義に含めない**（2026-10-08 オーナー決定、§3.1）。
  記録計の側のタグごとの設定（任意、既定は設定なし）として、(0) と並ぶ宣言データに
  する（下の (0b)）。
- 書き込み可・演算タグ・文字列タグなど、今の `TagPayload` が落としている
  項目は持たない（書き込みは §7、演算タグは banto-hub 固有）。
- データの置き場所は今と同じ `banto-tags` の `tags` テーブル。**関所と検証は
  既存のタグ CRUD の経路をそのまま使う**（3.7.4）。別の保存経路を作らない。

**(0b) しきい値の設定（記録計の側のタグごとの設定）**（§3.1・§3.2）

- 項目: 対象のタグ（ドライバの種類にかかわらず同じ方法で点を指す。Hub 経由のタグも
  含む）、しきい値 H / HH / L / LL（すべて任意）。**既定は設定なし**。
- 置き場所は ChronoGazer 自身の DB（`banto-tags` のタグ表の外）。検証（大小関係など）・
  関所・監査は (0) と同じ経路を通す。保存の意味は今のタグ編集と同じで、収集への反映は
  「収集を再起動」で行う。
- 収集のしきい値の判定は、この設定から作る。判定に使った値はイベントに残す（§3.5）。

**(1) 表示グループ定義**（§2・§3.2）

- 名前、並び順。
- 表示種別: トレンド / デジタル / バー / 計器 の **4 種から 1 つ**（§3.2 の
  固定パターン。種別はデータで増やせない）。
- ペン: **最大 8**。各ペンはタグへの参照（ID）と表示属性を持つ。色は banto
  チャート系列色を既定とする。
- 種別ごとの表示属性: 種別ごとに**閉じた項目の集合**を持つ（例: トレンドの
  既定時間窓、表示レンジ）。項目を足すことは「語彙を広げる」ことで、要件の
  改訂として行う。
- しきい値は**記録計の側のタグごとの設定（0b）を参照する**。グループ定義に複製しない
  （§3.2 の「タグ毎」）。
- 上限: グループ 16、1 グループ 8 ペン（§3.2）。超えるものは検証で拒否する。

**(2) 帳票テンプレート**（§3.5）

- 名前、帳票の種類（v1 は日報だけ）。
- テンプレート本文: `@banto/report` の Markdown サブセットの文字列。
- 画像は外部 URL を参照させない。必要ならアプリ内の添付画像だけを許す（3.7.9 の 6）。
- データの束ね方: 対象のタグと代表値（平均 / 最大 / 最小）、期間（日報は
  1 日）。テンプレートが参照できるのは、アプリがこの指定から組み立てた
  **決まった形のデータだけ**。テンプレートから任意の問い合わせはできない。

**適用の動作**（3.7.1 の決定）

- 承認された変更は、**人が同じ変更を手動で保存したときと同じ動作**をする。
  今の動作（3.7.2）に当てはめると:
  - 接続・収集グループ・タグ・しきい値の設定の変更は、承認で保存されるが、稼働中の収集には
    自動で反映されない。反映は「収集を再起動」で行う（手動の保存と同じ）。
  - 表示グループ・帳票テンプレートは、保存された時点から表示・印刷に使われる
    （手動の保存と同じ）。
- 手動の動作が将来変わったら、AI 経由の動作も同じように変わる。AI 経由のため
  だけの反映の経路は作らない。
- 目的（3.7.1）に照らし、承認の画面では「反映には収集の再起動が要る」ことを
  示し、再起動への導線を置く。今の手動保存の案内（3.7.2）が足りない点は、
  手動の側も同じように直す（手動と AI で案内を分けない）。
- 削除や改名は、参照している定義（配下の収集グループ・タグ、表示グループの
  ペン、帳票のデータ指定）に影響する。検証とプレビューで、影響を受ける
  定義を示す。

**範囲外**（宣言データにも AI にも入れない）

- 汎用画面エディタ（自由配置・座標・任意のウィジェット）。
- 任意のコード・スクリプト・式（JS、SQL、演算式、生 HTML）。
- ユーザー・権限・アプリ設定。
- 収集の開始 / 停止・再起動を **AI の操作として**行うこと（人が画面で行う）。
- PLC への書き込み、書き込み可のタグ（§7）。

#### 3.7.4 関所（検証 → プレビュー → 承認 → 保存）

- **経路を問わず同じ関所を通す**。画面からの手動編集、REST、Tauri、MCP の
  どれも、同じ検証関数と同じ保存・監査の経路を使う。抜け道を作らない。
  接続・収集グループ・タグは、既存の CRUD の検証・保存・監査の経路を使う。
- **検証**: サーバー側の 1 つの関数で行う。形（種別ごとの許容項目）、上限、
  参照する接続・収集グループ・タグの存在、接続と収集グループの項目
  （プロトコル・ポート・収集周期など）、タグの項目（アドレス・データ型・
  スケーリング・しきい値の大小関係など）、しきい値の設定（大小関係・対象タグの存在）、帳票テンプレートの構文を確かめる。
  **保存せずに検証だけする口**を持つ。
- **プレビュー**: 保存せずに見せる。AI が作った下書きは、プレビューを用意した
  状態で人に渡す（3.7.1 の目的）。
  - 表示グループと帳票: 実際の表示部品（監視画面の 4 種、帳票は
    `ReportView`）で、現在値やサンプルのデータを描く。
  - 接続・収集グループ・タグ: 変更前後の差分と、影響を受ける定義、反映に
    収集の再起動が要ることを示す。PLC へ試しにつないで 1 回読む（読み取り
    だけ、収集とは別の接続・キュー、時間の上限付き。3.7.9 の 7）。読み先は
    タグ → 収集グループ → PLC 接続の順にたどり、同じ下書きの中で接続や
    収集グループも変えているときは下書きの値を使う。読めなかったときは
    理由（接続できない・アドレスが無いなど）をプレビューに出し、承認するか
    どうかは人が決める（読めないことだけを理由に承認を止めない）。
- **承認**: 下書きは承認されるまで有効にならない。承認は **1 回の操作**で
  済ませる（3.7.1 の目的）。**AI が作った定義の承認は人が行う**（AI の
  トークンでは承認できない）。承認は editor 以上で、自己承認・まとめての承認が
  できる（3.7.9 の 3）。下書きは元の版を持ち、承認時に再検証する（3.7.9 の 8）。
  承認した定義は直近 10 版まで残り、前の版へ戻せる（3.7.9 の 4）。
- **保存と監査**: 承認と同時に有効な定義になり、banto M14 の監査ログに残す。
  記録するのは、誰が（作成者・承認者、経路 = rest / tauri / mcp、AI 経由か
  どうか）、何を（PLC 接続 / 収集グループ / タグ定義 / しきい値の設定 / 表示グループ /
  帳票テンプレート、対象の ID と名前、作成 / 更新 / 削除）、結果（承認 / 却下 /
  検証エラー）。読み取りとプレビューは記録しない（既存の流儀）。
- 検証で落ちたものは保存しない。一部だけ保存することはしない。

#### 3.7.5 AI の境界

- AI は **REST / MCP の公開面だけ**を通る。DB への直接アクセスと、サービス層
  への直結はしない（ADR-0009 の決定 2: 直結は認可・監査の関所を迂回できる）。
- AI のトークンは**ユーザーの role に縛る**。そのユーザーが画面でできないことは
  AI にもできない。hub の `admin` API キーのような全権のキーにはしない。
- AI に見せる操作は 3.7.3 の範囲（PLC 接続・収集グループ・タグ定義・しきい値の
  設定・表示グループ・帳票テンプレート）だけ。範囲外の操作（収集の開始 / 停止・再起動、
  ユーザー・設定、PLC への書き込み）は MCP のツール一覧に出さない。
- AI が作った定義は、手動の編集と**同じ検証**を通り、3.7.4 の関所を通る。
  AI ができるのは下書きの作成・検証・プレビューの依頼までで、承認はしない。
- AI 経由の操作は監査で見分けられるようにする。
- AI の実行形態とトークンは 3.7.9 の 1・2（外部 MCP クライアント向けの MCP 口、
  「AI を使う」で自動発行するユーザーのキー、既定はループバックだけ）。

#### 3.7.6 手動編集（AI を使わない編集）

- **必須**とする。AI は手動編集の代行であって、唯一の入口にしない。
  - PLC 接続・収集グループ・タグ定義: R0 の画面一覧（§6 の 3「タグ設定」）に
    あり、実装済み。しきい値は**記録計の側の設定**として、タグ設定画面（`/tags`）の
    タグの編集ペインの下で別に保存する（#532 で実装。3.7.3 の (0b)）。
  - 表示グループ: R0 の画面一覧（§6 の 4「グループ設定」）にもともとある。
    #393 がこれ。グループ設定画面でしきい値を見せる・直す場合も、保存は
    しきい値の設定（3.7.3 の (0b)）の経路で行う。
  - 帳票テンプレート: §7 の「M19 の MD テンプレート手書きで賄う」の手書きに
    当たる。テキストで編集してプレビューする画面を持つ（デザイナではない）。
- 手動編集も 3.7.4 の検証・プレビュー・保存（監査）を通る。手動編集は保存が
  承認を兼ねる（3.7.9 の 3）。目的（3.7.1）に照らし、手動編集の手順を今より
  増やさない。

#### 3.7.7 スコープの護り（§7）との関係

- **§7 は緩めない**。宣言データは §3.2 の 4 種固定パターンの中のパラメータで
  あり、汎用画面エディタではない。
- 語彙（表示種別、種別ごとの属性）を広げるのは**要件の改訂（オーナー決定）**で
  行う。データや AI では語彙を増やせない。
- 帳票: §7 の「帳票のカスタムデザイナは作らない」はそのまま。テンプレート
  文字列をテキストで書く（人でも AI でも）のは §7 の「MD テンプレート手書き」で
  あり、両立する。WYSIWYG やドラッグ配置は作らない。
- 接続・収集グループ・タグを AI で作れても、収集は**読み取りだけ**のまま。
  書き込み可のタグは作れず、PLC への書き込みが無いことも変わらない。

#### 3.7.9 運用の決定（旧未決。いずれも 2026-10-08 オーナー決定）

草案の未決 9 項目は、すべて推奨案どおりに決まった。**未決は残っていない**。

1. **AI の実行形態**: まず外部の MCP クライアント向けに MCP 口を作る。Claude
   Desktop / Claude Code への登録は、画面から 1 回の操作で行えるようにする。
   1 回の操作で登録できるのは、ChronoGazer と同じ PC の MCP クライアント。
   LAN の別の PC から使うときは、2 で LAN へ出すことを有効にしたうえで、
   画面に出る設定（接続先とキー）をその PC のクライアントに写す。この
   キーはクライアントごとに発行し、個別に失効できる。
   claude CLI のサイドカー起動は、必要になったら後で足す。
2. **トークン**: 画面で「AI を使う」を有効にすると、ユーザーに紐づく API キー
   （role を引き継ぐ。失効でき、期限付き）を自動で発行して登録する。同じ PC の
   クライアントなら、ユーザーがキーを扱うことは無い（LAN の別の PC は 1 のとおり）。MCP 口は既定でループバックだけで待ち受け、LAN へは
   設定で明示的に有効にしたときだけ出す。
3. **承認**: editor 以上。自己承認してよい。用意済みのプレビューから 1 回の
   操作で承認する。複数の下書きをまとめて承認できる。AI のトークンでは承認
   できない。手動編集は保存が承認を兼ねる。
4. **版の管理**: 定義ごとに直近 10 版を自動で残す。前の版へ 1 回の操作で
   戻せる（関所と監査を通す。editor 以上）。
5. **書き出しと取り込み**: 後回し。v1 は設置ごとに持ち、M17 バックアップの

6. **帳票テンプレートの画像**: 外部 URL は参照させない。必要ならアプリ内の
   添付画像だけを許す。
7. **プレビューでの PLC の試し読み**: 行う。読み取りだけで、収集の接続・
   キューとは分け、時間の上限を付ける。
8. **下書き**: 元の版を持たせ、承認時に再検証する。元が変わっていたら承認を
   拒否する（楽観ロック）。参照されているものの削除は、参照元の一覧を示して
   拒否する。改名は通す（参照は ID で持つ）。
9. **段階 1（#393）**: 関所（段階 3）を待たずに進めてよい。
10. **再起動の案内**: 承認画面と、手動で保存した後の両方で「反映には収集の
    再起動が要る」ことを示し、再起動への導線を置く（3.7.3 の「適用の動作」）。
