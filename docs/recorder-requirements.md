## 1. 製品コンセプト

**ペーパーレスレコーダ（デジタル記録計）のソフトウェア版**。
既設 PLC（三菱 MELSEC、MC/SLMP）からタグ値を周期収集して時系列保存し、
リアルタイム/ヒストリカル/ハイブリッドトレンドと計器表示を提供する。

- 実機レコーダ（数十万円・チャネル数固定・専用ハード）に対し、
  **既設PLC + 現場PC（またはミニPC1台）でチャネル数自由**を武器にする
- banto テンプレート由来: デスクトップ（Tauri）+ LAN ブラウザ配信の二形態。
  現場の壁掛けモニタ（キオスク、認証無効モード）と事務所ブラウザ閲覧
  （viewer ロール）を同一プロセスで賄う
- **記録計であって SCADA ではない**: 読み取り専用・表示は固定パターン。
  スコープの護りは §7

### 対象環境

| 項目              | v1                                                                                                                                                                                                                     |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OS                | Windows 10/11（デスクトップ + LAN サーバ）                                                                                                                                                                             |
| PLC               | **Modbus TCP を先行対応**（2026-07-12 決定: シミュレータ/ツールが豊富でデバッグ容易なため開発初期はこちら）→ 三菱 MELSEC（MC/SLMP）を v1 リリースまでに追加（本命ターゲット）。プロトコルは trait で差し替え可能に設計 |
| 同時接続 PLC 台数 | 4 台まで                                                                                                                                                                                                               |
| クライアント      | デスクトップ 1 + LAN ブラウザ数台（banto 準拠）                                                                                                                                                                        |

## 2. 用語

| 用語     | 定義                                                                  |
| -------- | --------------------------------------------------------------------- |
| タグ     | 収集点。名前 + PLC アドレス + データ型 + スケーリング + 単位 + 小数桁 |
| グループ | 表示の単位。最大 **8 ペン**（タグ参照）を束ね、表示種別を持つ         |
| ペン     | グループ内のタグ参照 + 表示属性（色は banto チャート系列色を既定）    |
| 品質     | サンプル毎の Good / Bad（通信エラー）/ Stale（更新停止）              |

## 3. 機能要件

### 3.1 タグ・収集（I1〜I3 に委譲、記録計はその利用側）

- タグ定義 CRUD（editor 以上）: 名前、PLC 接続、デバイス（D/W/R/X/Y 等）、
  データ型（ビット/16bit/32bit 符号有無/実数）、スケーリング
  （生値レンジ→工学値レンジの線形変換）、単位、小数桁
  - **2026-09-08 追補（issue #325、R0 確定後の共有スキーマ変更）**: タグ定義は
    I1（`banto-tags`）に委譲しているため、Modbus TCP 接続配下のタグに限り
    64bit 型（`i64`/`u64`/`f64`）が追加登録できるようになった（4 レジスタ占有、
    `i64`/`u64` は 2^53 超で精度低下）。R0 本文が挙げる型一覧はこの追加を
    反映していないが、実装スコープの変更ではなく I1 側の型拡張の反映のため
    本文は書き換えず、ここに追補する。詳細は
    [tag-server-design.md](tag-server-design.md) §6.3。
- 収集周期はタグ毎ではなく**収集グループ毎**（PLC 一括読み出しの単位）。
  標準 1s / 選択肢 100ms・200ms・500ms・2s・5s・10s・1min。
  **最短 100ms を性能目標とする**（2026-07-12 決定）。I2/I3 の実測で
  達成可否を検証し、未達構成（タグ数×PLC台数）では設定バリデーションで
  下限を引き上げる
- **2026-09-23 オーナー決定（#413）: 接続単位シミュレーションを開ける**。
  PLC 接続ごとに「実機の代わりにプロセス内シミュレータへ接続する」切替
  （banto-tags の `simulation` 列。banto-hub の接続単位シミュレーションと同じ
  収集層の仕組み）を、タグ設定画面から設定できるようにした。R1-B では
  banto-hub 固有機能として閉じていたが、「実機が無いときに設定できないのは
  使い物にならない」ため開けた。**シミュレーション接続の値は現在値・しきい値
  イベントには出るが、時系列ファイルには記録しない**（本書の「保存」の対象は
  実 PLC の値だけ - 収集層 `banto-collect` の約束で banto-hub と共有）。画面は
  そのことを常に表示し、切替は「収集を再起動」で反映する。詳細は
  [r1-plan.md](r1-plan.md) の R1-B の節。R0 の要件・スコープ自体は変えていない
  （開発・試運転の補助で、記録計としての保存対象は増えない）。
- **2026-09-23 オーナー決定（#414 段階2）: 開始時に不正な設定だけを外し、
  残りを動かす**。収集の開始時に、読めないタグ（アドレス・データ型・ビット
  指定）・使えない収集グループ（収集周期）・使えない PLC 接続（プロトコル・
  ポート・ユニット ID）だけを外し、正常なものは収集する（それまでは 1 件でも
  不正があると何も収集しなかった）。**不正なものがあることは必ず分かるように
  する**（収集の設定画面の「除外あり（N 件）」と一覧、タグ設定画面の一覧。
  **収集イベントには記録しない**）。外したタグの値は**保存しない（DB 上は
  null）**で、現在値は「値なし・品質 invalid」（通信エラーの Bad とは別）。
  詳細は [r1-plan.md](r1-plan.md) の R1-C の節。R0 の要件・スコープ自体は
  変えていない（正常なタグの保存は従来どおり）。
- 品質フラグ付きで保存。PLC 断で Bad を記録し続け、**復旧後に自動再接続**
- タグ数上限（v1 目標）: **256 タグ**

### 3.2 表示グループ

グループは以下の表示種別を持つ。**レイアウトは固定パターン**
（画面エディタは作らない。§7）:

| 種別     | 内容                                                 | banto 資産      |
| -------- | ---------------------------------------------------- | --------------- |
| トレンド | 8 ペンの時系列（下記 3.3）                           | M13 LineChart   |
| デジタル | 現在値の数値大表示（グリッド配置、単位・品質色分け） | 新規（軽量）    |
| バー     | 縦バーメータ + 目盛 + しきい値色                     | 新規（軽量）    |
| 計器     | 円形ゲージ                                           | 既存 Gauge 拡張 |

- **2026-09-23 オーナー決定（#414 段階2）: 値が無いことを 0 と区別する**。
  4 種すべてで、値が無いこと（欠測・現在値の null・§3.1 で外したタグの品質
  invalid）を 0 と区別して表示する（「null と分かればよい」）。R1-D の要件
  （[r1-plan.md](r1-plan.md) の R1-D の節）。
- グループ数上限（v1 目標）: **16**。グループ切替はタブ or コマンドパレット
- しきい値（タグ毎に H/HH/L/LL、任意）: バー/計器の色変化、
  トレンドの帯（M13 bands）、イベント一覧（3.5）に使用

### 3.3 トレンド 3 モード

- **リアルタイム**: 直近時間窓（既定 10 分、選択可）を追従描画。
  M13 ストリーミング。更新は収集周期に同期
- **ヒストリカル**: 期間指定 + ズーム/パン（M13 viewport）。
  データは I4 のサーバ側間引き経由（可視幅ピクセル以下に削減して返す）
- **ハイブリッド**: リアルタイム追従中に左へパンすると過去へシームレスに
  連続し、右端へ戻すと追従再開。メモリ上のローリング窓（直近）と
  DB（過去、間引き済み）を viewport 位置で合成（plan.md §5）

### 3.4 保存・保持

- SQLite + WAL、バッチ INSERT。**日単位のファイル分割**（plan.md §5）。
  実装は banto-tstore（I3a）: **日次ファイル + スキーマ凍結**方式
  （2026-07-12 決定。§8 参照）— ファイルは作成時にスキーマ確定・以後
  `ALTER` せず、タグ構成変更は新ファイルへの強制ローテーションで吸収する
- 保持期間既定 **90 日**（設定可）。期限超過ファイルの自動削除
- **2026-09-24 オーナー決定（#424 案 A、実装済み）: 記録時刻とデータファイルの
  日付の契約**。データファイルはファイル名の日付（ローカル日付）で選ばれる
  （読み出しの候補選び、保持期間の削除のどちらも、ファイルを開かずに名前の
  日付だけで判断する）。そのため**行の記録時刻は、ファイルの日付から ±24h 以内**
  （正確には、その日付の UTC 0 時を `start` として
  `start - 24h <= 記録時刻 < start + 48h`）でなければならない。banto-tstore の
  書き込み（`TsWriter::append`）は、読み出し（banto-tsquery）の候補選びと
  **同じ述語・同じ余白の定数**
  （`ptime_is_findable_in` / `MAX_OFFSET_PAD_MS`）でこれを判定し、外れた行を
  エラーで拒否する（契約の外の行は、その時刻だけを含む狭い検索範囲だと
  ファイルが候補から外れて取りこぼされる。ファイルの日付も含む広い範囲なら
  読めるが、範囲の取り方で結果が変わる）。これで、受け付けた行は、その時刻を
  含むどの検索範囲でもファイルの選択から漏れない。収集の記録時刻はファイルの
  日付を決めるのと同じ時計から取るので、通常の収集（日付の変わり目、夏時間、時計の巻き戻し）は拒否されない。
  拒否されるのは、記録時刻を取ってから書き込むまでの間に時計が大きく
  （24h − |UTC オフセット| 以上）飛んだ瞬間の 1 サンプルだけで、これは
  **割り切って捨てる**（収集は既存の「書き込み失敗」として記録し、次の書き込み
  から戻る）。ファイルに記録時刻の最小・最大を持たせる案（案 B）は、PLC 側の
  時刻や過去データの取り込みが必要になったときに設計する
- banto M17 バックアップは設定 DB（タグ・グループ定義）に適用。
  時系列データファイルは分割単位でのコピー運用（バックアップ対象外）

### 3.5 イベント・出力

- イベント一覧: しきい値の超過/復帰、PLC 断/復旧、収集開始/停止を
  時刻付きで記録・一覧表示（**ACK・状態遷移管理はしない**、§7）
- 期間指定 CSV 出力: タグ選択 + 期間 → M15 CSV 基盤で出力
  （過去アプリ「時系列CSV出力」の回収）
- 日報帳票: 1 日分の代表値（平均/最大/最小）を banto M19 report の
  MD テンプレートで印刷（R3。M19 完了が前提）

### 3.6 設定・権限（banto 準拠）

- ロール: admin（システム設定・ユーザー）/ editor（タグ・グループ・
  しきい値編集）/ viewer（閲覧のみ）。壁掛け端末は認証無効モード（表示専用）
- 収集の開始/停止は editor 以上。操作は banto M14 監査ログに記録
  - **2026-09-18 オーナー決定（#383 段階2a の実装確認）**: 収集の開始/停止
    は本文どおり **editor 以上**とする。banto-hub は同種の制御（自動書き込み
    エンジンの arm/disarm 等）を admin 限定にしているが、chronogazer は
    別プロダクトであり R0 本文のこの決定を継承する - banto-hub の先例に
    引きずられて admin 限定へ変更しない。R1-C（収集ランタイム実装）が
    この決定に従うことの確認として記録する。
  - **2026-09-20 オーナー決定（#407 = R1-C の C-2 レビュー）**: **収集の
    「状態の読み取り」は viewer 以上**とする（開始/停止の editor 以上とは
    床を分ける）。本文の viewer は「**閲覧のみ**」であって「何も見えない」
    ではなく、収集が動いているかどうかは監視画面（R1-D）の基本情報である。
    状態に機微な情報（接続先・キー・ファイルパス・起動失敗の理由）は
    含めない設計なので、viewer に見せて困るものが無い。Hub 接続の状態
    （`hub_status`）が admin 限定なのは接続先とキーを扱うためで、**収集の
    稼働状態はそれとは性質が違う** - 上と同じく先例に引きずられない。
    監査の `resource` は床を分けても `"collect"` の 1 つに揃える。

### 3.7 タグ定義・表示構成・帳票テンプレートの宣言データ化と AI 対話による作成

状態: **要件の草案 / 未実装**（#524、2026-10-08）。決まっているのは 3.7.1 の
オーナー決定だけ。それ以外の設計判断は 3.7.9 の未決リストに置く。実装は
要件が固まってから別 PR にする。

#### 3.7.1 決まっていること（2026-10-08 オーナー決定、[plan.md](plan.md) §5）

- トレンドのグループ表示構成と帳票テンプレートは、**再ビルドなしに変えられる
  シリアライズ可能な宣言データ**として DB に持つ。
- **タグ定義（I1）も同じ扱いにする**（2026-10-08 オーナー決定。plan.md §5 の
  同日の決定を広げたもの）。しきい値（H/HH/L/LL）はタグの属性なので、
  タグ定義に含まれる。
- AI アシスタントが対話で作れる範囲は、**この宣言データの範囲と一致させる**
  （banto ADR-0009 の宣言境界と同じ線）。
- 生成した定義は必ず **検証 → プレビュー → 承認 → 保存（監査付き）** を通す。
- **汎用画面エディタは入れない**（§7）。固定グループパターンの語彙を広げて賄う。

出典は banto の旧 industrial-plan §5（2026-08-26 議論、banto
`docs/history/industrial-plan.md`）。旧文もタグ定義・グループ表示構成・帳票
テンプレートの 3 つを挙げていた。PLC 接続・収集グループは決定に含まれて
いないので、本節では範囲外とする（含めるかは 3.7.9）。

#### 3.7.2 現状（2026-10-08、コードとの照合）

- **タグ定義の CRUD は実装済み**。データは `banto-tags` の `tags` テーブルに
  あり、REST（`/api/tags`、読み取りは viewer 以上、変更は editor 以上）と
  Tauri の両経路で、監査付きで変更できる（`apps/chronogazer/core/src/rest.rs`
  の `tag_registry_router`。検証は `banto-tags` の `validate_tag_input` ほか、
  `crates/banto-tags/src/tag.rs`）。画面は `/tags`。
- **しきい値は列としてはタグにあるが、ChronoGazer からは設定できない**。
  `tags` テーブルの `threshold_h` / `threshold_hh` / `threshold_l` /
  `threshold_ll`（`crates/banto-tags/migrations/0003_tags.sql`）を、収集の
  しきい値イベントが使っている。一方、ChronoGazer の `TagPayload`
  （`rest.rs`）はしきい値を受け取らず、`banto-tags` へ渡すときに常に `None` に
  している。画面にも編集欄が無い。`TagPayload` の doc は、しきい値の編集を
  グループ設定画面の役目と読んでいた（#393 の本文も同じ）。本節は 3.7.1 の
  決定に従い、しきい値をタグ定義の一部として扱う。
  - あわせて、今の形のままでは**タグを更新するとしきい値が消える**（更新でも
    `None` を渡すため）。今は ChronoGazer の中にしきい値を入れる手段が無いので
    実害は出ていないが、しきい値を設定できるようにするときに直す必要がある。
  - 同じ `TagPayload` は `expected_revision` も渡していない（楽観ロックが
    効いていない）。
- **タグの変更は、稼働中の収集には自動では反映されない**。反映は明示的な
  「収集を再起動」操作だけで行う（`apps/chronogazer/core/src/collect.rs` の
  doc、[r1-plan.md](r1-plan.md) の R1-C）。設定を 1 行直すたびに収集が
  途切れないようにするための約束。タグ構成が変わると、データファイルは
  新しいファイルへローテーションする（§3.4）。
- **表示グループは未実装**。テーブルが無い（app の
  `apps/chronogazer/core/migrations-sqlite/` は settings・users・user_roles・
  audit_log だけ。`banto-tags` は PLC 接続・収集グループ・タグだけ）。監視画面
  （`/monitor`）は「表示グループが未設定です」を出すプレースホルダ。CRUD と
  画面は #393（R1-B の残り）、表示は R1-D（[r1-plan.md](r1-plan.md)）で、
  どちらも未着手。
- **表示グループは収集グループと別物**（§2）。収集グループは PLC 一括読み出しの
  単位で、`banto-tags` にある。
- **帳票は未実装**（R3）。ChronoGazer は `@banto/report` にまだ依存していない。
  `@banto/report` は**テンプレートを文字列で受ける**
  （`renderReport(template, data)`、`<ReportView {template} {data}>`）ので、
  DB から読んだ文字列をそのまま描ける。構文は Markdown のサブセット +
  `{{ }}` の値挿入・`#each`・`#if`・フォーマッタで、生 HTML はエスケープされ、
  式は書けない（banto `docs/design/report-plan.md` §3.1・§3.2）。
- **MCP・API キーは ChronoGazer に無い**。banto 本体にも MCP の仕組みは無い。
- **banto-hub の構成補助 MCP（T21）は前例だが、そのまま流用しない**。hub は
  `admin` スコープの `bh_` API キー 1 本が構成全権を持ち、変更はその場で
  commit される（不可逆操作に `confirm` を求めるだけで、承認の段は無い。
  [banto-hub-t21-design.md](banto-hub-t21-design.md) §2・§3、
  [banto-hub-mcp-reference.md](banto-hub-mcp-reference.md) §6）。本節は
  ユーザーの role（viewer / editor / admin、§3.6）に縛られたトークンと、
  承認の段を求める。流用できるのは「既存 REST の検証・保存・監査の経路を
  共有して抜け道を作らない」作法と、「保存せずに検証だけする口」
  （`check_expression`）の形。
  - hub の構成 MCP もタグを編集できるが、それは **hub 自身の DB のタグ**で
    ある。ChronoGazer のタグは ChronoGazer の DB（同じ `banto-tags` の
    スキーマを持つ別のファイル）にあり、hub の MCP からは触れない。本節の
    タグ定義は後者だけを指す。
- 監査は banto M14 の `audit_log` に、変更操作を記録している（読み取りは
  記録しない。閲覧は admin。`apps/chronogazer/core/src/rest.rs` の doc）。

#### 3.7.3 宣言データの範囲

宣言データは「値の集まり」で、実行できるものを含まない。要件の水準で次の
項目を持つ（DB スキーマは後続の設計で決める）。

**(0) タグ定義**（§2・§3.1）

- 項目は §3.1 のタグ定義 CRUD と同じ: 名前、所属する収集グループ（= PLC
  接続）への参照、デバイス / アドレス、データ型、スケーリング（生値レンジ →
  工学値レンジ）、単位、小数桁、有効 / 無効。
- **しきい値 H / HH / L / LL**（任意）。タグの属性として、ここで編集する。
- 参照できるのは**既にある**収集グループ・PLC 接続だけ。タグ定義の中で接続や
  収集グループを作ったり変えたりはしない。
- 書き込み可・演算タグ・文字列タグなど、今の `TagPayload` が落としている
  項目は持たない（書き込みは §7、演算タグは banto-hub 固有）。
- データの置き場所は今と同じ `banto-tags` の `tags` テーブル。**関所と検証は
  既存のタグ CRUD の経路をそのまま使う**（3.7.4）。別の保存経路を作らない。
- **収集への影響**: 承認されたタグの変更は、収集としきい値イベントに効く。
  今の約束（3.7.2）どおり、**承認しても稼働中の収集には自動で反映せず、
  「収集を再起動」で反映する**ことを前提とする。承認の画面で「反映には
  収集の再起動が要る」ことを示す。承認と同時に再起動するかどうかは 3.7.9。
- タグを削除・改名したときは、それを参照する表示グループのペンと帳票の
  データ指定に影響する。検証とプレビューで、影響を受ける定義を示す。

**(1) 表示グループ定義**（§2・§3.2）

- 名前、並び順。
- 表示種別: トレンド / デジタル / バー / 計器 の **4 種から 1 つ**（§3.2 の
  固定パターン。種別はデータで増やせない）。
- ペン: **最大 8**。各ペンはタグへの参照（ID）と表示属性を持つ。色は banto
  チャート系列色を既定とする。
- 種別ごとの表示属性: 種別ごとに**閉じた項目の集合**を持つ（例: トレンドの
  既定時間窓、表示レンジ）。項目を足すことは「語彙を広げる」ことで、要件の
  改訂として行う。
- しきい値は**タグ定義（0）を参照する**。グループ定義に複製しない（§3.2 の
  「タグ毎」）。
- 上限: グループ 16、1 グループ 8 ペン（§3.2）。超えるものは検証で拒否する。

**(2) 帳票テンプレート**（§3.5）

- 名前、帳票の種類（v1 は日報だけ）。
- テンプレート本文: `@banto/report` の Markdown サブセットの文字列。
- データの束ね方: 対象のタグと代表値（平均 / 最大 / 最小）、期間（日報は
  1 日）。テンプレートが参照できるのは、アプリがこの指定から組み立てた
  **決まった形のデータだけ**。テンプレートから任意の問い合わせはできない。

**範囲外**（宣言データにも AI にも入れない）

- 汎用画面エディタ（自由配置・座標・任意のウィジェット）。
- 任意のコード・スクリプト・式（JS、SQL、演算式、生 HTML）。
- PLC 接続・収集グループの編集（含めるかは 3.7.9）。
- ユーザー・権限・アプリ設定、収集の開始 / 停止・再起動。
- PLC への書き込み、書き込み可のタグ（§7）。

#### 3.7.4 関所（検証 → プレビュー → 承認 → 保存）

- **経路を問わず同じ関所を通す**。画面からの手動編集、REST、Tauri、MCP の
  どれも、同じ検証関数と同じ保存・監査の経路を使う。抜け道を作らない。
  タグ定義は既存のタグ CRUD の検証・保存・監査の経路を使う。
- **検証**: サーバー側の 1 つの関数で行う。形（種別ごとの許容項目）、上限、
  参照するタグ・収集グループの存在、タグの項目（アドレス・データ型・
  スケーリング・しきい値の大小関係など）、帳票テンプレートの構文を確かめる。
  **保存せずに検証だけする口**を持つ。
- **プレビュー**: 保存せずに見せる。
  - 表示グループと帳票: 実際の表示部品（監視画面の 4 種、帳票は
    `ReportView`）で、現在値やサンプルのデータを描く。
  - タグ定義: 変更前後の差分と、影響を受ける表示グループ・帳票、反映に
    収集の再起動が要ることを示す。PLC から試しに 1 回読むかは 3.7.9。
- **承認**: 下書きは承認されるまで有効にならない。**AI が作った定義の承認は
  人が行う**（AI のトークンでは承認できない）。承認できる role と自己承認の
  扱いは 3.7.9。
- **保存と監査**: 承認と同時に有効な定義になり、banto M14 の監査ログに残す。
  記録するのは、誰が（作成者・承認者、経路 = rest / tauri / mcp、AI 経由か
  どうか）、何を（タグ定義 / 表示グループ / 帳票テンプレート、対象の ID と
  名前、作成 / 更新 / 削除）、結果（承認 / 却下 / 検証エラー）。読み取りと
  プレビューは記録しない（既存の流儀）。
- 検証で落ちたものは保存しない。一部だけ保存することはしない。

#### 3.7.5 AI の境界

- AI は **REST / MCP の公開面だけ**を通る。DB への直接アクセスと、サービス層
  への直結はしない（ADR-0009 の決定 2: 直結は認可・監査の関所を迂回できる）。
- AI のトークンは**ユーザーの role に縛る**。そのユーザーが画面でできないことは
  AI にもできない。hub の `admin` API キーのような全権のキーにはしない。
- AI に見せる操作は 3.7.3 の範囲（タグ定義・表示グループ・帳票テンプレート）
  だけ。範囲外の操作（PLC 接続・収集グループの編集、収集の開始 / 停止・
  再起動、ユーザー・設定、PLC への書き込み）は MCP のツール一覧に出さない。
- AI が作った定義は、手動の編集と**同じ検証**を通り、3.7.4 の関所を通る。
  AI ができるのは下書きの作成・検証・プレビューの依頼までで、承認はしない。
- AI 経由の操作は監査で見分けられるようにする。
- AI の実行形態（ユーザーの claude CLI をサイドカーで起動する旧案か、外部の
  MCP クライアントか）は 3.7.9。

#### 3.7.6 手動編集（AI を使わない編集）

- **必須**とする。AI は手動編集の代行であって、唯一の入口にしない。
  - タグ定義: R0 の画面一覧（§6 の 3「タグ設定」）にあり、実装済み。
    **しきい値の編集欄を足す**必要がある（3.7.2）。
  - 表示グループ: R0 の画面一覧（§6 の 4「グループ設定」）にもともとある。
    #393 がこれ。グループ設定画面でしきい値を見せる・直す場合も、保存は
    タグ定義の経路で行う。
  - 帳票テンプレート: §7 の「M19 の MD テンプレート手書きで賄う」の手書きに
    当たる。テキストで編集してプレビューする画面を持つ（デザイナではない）。
- 手動編集も 3.7.4 の検証・プレビュー・保存（監査）を通る。手動編集に別人の
  承認を求めるかは 3.7.9。

#### 3.7.7 スコープの護り（§7）との関係

- **§7 は緩めない**。宣言データは §3.2 の 4 種固定パターンの中のパラメータで
  あり、汎用画面エディタではない。
- 語彙（表示種別、種別ごとの属性）を広げるのは**要件の改訂（オーナー決定）**で
  行う。データや AI では語彙を増やせない。
- 帳票: §7 の「帳票のカスタムデザイナは作らない」はそのまま。テンプレート
  文字列をテキストで書く（人でも AI でも）のは §7 の「MD テンプレート手書き」で
  あり、両立する。WYSIWYG やドラッグ配置は作らない。
- タグ定義を AI で作れても、タグは**読み取りの収集点**のまま。書き込み可の
  タグは作れず、PLC への書き込みが無いことも変わらない。
