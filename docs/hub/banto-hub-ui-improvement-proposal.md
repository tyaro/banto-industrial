## 目的と原則

HUB はタグサーバー・IoT サーバーとして、**設定、接続、状態確認、外部公開**を担う。タグ定義の追加はできるが、測定値や DB のレコードを利用者が手入力して蓄積する画面は設けない。書き込み可能なタグへの手動書き込みは、接続先の機器へ値を送る操作として別に扱う。

優先するのは、学習の容易さ、設定の簡易さ、日常の使い勝手、視認性。画面の説明文を増やすより、選んだ対象・現在の状態・次にできる操作を明確にする。左ペインとヘッダーで分かる階層をパンくずや重複見出しで繰り返さない。補助説明は、入力やエラーの判断に必要な場所へ置く。

## 共通の画面構成

### banto 系の共通の型（2026-11-17 オーナー決定）

HUB・ChronoGazer ほか banto 系のアプリで操作を揃えるため、次の型を共通にする。ChronoGazer での当てはめは[ChronoGazer 画面改善案](../chronogazer/chronogazer-ui-improvement-proposal.md) §2。

| 領域         | 役割                                                                                      |
| ------------ | ----------------------------------------------------------------------------------------- |
| メニューバー | **機能**を切り替える。ナビはヘッダーの行に入れる（banto v7.2.0 のメニューバー、#1159）    |
| 左ツリー     | そのページで操作する**対象**を選ぶ。2 階層まで（接続先 → 収集グループ）。タグは展開しない |
| 中央         | **タブ**で「一覧」と「設定」を切り替える                                                  |
| 右ペイン     | 中央の一覧で選んだ**行の詳細**だけを表示する                                              |

- 機能（メニューバー）と対象（左ツリー）を分け、同じものを二重に持たない。初めの案の「全体状態から HUB 設定までを一つのツリーで選ぶ」形は採らない。
- 用語は「接続先」「収集グループ」に揃える（両アプリの現行の画面と同じ）。
- 部品（ツリー・3 ペイン・中央のタブ）は、重複を避けて banto（`@banto/ui`）に置き、各アプリはそれを使う。
- 900px 以下ではナビは今のドロワーに戻る（banto の決定 D10-a）。狭い画面では一覧の幅を優先し、左ペインを折りたたみ、右ペインは必要時に重ねて開く。選択したグループ名とタグ名は残して、ペインを閉じても対象を見失わないようにする。

### HUB への当てはめ

メニューバーの並び: **状態 / タグ / DB / 公開 / 管理 ▾（API キー・ユーザー管理・監査ログ・書き込み監査）/ 設定**。設定は外観・アカウント・データ・セキュリティなど HUB 全体の設定だけにする（公開サービスは「公開」へ移す）。

**タグページ**（「タグ登録」と「タグモニタ」を一つにする。2026-11-17 オーナー決定）:

| 左ツリーで選んだもの | 中央のタブ「タグ一覧」 | 中央のタブ「設定」                                                           |
| -------------------- | ---------------------- | ---------------------------------------------------------------------------- |
| すべて               | 全タグ（検索で絞る）   | 出さない                                                                     |
| 接続先               | その接続先の全タグ     | 接続先の設定（アドレス・ポート・プロトコルなど）、配下のグループの一覧と追加 |
| 収集グループ         | グループのタグ         | グループの設定（周期など）と、経路ごとの公開のトグル（§外部公開）            |

- 右ペインはタグを選んだときだけ開き、タグの個別設定を表示する。閲覧者には値だけを見せる。
- 既定のタブは「タグ一覧」。ツリーで別の対象を選んでも、開いていたタブを保つ。設定タブへ切り替えたら右ペインを閉じる。
- 未保存のままタブ・ツリーの対象を変えるときは、捨ててよいか確かめる。ただし右ペイン（タグの編集）は、ツリーで対象を変えるだけなら確かめず、ペインも閉じない（入力は残る。式の編集中に別のグループのタグを挿入する流れを保つため。2026-11-18 オーナー決定、#1183）。「設定」タブのフォームの未保存と、「設定」タブへ移るときの右ペインは確かめる。
- 選択中の対象とタブを URL に持ち、再読み込みや戻る操作で同じ画面に戻る。

タグ表はタグ名、アドレス、現在値、状態、更新時刻を基本列にする。各行は一行で表示し、長い情報は右ペインに置く。行クリックによる詳細選択と、一括操作用のチェック欄を分ける。

統合は段階を踏む（`/tags` が大きいため）: ① 2 つのページでツリーの選択を共有する → ② タグ表に現在値の列を足す（段階 3 の表示中のタグの購読と合わせる）→ ③ `/monitor` を `/tags` に吸収する。

## タグの設定と運用

- タグ一覧に常時見える「タグを追加」を置く。選択中の接続先・収集グループを初期値として引き継ぐ。「保存して次を追加」と「保存して閉じる」を用意する。
- 初めに必要な入力は名前、アドレス、データ型。単位、換算、書き込み許可などは必要に応じて設定する。書き込みは既定で許可しない。
- 実機がなくても接続先、グループ、タグ定義を保存できる。保存前の形式・型の検証と、実機から値を取得できたかの確認は別にする。実機確認前の「未確認」と、収集開始後の通信異常を画面上で区別する。（2026-11-18 オーナー決定: 「未確認」は Hub の今回の起動後に、そのタグで一度も良好値を受けていない状態で、DB には記録しない。表示はタグモニタの品質の列。タグ追加の導線は収集グループ選択時だけのまま）シミュレーションは任意の確認手段として、実機の値と明確に区別する。
- 現在値には品質と更新時刻を併記する。接続断で多数のタグが影響を受けたときは、接続先の原因を先に示して対処先へ移動できるようにする。
- 保存した設定と運転中へ反映された設定の状態を区別する。未保存のまま別のタグやグループを選んだ場合は、入力を失わせない。

初回は「接続先を設定 → グループを設定 → タグを追加 → 値を確認 → 公開」を、実際の完了状態に合わせて次の操作へつなぐ。実機がない場合、値の確認は後から実施できる。通常運用では初回用の案内を常時表示しない。

## タグモニタからの手動書き込み

一般的なタグサーバーのタグモニタと同様に、選んだタグへ値を書き込める操作を追加する案。中央のタグ表で行を選び、右ペインにタグ名、接続先、現在値、品質、更新時刻、書き込み可否を表示する。書き込み可能なタグでは入力欄と「値を書き込む」を出す。bit はオン・オフ、数値はデータ型・範囲・単位に合う入力にする。行の選択、ダブルクリック、値の入力だけでは送信しない。

送信前に対象タグ、接続先、現在値と新しい値を確認できるようにする。タグ単位の書き込み許可、HUB 全体の書き込み受付（`write_enabled`）、ドライバの対応、利用者の操作権限を満たすときだけ実行する。読み取り専用タグ、演算タグ、DB タグなど書き込めない対象は理由を表示する。シミュレーション接続への書き込みは拒否されず内蔵シミュレータへ反映される（2026-09-15 オーナー決定 #363）ため、実機への操作と区別して表示する。多数のタグへの一括書き込みは、この画面の初期範囲に含めない。

成功時は書き込み結果を示し、現在値は次の受信値で更新する。結果不明では自動再送しない。

### 現行の書き込み経路との関係

- **書き込み経路の決定とぶつかる**: 現行は「外部からの書き込みの受付経路は REST と gRPC の 2 つのみ」（2026-08-04 オーナー決定、[タグサーバー設計](tag-server-design.md) §6）。どちらも `write:{tag}` スコープ付き API キーを要求する。MCP の書き込みツールも同じ `execute_write` を通るが、ロックダウン後は書き込まず推奨だけを返す（[MCP リファレンス](banto-hub-mcp-reference.md) §3）。管理 UI に画面利用者の権限で書き込む専用経路を作ることは、この決定の変更になる。実装前に、経路の追加を認めるか、既存の経路のどれかに画面を載せるかをオーナー決定として記録する。
- **試運転中とロックダウン後の扱い**: MCP と同じく、ロックダウン後は画面からの書き込みを止めるのか、画面利用者の権限があれば許すのかを決める。
- **共通の関門**: どの方式でも、既存の `execute_write` の関門（タグの `writable`、`write_enabled`、プロトコル、レート制限、値の変換）と監査を同じ経路で通す。ブラウザへ書き込み用 API キーを渡さない。設定編集権限と現場操作権限を同一視するかも決める。
- **結果の区別は既存の監査に合わせる**: 監査行はすでに `ok`・`rejected`（定義上の拒否）・`failed`（確かに効いていない）・`uncertain`（送ったあとで結果が分からない）に分かれている（#711・#898、`apps/banto-hub/core/src/write_path.rs`）。一方、REST の応答は `failed` と `uncertain` を区別せず、どちらも 502 `write_failed` を返す。画面ではこの 4 つの結果をそのまま示し、応答と監査行を対応付けられるようにする。
- **履歴は既存の監査画面を使う**: 書き込み履歴は既存の監査画面（`write-audit`、結果での絞り込みあり）に残る。右ペインからは、そのタグで絞り込んだ監査画面へ移る導線を置き、新しい履歴画面は作らない。操作者を監査に残すには、現行のキー ID に代わる画面利用者の識別を監査行へ記録する必要がある。

## 外部公開

タグの外部公開の対象は**収集グループ単位**で設定する。タグの右ペインに公開経路の設定を繰り返さない。公開の設定画面では、対象タグ数と、公開を止めた場合に外部クライアントから見えなくなる影響を確認できるようにする。

経路は性質が異なる。OPC UA・REST・WebSocket・gRPC・MCP は HUB が待ち受けて外部クライアントへ応えるサービスで、MQTT は HUB から外部のブローカーへ値を送り出す発行（publish）である。画面ではこの違いを分けて示す。

**決定（2026-11-17 オーナー）**:

- 公開の可否は**経路ごと**に、収集グループの設定タブのトグルで決める。トグルは **OPC UA / REST・WebSocket / gRPC / MCP / MQTT 発行** の 5 つ。REST と WebSocket は同じサーバーで catalog も共通なので一つにまとめる。
- 新しいグループの既定は**公開**（現行の「全グループを全経路に出す」動きと同じ）。
- トグルを切る前に、対象のタグ数と、その経路で今つながっているクライアントを示して確かめる。切った経路では、そのグループの一覧・読み取り・購読・書き込みをすべて止める（見えなくするだけにしない）。
- メニューバーの「公開」ページは**どう公開するか**（各経路の起動・ポート・証明書・認証）と、経路ごとの公開グループの一覧を扱う。左ツリーは「待ち受け」（OPC UA・REST/WebSocket・gRPC・MCP）と「発行」（MQTT）に分ける。今「設定 › 接続」にある MQTT 発行・gRPC・OPC UA の設定はここへ移す。API キーは管理者向けなので「管理 ▾」に残し、「公開」からリンクする。

現行の catalog は外部クライアントのバインディング契約である。グループの非公開化は見た目の変更だけではなく、catalog、値の読み取り・購読・書き込み、OPC UA・REST・WebSocket・gRPC・MCP・MQTT のすべての経路、構成変更通知へ同じ方針を適用する仕様変更として扱う。

## DB の扱い

DB 接続はタグ側の親グループに相当し、テーブルはその下の選択対象として見せる。ただしテーブルは複数行・複数列を持つ表データであり、タグ値へ自動変換しない。

接続先のアドレスまたはホスト名、ポート、DB 名、ユーザー、パスワードを設定し、接続確認後に取得したテーブル一覧から利用対象を選ぶ。テーブル名の手入力を基本操作にしない。読み取りのみか書き込みも必要かを設定し、必要なら診断目的の検索を試せるようにする。表データの利用経路は REST、必要に応じて gRPC とする。

これは現行の DB Source（SQL の結果をタグ値へ写す）・DB Sink（タグ値を DB へ保存する）の画面整理だけでは実現しない。表データ用 API の検索条件、件数上限、追加・更新の操作、DB 権限と API 利用者の権限を別途設計する必要がある。DB テーブルを左ツリーの末端に置くか、タグと同様に中央の一覧へ置くかも未決定。

## ドック型の配置（2026-11-20 オーナー決定）

banto のドック・フローティングのパネル（`@banto/dock-svelte`）を使い、HUB の画面を OPC UA のクライアント（UA Expert など）に近い配置へ寄せる。

- 配置: 左に接続のツリー、中央にタグの一覧とモニタ、右に属性、下にログ。浮かべられる窓も使う。統合の段階 ②・③ は今の 2 ページの形では作らず、ドックの上で組み直す。
- URL とレイアウトの線引き: 選択中の対象とタブは今の URL（`?target=`・`&tab=`）のまま持つ。パネルの配置は利用者ごとのレイアウトの保存に任せ、URL には載せない。
- 既定の配置: 1920×1080 前後で決め、ツリー・中央・属性・ログを開いておく。狭い画面は作り込まず、崩れないことだけを守る（一定の幅を切ったら右と下を自動で畳む。#1159 の 125% の確認もこの範囲）。自動で畳むのは狭い間だけの表示の状態で、利用者が保存した配置には書き込まない（幅を戻すと保存した配置に戻る）。畳んだ右・下は、狭い画面でも開いて操作できる経路を残す（#1159 は 1366×768・125% で右ペインを含めて読めることが要件）。
- 値を見張る窓: まず画面の中に浮かぶ窓として作る。Tauri で OS の別ウィンドウ（2 台目のモニタ）へ出せるかは、調べてから別に決める。
- 進め方: 下のログのパネル（接続の切断と復帰・書き込みの監査・アラーム・MCP や API の呼び出し） → 値を見張る窓 → 段階 ②・③ の組み直し。

### 下のログのパネル（2026-11-21 オーナー決定、#1253）

- 出す記録は 3 種で始める:
  - 接続: `collect_events` の `plc_connected`・`plc_disconnected`・`plc_reconnected`（#344 の意味。切断の始まりと、最初の良好な読み取りでの復帰）と、受け入れの接続の切断（`audit_log` の `origin = 'ingest' AND action = 'ingest_disconnected'` に限る）。
  - 書き込み: `hub_write_audit` の行（`ok`・`rejected`・`failed`・`uncertain` を含む）。
