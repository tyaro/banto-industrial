## 0. 結論（要約）

- **B1**: 本番用の headless host は `banto-serve` の本番化ではなく **新しい bin `chronogazer-server`**。`banto-serve` は E2E 10 本以上が使う開発用の入口なので、既定（`0.0.0.0`、`./banto-dev.sqlite3`）を変えずに残す。先に Tauri（`src-tauri/src/lib.rs` の `setup`）と `banto-serve` の `main` に重複する組み立て（約 300 行）を `chronogazer_core` のライブラリ境界 **`EngineRuntime`** に寄せる（banto-hub の `HubRuntime` と同じ型）。3 つの host（デスクトップ／headless／サービス）はすべてこれを呼ぶ。
- **KeyStore（H10）**: DPAPI（`CRYPTPROTECT_LOCAL_MACHINE`）でファイルに保存する実装を **新しい共有 crate**（仮称 `crates/banto-secret-store`）に置き、`banto_hub_bootstrap::KeyStore` を実装する。将来は sink の平文 API キーや Hub の MQTT パスワードにも使える。
- **B2**: 今の Tauri アプリを banto-hub の T16-2 と同じ判定木のシェルにする。サービスが Running かつ healthy ならローカルのエンジンを起動せず `http://127.0.0.1:<port>/` へ navigate、サービスが無い・Stopped ならプロセス内で起動、遷移中・不健康なら fallback 画面。**落とし穴**: navigate 先でも Tauri は `__TAURI_INTERNALS__` を注入するので、フロントの `isTauri()`（`apps/chronogazer/src/lib/banto/environment.ts:16`）が true になり invoke 経路を選んで壊れる。判定の修正が必須（§3.2）。
- **B3**: banto-hub の SCM・elev・ACL・NSIS の実装は大半が `banto-hub-core` に BantoHub 固定で入り、sink は写しを複製している。ChronoGazer で 3 つ目の複製を作らないよう共有 crate に抽出し、hub と sink も乗り換える。
- **別件（banto-hub の既存の欠け）**: Hub と sink のサービス本体は `ServiceControlAccept::STOP` しか受けていない（`apps/banto-hub/core/src/bin/banto_hub/win_service.rs:314-318`、`apps/banto-hub-sink/src/service.rs:324`）。OS のシャットダウン時に SHUTDOWN/PRESHUTDOWN 通知が来ず最終 flush を通らない可能性が高い（#586 のサービス版）。→ issue #589。ChronoGazer は最初から PRESHUTDOWN を受ける。

## 2. ChronoGazer の現状

- 収集はデスクトップの Tauri プロセス内（`src-tauri/src/lib.rs` の `setup`）。順序: A1 ロック → リストア適用 → `init_db` → 窓 → services → `HubService::new(KeyringKeyStore)` → `hub.resume` → `collect.attach_hub` → `autostart` → retention → LAN サーバー（`server.enabled` のときだけ）→ `AppState` → 監査 flusher → トレイ。画面は invoke（約 80 個の Tauri コマンド）で、REST は使っていない。
- 終了: `shutdown_app_state` が 取り消せない印 → LAN サーバー → `collect.stop`（最終 flush）→ `hub.shutdown` → `pool.close` を予算 5 秒で。
- `banto-serve` は開発・E2E 用。本番との差: 既定 bind `0.0.0.0`・DB `./banto-dev.sqlite3`、`HubService::shutdown`・`pool.close` を呼ばない、起動失敗を `expect`/`exit(1)`、ログはコンソールだけ、SCM 連携なし、KeyStore は `UnavailableKeyStore`（既定）、終了は Ctrl-C だけ。**本番に使える度合いは起動配線の参考まで**。
- `BANTO_HUB_MEMORY_KEYS=1`: 開発・E2E 専用（`MemoryKeyStore`＋`attach_hub`）。`e2e/tests/user-simulator-monitor-hub.spec.ts` が依存。
- 自動ログイン: ログイン不要モード → 自動ログイン（OS キーリングのパスワード）→ ログイン画面。
- データ: `%APPDATA%\dev.tyaro.chronogazer\`（`chronogazer.sqlite3`、`data\`、`backups\`、`audit-spool\`、`tray-hint-shown`）。`data.dir` は絶対パスも可。
- A1: 排他単位は DB の正規化パス、mutex `Global\ChronoGazer.<hash>`、host 種別は `Desktop` と `Serve`（B1-4 で `Server`・`Service` を追加）。A2: トレイ常駐と単一インスタンス。ログオン時の自動起動なし。
- REST に無い Tauri 専用の操作: LAN サーバー設定、認証モード、自動ログイン、Acrylic、バックアップフォルダを開く、汎用の `settings_get/set`、初回セットアップ。
- 配布: `tauri.conf.json` の bundle は既定（NSIS currentUser）、専用インストーラなし。

## 3. 設計案

### 3.1 B1: headless host と KeyStore

**(a) `chronogazer_core::engine`（新設）**: `EngineConfig { db_path, data_base, key_store, host, listen, allow_setup, seed_viewer_public }` → `EngineRuntime::start(cfg) -> Result<RunningEngine, EngineStartError>`。A1 ロック（DB に触れる前）→ リストア → `init_db` → services → hub（`attach_registry`、`attach_hub`）→ resume/autostart/retention → listener → 監査 flusher。失敗は `Result`。`RunningEngine` は各 service のハンドルと `shutdown(budget) -> ShutdownReport`（今の順序、最初に `begin_shutdown`）。LAN の listener は入れ替えられる `ServerSlot`。最初の PR は `banto-serve` だけを乗り換え、Tauri は別 PR。

**(b) 新しい bin `chronogazer-server`**: B1 はコンソールモードだけ（`run-service`/`install`/`uninstall` は B3、1 つの exe）。

- データ: 既定 `%ProgramData%\ChronoGazer\`、`CHRONOGAZER_ROOT` で上書き（空文字は無視、純関数で非 Windows でもテスト）。

```
%ProgramData%\ChronoGazer\
  chronogazer.sqlite3, chronogazer.sqlite3.instance.lock
  data\
  backups\chronogazer.sqlite3\  audit-spool\chronogazer.sqlite3\
  logs\chronogazer-server-YYYY-MM-DD.log
  secrets\hub-keys\<sha256(account)>.bin
  run\endpoint.json   （port・pid・scope・version。シェルの probe 用。Users に読み取り可）
```

- **H9: 既存の `%APPDATA%` は読まないし移さない**（消さない）。旧データの案内（決定 3）は **このエンジン（サービスでは LocalSystem で動き、利用者の `%APPDATA%` を指さない）ではなく、利用者として動くシェル（B2-4）が行う**（2026-10-12、#590 のレビュー）: シェルが対話ユーザーの `%APPDATA%\dev.tyaro.chronogazer\chronogazer.sqlite3` の存在を調べ、画面で 1 回だけ案内する。案内済みの印は**利用者ごと**（その利用者の `%LOCALAPPDATA%` 配下）に持つ。インストーラも、インストールした利用者の旧データを見つけたら完了画面で案内する。
- `ChronoGazerHost` に `Server` と `Service` を追加。
- 待ち受け: **loopback の listener は常に開く**（`127.0.0.1:<server.port>`）。`server.enabled` のときだけ LAN 用を足す（`0.0.0.0` なら 1 本にまとめる）。既定 port 8721（Hub の 8722 と衝突しない）。認証無効と LAN の不整合の判定はデスクトップと同じ。
- `GET /api/host`（未認証、新設）: `{ product: "chronogazer", hostKind, version, scope }`。シェルの probe が別製品・別 DB・port 競合を見分ける。
- KeyStore は常に `DpapiFileKeyStore`、`attach_hub` も常に。**`BANTO_HUB_MEMORY_KEYS` はこの bin では読まない**（`banto-serve` 専用のまま）。
- 終了: Ctrl-C・Ctrl-Break は `shutdown`（予算 15 秒）。**コンソールを閉じたとき（`CTRL_CLOSE_EVENT`）は Windows が待つ時間が約 5 秒しかない**ので別の経路・別の予算にし、OS の猶予内（例 4 秒）で最終 flush まで終える（2026-10-12、#590 のレビュー）。B1-5 の受入条件に「コンソールの × で閉じても `collection_stopped` と最後の行が残る」を実機で含める。
- ログ: `logs\` に日付つきファイル、stderr も向け直す。保持日数は設定値（初期案 30 日）。

**(c) `crates/banto-secret-store`（新設、H10）**: `Protector` trait、Windows 実装 `DpapiMachine`（`CRYPTPROTECT_LOCAL_MACHINE | CRYPTPROTECT_UI_FORBIDDEN`、`LocalFree`、平文は `zeroize`）、テスト用 `PlainProtector`。`FileSecretStore<P>`: 1 アカウント 1 ファイル（名前は `sha256(account)`）、中身はマジック `BSS1`・版数・アカウント・blob、entropy は `"banto-secret-store/v1:" + account`（ファイルを入れ替えても復号できない）、書き込みは一時ファイル → `MoveFileExW(REPLACE_EXISTING|WRITE_THROUGH)`、削除は「無ければ Ok」、プロセス内は `Mutex`。ディレクトリは継承しない保護された DACL（SYSTEM と Administrators が Full、**インストール利用者の SID に Modify**。決定 4 - 非昇格のデスクトップ host が同じキーを読み書きするため。Users や Operators 全体には付与しない）。作成・更新のたびにこの DACL を保つ（呼び出し側が指定したインストール利用者の SID を受け取る）。`impl KeyStore`、失敗は秘密を含めない。非 Windows は `UnsupportedPlatform` で fail closed。

**(d) テスト方針**: engine は既存の `collect_roundtrip.rs` と E2E が green、start の失敗が `Result`、shutdown の順序、ロック競合で DB に触れない。`chronogazer-server` はルート解決の全分岐、`ListenPlan`、`/api/host`、一時ルートで dev_plc から収集する統合テスト。secret-store は形式・原子的置換・entropy 取り違えの拒否・削除の冪等性（全 OS）、DPAPI の往復（Windows）、再起動後に Hub の resume が張れること（Windows、2 回起動）。

### 3.2 B2: シェルの決定（概略）

**B1-1 の実装メモ（2026-10-12、実装済み）**:

- 起動は `EngineRuntime::open`（A1 の排他 → リストア予約の適用 → `init_db`）と `OpenedEngine::start`（サービス → Hub → 収集 → listener → 監査の定期の流し込み）の 2 段。デスクトップは今どおり DB を開けた後・サービスの前に窓を作るため、B1-2 では間で窓を作る。B1-2 の呼び方の見通しは `apps/chronogazer/core/src/engine.rs` のモジュール doc。

**追補: 起動に失敗したときのエラーの窓と対処の選択（2026-10-12 オーナー決定・実装済み）**:

オーナー決定（2026-10-12）: 起動時に止まる失敗で、**panic で落とさず、エラーの窓を出して利用者に対処を選ばせる**。
どの選択肢でも**今の DB や記録を消さない**。

| 起きたこと                                                                                          | 選べる対処                                                                                                                                                                       |
| --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| データの保存先（`data.dir`、`EngineStartError::StoreConfig`）が読めない                             | ① 保存先のフォルダを選び直す（フォルダ選択ダイアログ、設定に保存して起動を続ける）② 既定の場所に戻して起動する（記録は元の場所に残り画面からは見えなくなる旨を先に伝える）③ 終了 |

| 保存先に書き込めない（USB の取り外し・権限・ドライブが無い。起動時の試し書き、2026-10-12 追加決定） | もう一度確かめる（差し直した等の後に同じ保存先でやり直す）・① 選び直す・② 既定に戻す・③ 終了                                                                                     |

- ① ② のうち作り直す・戻す・既定に戻すは確認を 1 回はさむ。対処が失敗したら（フォルダに書けない・バックアップが壊れている・名前を変えられない）同じ窓に理由を出して選び直せる。

実装メモ（2026-10-12）:

- **判断と対処は `chronogazer_core::startup_recovery`**（Tauri に依存しない）。`classify`（`EngineStartError` → `FailureKind`）と `plan`（`FailureKind` → `WindowPlan`）は純関数で、表のテストで総当たりにした。対処は `set_aside_broken_db`（作り直す）・`restore_from_backup`（戻す）・`apply_store_dir`（選び直す・既定に戻す）。窓は `src-tauri` の `startup` モジュールと `static/startup-recovery.html`（今までのエラーの窓 `legacy-db.html` と同じく、コマンドを呼ばない静的ページ）。
- **分類**: DB の失敗は SQLite の文言で分ける（`file is not a database`・`malformed`・`corrupt` → 壊れている、それ以外 → 開けない）。sqlx の `VersionMissing`（この版が知らない migration が当たっている = 新しい版の ChronoGazer が使った DB）は**「終了」だけ**にした（壊れていない DB を脇へ退けないため。その版で開くよう案内する）。`Hub` の初期化と、`start` の前の設定（認証・LAN）の読み取りの失敗は「設定 DB を読めない」として DB の窓。保存設定の失敗は、読めないのが `data.dir` そのもの（`StoreConfig::data_dir_unreadable`、engine が pool を閉じる前に確かめる）で DB が壊れていないときだけ保存先の窓、`data.dir` は読めるが保持期間などが読めないときは DB の窓（開けない）。
- **作り直す**: `-wal`・`-shm`・`-journal` を**先に**、本体を最後に `<DB 名>.broken-<日時>`（ローカル時刻の `YYYYMMDD-HHMMSS`、同名があれば `-1`…）へ移す（本体だけ移して古い WAL が元の名前に残ると、作り直した空の DB に当たりうるため）。途中で失敗したら移したものを元に戻す。Windows で閉じた直後のハンドルに備えて名前の変更は短く再試行する（最大約 3 秒）。
- **バックアップから戻す**: `BackupService::stage_restore_from_file`（整合性検査と必須テーブル）で予約 → 壊れた DB を作り直しと同じ形で退ける → **対処の中で** `apply_pending_restore_at_startup`（今のリストアと同じ関数、再検査つき）を呼んで適用し、**実際に適用されたことを確かめる**（#594 のレビュー P1: 次の `open` に任せると、適用が失敗しても通常の起動は記録して続けるため、元の DB を退けた後の `init_db` が空の DB を作り、戻せたかのように窓が閉じる。予約が残って次の起動で遅れて適用されることもある）。適用されなければ（I/O の失敗・検査に通らない）予約を取り消し、退けた DB を元の名前に戻して同じ窓に理由を出す（何も消さない。元の名前に何かが置かれていたら上書きせず退けたまま残す）。適用した結果はエンジンへ渡し、`restore_applied` を監査に残す。通常の起動（設定画面で予約したリストア）の適用の失敗は今までどおり記録して続ける。退ける理由: リストアの適用は今の DB の本体だけを `pre-restore-*` に写して `-wal`・`-shm` を消すので、壊れた DB の WAL の記録を失いうる（その代わり `restore_applied` の `preRestoreBackupFileName` は空になる。`startup_recovery` の監査に退けた名前が残る）。退けられなければ予約を取り消す。`BackupService` は SQLite のハンドルを要求する（SQLite かどうかの確認だけに使う）ので、壊れた DB の代わりにメモリ上の空の pool を渡す。
- **保存先**: 書く前にフォルダに書き込めることを確かめ（作る → 小さなファイルを書いて消す）、だめなら設定を変えずに理由を返す。書くのは `data.dir` の 1 項目だけ（保持期間には触れない）。フォルダは絶対パスだけ受ける。
- **保存先の試し書き**（2026-10-12 追加決定）: `EngineConfig::store_dir_check_required`（デスクトップ `true`、`banto-serve` `false`）のとき、`start` が保存設定を解決した直後（収集を組む前）に解決済みの `data.dir` へ `check_writable_dir`（無ければ作る - 収集の開始も作るので同じ扱い - 一時ファイルを書いて消す。既存の中身には触れない）を行い、失敗なら Hub を止め pool を閉じて `EngineStartError::StoreDirUnwritable` を返す。窓は「書き込めない」（値を読めない窓と文言を分け、理由にフォルダと OS のエラーを出す）で、選択肢の先頭に「もう一度確かめる」（何も変えずに起動をやり直す）。`banto-serve` は確かめない（開発・E2E 用。今までどおり書けなければ収集の開始がエラーを状態に残す。E2E の前提を変えないため）。B3 のサービスは同じ判断（`classify`・`plan`）を使える。
- **A1 の排他（#594 のオーナーレビュー P1）**: 作り直す・バックアップから戻すは、DB・付随ファイル・リストアの予約を変える**前に**エンジンと同じ A1 の排他を取り（`startup_recovery::lock_for_recovery`、`recreate_database`・`restore_from_backup` の中）、取れなければ何も変えずに「既に banto-serve が使用中」などの理由を同じ窓に出す。取った排他は `RecoveryLock` として `EngineRuntime::open_with_recovery_lock` へ途切れずに引き継ぐ（その後はエンジンが持つ）。保存先の書き換え（`apply_store_dir`）は `open` の後（エンジンが排他を持つ）に行う。**窓を出している間ずっとは持たず、操作の瞬間に取る**ことにした: 窓を出している間は DB に触れていないので持つ必要が無く、持っていると利用者が同じ DB を使う `banto-serve`・別の ChronoGazer を確かめたり止めたりして対処したいときに、そちらの起動まで止めてしまうため。例: `retention.days` だけが読めない DB はデスクトップでは DB の窓で止まるが、`banto-serve`（`store_config_required = false`）は既定値で起動できる - その間に窓で作り直しを選んでも、ファイルは一切変わらない（以前は排他を確かめずに名前を変えていた。Unix では開かれた DB の rename も通る）。
- **画面の作成の失敗（#594 のレビュー P2）**: エンジンが動いた後にメインの窓・トレイを作れなかったら、作りかけのメインの窓を破棄し、エンジンを終了処理（`RunningEngine::shutdown`）で止めてから「終了」だけの窓を出す（`abandon_after_window_failure`）。以前はメインの窓とエンジンが残り、窓を閉じても終了せず（メインの窓は × で隠れるだけ）、トレイも無いまま収集だけが動き続けた。確認用に、デバッグビルドだけ環境変数 `CHRONOGAZER_TEST_FAIL_TRAY` でトレイの作成の失敗を注入できる（リリースビルドには入らない）。
- **やり直しの方式: 同じプロセスで `open`/`start` をやり直す**（`AppHandle::restart` にしない）。理由: 再起動は古いプロセスが終わりきる前に新しいプロセスが単一インスタンスのプラグイン・A1 の排他にぶつかりうること、選んだ対処を新しいプロセスへ渡す経路が要ること。失敗して戻った `open`/`start` は A1 の排他と pool を返している: `init_db` は失敗の経路でも pool を閉じてから返すようにした（以前は旧形式の判定と migration の失敗で閉じずに戻っていた）、`start` の失敗の経路は B1-1 から閉じる、`start` の前で止めるときは新設の `OpenedEngine::close`（pool を閉じるのを待ってから排他を返す）。
- **デスクトップの起動の組み立て**を `launch_desktop` に切り出し、`setup()` の最初の起動と対処の後のやり直しの両方が呼ぶ。**メインの窓は `start` の後（`AppState` を manage した後）に作るように移した**（B1-2 では `open` と `start` の間）: `start` の失敗でメインの画面を出してから対処の窓に切り替えないため。旧形式の DB で空の画面を先に出さない、という B1-2 の理由もそのまま満たし、画面のコマンドが `AppState` より先に呼ばれることも無くなる。
- **窓と Rust のやりとり**: 窓は capabilities の対象外（コマンドを呼べない）のまま、選んだ対処を `/__recovery/<対処>?file=<バックアップ>` への移動で知らせ、Rust が `on_navigation` で受け取って移動を取り消す。Rust は今出している選択肢だけを受け、処理中は二度押しを無視し、窓の × を止める（名前の変更の途中で終わらせない）。結果は同じ窓に描き直す。フォルダ選択は Rust 側の `tauri-plugin-dialog`。
- **監査**: 選んだ対処は DB を開けた後の `OpenedEngine::start` が `startup_recovery`（`resource: startup`、`detail.choice` と退けたファイル名・バックアップ名・保存先）として記録する（`OpenedEngine::with_recovery_note`）。「もう一度確かめる」も `choice = retryStoreCheck` を残す（#594 のオーナー再レビュー。再試行の記録だけは `start` の失敗しうる処理（保存先の書き込み確認・listener の bind）がすべて済んだ後に書く。書けないまま押して窓に戻る再試行には成功の行を残さない。他の対処は対処自体が済んでいるので `start` の早い段階で記録する）。
- **洗い出した panic と扱い**（`setup` の中）: `app_data_dir()`・`create_dir_all` の `expect` → 「終了」だけの窓。`init_db` の失敗の `panic!` → 分類して窓。`auth_config`・`server_config` の `expect` → DB の窓（`opened.close()` の後）。`start` の `Hub`・`StoreConfig`・その他の `panic!` → 分類して窓。メインの窓・トレイの作成の `?`（`setup` が `Err` を返すと `run()` の `expect` で panic）→ 作りかけのメインの窓を破棄しエンジンを止めてから「終了」だけの窓（上の「画面の作成の失敗」）。`tauri.conf.json` の main の窓の定義・既定アイコンの `expect` → エラーに変えた。**残した panic**: `run()` の `.build(..).expect("error while building tauri application")`（Tauri 自体・WebView2 を起動できない = 窓を出す手段が無い）と、内容が文字列だけの `serde_json::to_string` の `expect`（失敗しない）。

**B1-3 の実装メモ（2026-10-13、実装済み）**:

- **crate**: `crates/banto-secret-store`（workspace に追加）。公開するのは `Protector`（`protect(plain, entropy)`・`unprotect(blob, entropy)`）、`DpapiMachine`（Windows）、`PlainProtector`（`test-support` feature。暗号化しないが entropy の一致は確かめる）、`FileSecretStore<P>`（`open(dir, DirAccess, protector)`・`load`・`store`・`remove`・`path_for`）、`DirAccess`（`service_only()` / `with_install_user(InstallUserSid)`）、`acl::{ensure_dir, verify_dir, reset_dir_acl, read_dir_dacl, current_user_sid}`、`SecretStoreError`。`impl banto_hub_bootstrap::KeyStore for FileSecretStore<_>`（失敗はすべて `ErrorKind::KeyStore`）。
- **ファイル**: 名前は `sha256(account)` の hex + `.bin`。中身は `BSS1`・版数 1（u16 LE）・アカウントの長さ（u32 LE、1〜1024）・アカウント（UTF-8）・blob の長さ（u32 LE、〜64 KiB）・blob。末尾の余分・切れ・知らない版数は壊れているとして拒否。entropy は `"banto-secret-store/v1:" + account`。読むときはファイルの中のアカウントの一致も確かめる（アカウントの欄は平文なので書き換えられるが、書き換えても entropy が違って復号できない - テストで固定）。平文の上限 16 KiB。
- **書き込み**: 同じディレクトリに `.<名前>.<pid>-<nonce>.tmp` を `create_new` で作り、書いて `sync_all` して閉じてから `MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH)`（非 Windows は `rename` + ディレクトリの `sync_all`）。一時ファイルは guard が失敗・panic でも消す。プロセスの中は `Mutex` で 1 つずつ（別のプロセスとの直列化はしない。A1 の排他でエンジンは 1 つ）。
- **ACL**: 無ければ `CreateDirectoryW` に SDDL `D:P(A;OICI;FA;;;S-1-5-18)(A;OICI;FA;;;S-1-5-32-544)(A;OICI;0x1301bf;;;<インストール利用者の SID>)` の記述子を渡し、**作るのと同時に**付ける。インストール利用者の SID は `S-1-5-21-`（ローカル・AD）と `S-1-12-1-`（Microsoft Entra ID）の領域の文字列だけ受け（SDDL に組み込むので文字も数字と `-` だけ）、作る・直す前に `LookupAccountSidW` で利用者のアカウント（グループではない）であることを確かめる（解決できない SID は拒む = fail closed。Entra の利用者はその PC でサインインしたことがあれば解決できる）。この SID の検証は**作る経路と既にある経路の分岐より前**に行う（#595 のレビュー P2: 既にある経路で飛ばしていたため、グループの SID に「変更」を付けた既存のディレクトリを受け入れえた）。`FileSecretStore` は `open` で 1 回だけ確かめ、読む・書く・消すたびの ACL の再確認では確かめ直さない（SID は `open` で固定され変わらない）。あれば DACL と所有者を読み戻し、**保護されている・継承された ACE が無い・許可の ACE がちょうど期待の 2〜3 個・所有者が SYSTEM / Administrators / インストール利用者**であることを確かめる。開くときだけでなく、読む・書く・消すたびに確かめる。
- **既にあるディレクトリの ACL が違うとき**（指示による決定、オーナー確認待ち）: **使わずに `AclMismatch` で失敗する（fail closed）。自動では直さない**（広げも狭めもしない。違う形には、管理者が意図して変えた・別の製品が使っている・一般の利用者が先に作った乗っ取りの準備、のどれもありうるため）。直すのは `acl::reset_dir_acl` の明示的な呼び出しだけで、B3-3 の昇格ヘルパ（管理者の操作）から使う想定。`reset_dir_acl` は所有者を変えないので、所有者が許可外なら直した後も失敗のまま（所有権の取り直しは手作業）。
- **しないこと**: 親ディレクトリ（`secrets\`）の ACL（B3-3）、ファイル 1 つ 1 つの DACL の確認（ディレクトリから継承し、書くたびに丸ごと置き換わる）、孤児のファイルの掃除。非 Windows は `open`・ACL の操作がすべて `UnsupportedPlatform`（`PlainProtector` と `open_without_acl` のテストは全 OS で通る）。
- **秘密を出さない**: crate はログを出さない。`SecretStoreError` は平文・blob・アカウントを持たない。`FileSecretStore` の `Debug` は手で実装（ディレクトリ・ACL の指定・protector の型名だけ）。復号した平文は `Zeroizing`、DPAPI の出力のバッファは消してから `LocalFree`。

- **listener の停止の上限**（#598 のオーナーレビュー P1、2026-10-13）: エンジンの終了の 3.（listener の停止）は banto の `RunningServer::stop` が開いている要求の完了を最大 5 秒待つため、本文を送り切らない HTTP の要求 1 本で、コンソールを閉じたときの予算（約 3.5 秒）を使い切り、5. の収集の停止（最終 flush・`collection_stopped`）を飛ばしたまま OS がプロセスを終わらせていた。Close の総予算を OS の猶予を超えて延ばすのではなく、**listener の停止は裏のタスクで並べて始め、`engine::listener_stop_cap`（予算の 4 分の 1、最大 1 秒）までだけ待って収集の停止へ進む**ようにした（停止そのものは裏で続き、banto の 5 秒で中断される。`ShutdownReport::listener_stop_abandoned`）。デスクトップ（5 秒）・Ctrl-C（15 秒）の経路も同じ engine の終了なので共通に直った。順序の約束（消費者 → 書き手 → 生産者 → DB）は変えていない: 停止の合図で新しい接続は受け付けなくなり、残った要求が収集を始めることは取り消せない印が断る。残った要求が DB を触っても pool は 6. まで開いていて、閉じた後に届いたものは DB のエラーになるだけで記録は失わない。検証: 収集中に `POST /api/auth/login` へ `Content-Length: 100` で本文の先頭 1 バイトだけ送って接続を保ったまま、(a) Ctrl-C で止めると 4 秒未満で終わり `collection_stopped` と行が残る、(b) ウィンドウを閉じる経路でも残る（統合テスト 2 件）。反証: 上限なしで待つ元の形に戻すと、(a) は約 5.1 秒かかり、(b) は最新のイベントが `plc_connected` のまま（`collection_stopped` が無い）で落ちる。
- **保持期間の掃除の待ちを収集の停止の後へ**（#598、2026-10-13。#597 の取り込みの後）: #597 は掃除の終わりを listener の前（収集の停止の前）で待っていたため、掃除が長引くと listener と同じく最終 flush の予算を食いえた。掃除には最初の 2. で止める合図だけを送り、**終わりを待つのは 6.（収集の停止・Hub の購読の停止の後、pool を閉じる前）**にした。新しい順序は「1 印 → 2 背景タスクに合図 → 3 listener（上限つき）→ 4 収集の停止（最終 flush）→ 5 Hub → 6 掃除の終わり → 7 pool を閉じる」。掃除の待ちが時間切れなら `RetentionStopped` を報告せず pool も閉じない（#597 の約束はそのまま）。**掃除と収集の停止が重なっても壊れない**: 削除（`CollectorService::prune_data_files`）と停止はどちらも収集の `writer_gate` を取ってから書き手に触れるので直列になる（削除が書き手を掴んだまま停止が close に進むことも、close の途中で書き手なしの削除が走ることも無い）。残る待ちは、削除の最中に終了が来たときに収集の停止がその削除の終わりを待つことだけ（同期のファイル削除で短い。待つ位置を動かしても変わらない）。検証: 掃除を途中で止めたまま 3.5 秒の予算で終了すると、収集の停止までは進んで `collection_stopped` が残り、時間切れで pool は閉じない（engine のテスト）。#597 のテストは、時間切れの終了が収集の停止・Hub の停止までは進むことを期待するように直した（掃除の終わりと pool を閉じる手順は報告しない、は同じ）。反証: 掃除の待ちを収集の停止の前に戻すと新しいテストが落ちる。

- **合成の identity の名前をアカウント名として予約（#600 の Copilot の指摘、2026-10-14）**: 監査の行は `actor_username`/`actor_role` しか持たないので、資格情報なしのセッションと同じ名前のアカウントがあると操作者を区別できない（banto のアカウント名の検証は 1〜32 文字の長さだけ）。`local`（ログイン不要モード）・`localDesktop`（この PC からの接続）・`public`（閲覧公開、banto の `PUBLIC_VIEWER_ID`）を予約し（`local_grant::RESERVED_USERNAMES`）、前後の空白を除いて大文字小文字を区別せずに比べ、アカウントを作るすべての経路で banto のサービスを呼ぶ**前に**断る: REST の `POST /api/auth/setup`・`POST /api/users`（`/api` の前段のミドルウェアで本文を読む）、デスクトップの `auth_setup`・`users_create`。誤りは banto のアカウント名の検証と同じ形（`422`、欄 `username`）にしたので、画面は既存の欄の誤りとして出す（画面の変更なし。依頼の「400」ではなく、既存の名前の誤りと同じ `422` にそろえた）。アカウント名を変える口は無い（`PUT /api/users/{id}` は表示名と role だけ）。**既にその名前のアカウントがある DB**（予約より前に作ったもの）は、起動のたびにログへ警告を出し、アカウントは変えず起動も止めない（その間の初期化後の `localDesktop` の発行は下の追加のレビュー (3) で断るようにした。別の名前のアカウントへ移って削除してもらう。勝手に名前を変えるとログインできなくなる）。検証: 予約名の判定の単体テスト、REST の setup・`POST /api/users` とデスクトップの `setup_body`・`users_create_body` で予約名が `422`（アカウントは作られない）・普通の名前は通る。反証: 予約名の判定を常に偽にする → 3 件のテストが落ちる。
- **#600 の全体監査（上位モデル、2026-10-14。オーナー決定「おすすめで」: F1〜F4 をこの PR で直し、F5・F6 ほかは既知の制限）**: 1 件ずつの指摘が続いたため、B2-1 の範囲を一度に監査した。
  - **約束（G1〜G10 の要約）**: 発行は `chronogazer-server` の常時の listener への、peer と Host の両方が loopback の要求だけ（G1）。未初期化の間だけ admin、初期化後は `auth.local_grant`（既定 off・読めなければ off）、閉じる方向は即時で、setup が成功したら未初期化の admin のトークンは必ず失効（G2）。発行・設定変更のたびに監査が 1 対 1 で正しい actor（G3）。予約名のアカウントはどの経路・本文の表現でも作れない（G4）。`PUT /api/settings/server` はこの PC からの admin だけで、保存値と実際の listener が切断・失敗・並行でも食い違わない（G5）。`GET` は入れ替えを止めず新旧を混ぜない（G6）。`auth.disabled` は REST では読むだけ（G7）。setup はこの PC からだけ、未初期化の間の grant からの `POST /api/users` は `400`（G8）。秘密を出さない（G9）。status と発行の判定が食い違わない（G10）。
  - **F1（setup の後の失効が飛ぶ）→ 直した**: 成否を HTTP の状態ではなく応答の本文の `success` で決め（上流は失敗でも `200 {success:false}`）、2xx で読めない・解釈できない本文は失効へ倒す（fail closed）。DB を読み直さない（commit の後の追加の読み取りだけが失敗すると失効が飛んでいた）。失効は判断の直後に同期で行い、監査はその後。全体を下の切り離したタスクの中で行う。
  - **F2（`PUT /api/settings/server` の切断で入れ替えが途中で捨てられる）・F4（監査・失効の後処理が応答の future の寿命に依存）→ 直した**: hyper 1.x は応答を待つ間に相手の FIN を読むと service の future を捨てるので、handler の中で `.await` をまたぐ副作用は接続の切断で途中のまま捨てられる（slot が空のまま保存値は「公開」・監査の行が無い）。`local_grant::run_detached` で `tokio::spawn` した別のタスクに切り離し、handler は `JoinHandle` を待って結果をそのまま返す（応答の外形は不変。`JoinHandle` の drop はタスクを止めない）。対象は `PUT /api/settings/server`（`apply_server_settings` 丸ごと）、`PUT /api/settings/auth`（保存・失効・監査）、grant の発行とその監査、setup とその後の失効。**監査の提案（後処理だけを切り離す）より広く、grant の発行と setup は上流の処理ごと切り離した**: 上流の処理（setup の commit）の途中の await 点で捨てられても、上流の副作用と後処理が揃って完結するため。タスクが panic したら `500`（「状態を読み直して」）を返し、理由はログに残す。デスクトップの Tauri のコマンド（`server_apply`）は対象外（画面の呼び出しは切断で捨てられない）。
  - **F3（JSON の配列の本文で予約名の検査を素通り）→ 直した**: 上流の `SetupRequest`・`CreateUserRequest` は serde の配列の表現も受理するので、setup と `POST /api/users` の本文が JSON として読めて object でなければ `400`。JSON として読めない本文は従来どおり上流に任せる（重複キー・非文字列・Content-Type 違いは上流が断る）→ **下の追加のレビュー (1) で `400` に改めた**。
  - **検証**: engine の本物の TCP で、設定の lock を外から持って適用を保存の手前で決定的に止め、FIN を送り、応答なしで閉じられたのを確かめてから lock を放す → 監査の行（上限つきで待つ）・保存値・`GET` の状態が新しい設定にそろう（LAN の IP があれば開く方向も）。setup の判断の表、閉じた pool の `UsersService` でも `success: true` で失効すること、配列の本文の `400`、`run_detached` の panic が `500`。setup の commit の直後に切断しても失効する本物の TCP のテストもあるが、commit の**後**の await 点で捨てられる組み合わせは時間でしか作れないので、修正を戻しても落ちるとは限らない（決定的な守りは判断の表と DB のテスト）。反証: 切り離しをやめる → 切断の適用のテストが落ちる、判断を HTTP の状態だけに戻す・DB の読み直しを戻す → 判断の表・DB のテストが落ちる、object 以外を素通しにする → 配列のテストが落ちる。
  - **既知の制限（受け入れる）**: (1) **F5** 再起動が要る設定（ポートの変更）の保存の前の bind の確認は、常に `127.0.0.1:<port>` を見る（`0.0.0.0` にまとめる変更でも他のアドレスの塞がりは見ない。次の起動の失敗で分かる）。(2) **F6** `POST /api/users` の本文の先読みは認証の前に行う（上限 64KB、実害なし）。(3) `LanStatusCache` が起動の後に一度も書かれていない間の、適用の途中の `GET /api/settings/server` は `503`（上の「前回の見落とし」(2)）。(4) 発行の監査で応答の本文が読めない場合は `500` を返し、発行済みの未使用のトークンが寿命まで残る。(5) 同じ PC の reverse proxy・同じ PC の他の利用者（モジュール doc・§6）。(6) 切り離したタスクは接続が切れても走り続けるので、終了（`RunningEngine::shutdown`）と同時に来た適用は、終了が LAN の slot を空にした後で新しい listener を置きうる（従来の handler でも、常時の listener の graceful な停止が要求を待つ間に同じことが起きうる。`chronogazer-server` はその後プロセスを終えるので残らない）。(7) 切り離したのは B2-1 の経路だけ。上流（banto）の他の handler の監査（ユーザーの作成など）は従来どおり応答の future の中。
- **#600 の全体監査の後の追加のレビュー（オーナー P2・Copilot、2026-10-14）**:
  - **(1) アカウントを作る経路で JSON として読めない本文は `400`（オーナー P2、fail closed）**: `serde_json::Value` の読み手には再帰の上限（128）があるが、上流の `SetupRequest`・`CreateUserRequest` は知らない欄を `IgnoredAny` で読み飛ばすのでその上限に当たらない。知らない欄を 130 段の配列にした本文は前段では読めず上流では読めるので、上流に任せると予約名のアカウントが作れた（テストで再現）。setup・`POST /api/users` の前段で、読めない本文は「本文を JSON として読めません」の `400` にした。前段は認証の層の外側なので、認証なしの読めない本文も `401` ではなく `400`（F3 の配列と同じ）。既存のテストで JSON でない本文の素通りを前提にしたものは無かった。反証: `Err` を素通りに戻す → 深い入れ子のテストで setup が成功して落ちる。
  - **(2) 設定の REST の操作者は本文を待つ前に確定する（Copilot）**: `PUT /api/settings/server`・`PUT /api/settings/auth` は操作者を本文の JSON を読んだ後に引いていたので、本文を待つ間に別の要求が `localDesktop` の grant を失効させると、認可済みの変更が操作者なしで監査に残った。両方とも本文を読む前に要求のヘッダーから確定する。検証: 本文の最初の poll の後に grant を失効させてから本文を流しても、監査の操作者は `localDesktop`。反証: auth の側を本文の後に引く形へ戻す → 操作者が空で落ちる（server の側は LAN の入れ替えが要るのでルーターのテストでは組めず、同じ形の変更として扱う）。
  - **(3) 予約名のアカウントがある間は初期化後の `localDesktop` を発行しない（Copilot、fail closed）**: 起動時の警告だけでは、同じ名前のアカウントと発行したセッションの操作を監査で区別できないまま発行していた。初期化後の grant の条件（status と発行で共有の 1 つの関数、G10）に「予約名のアカウントが無い」を足し（`local_grant::has_reserved_accounts`）、status は `false`、発行の要求には前段で別の名前のアカウントに移って消すよう伝える `409` を返す（トークンは出さない。この PC からの要求だけに答え、LAN の peer には条件の `403` のまま。kind は banto と同じく percent decode して比べる）。条件は要求のたびに読むので、該当のアカウントを消せば再起動なしで開く。未初期化の間はアカウントが無いので変わらない。起動時の警告は残し、解消するまで発行しないことを書き足した。反証: 条件から外す → status が `true` で落ちる。
- **持ち越し**: フロント（`isTauri()` の判定・grant に自動で入る・デスクトップ専用の設定の非表示・`/api/settings/*` を使う画面）は B2-2。`localDesktop` のトークンは LAN の listener の上でも使える（`AuthState` は listener を入れ替えても続く 1 つの状態。発行を受けられるのは同じ PC のプロセスだけなので、トークンを持っている時点で同じ PC の内側にいる）。

## 6. リスク

**並行性と原子性**

- 起動時の競合: OS 起動直後でサービスが StartPending のときにシェルが起動 → 遷移中は fallback と「再試行」。最後は A1 の named mutex（Session 0 越えは `OpenMutexW` で確定済み）。
- 排他の単位は DB だけ: 解決した `data.dir` が同じだと二重書き込みを防げない既知の制約は残る（全 host が同じルートを使えば実害なし。決定 11）。
- KeyStore の書き込み: DB の `HubRecord` とキーファイルは 2 段の書き込み。片方だけ残ったときの既存 bootstrap の扱いを確認する。孤児キーは起動時に掃除しない（害が無い）。
- 停止の予算: サービスの停止は最終 flush を含む。SCM の既定の待ちに収まるよう PRESHUTDOWN と wait_hint を報告する。
- 上書きインストール中の欠測: 止めて置換して再開する間は収集が止まる（`collection_stopped` が残るので許容）。migration の失敗はサービスが起動失敗の終了コードで止まり、ログで案内。

**セキュリティ**

- **DPAPI machine スコープ**: 同じ PC 上のファイルを読めるすべてのプロセスとユーザーが復号できる。守れるのは別の PC へのコピーとオフラインの盗難だけ。**本当の境界はファイルの ACL**。VM の複製先でも復号でき、OS の再インストールでキーを失う（再発行が要る）。OS キーリング（ユーザースコープ）より広いことを明記する。
- **loopback grant の範囲**: peer が loopback なら誰でも発行を受けられる（多人数ログオン、同じ PC の他のアプリ）。**DNS rebinding** 対策で Host が loopback であることの確認を必須にする（hub の試運転 grant も同じ露出を持つので同時に見直す価値がある）。同じ PC の reverse proxy の前に置かない。
- **LAN 公開との関係**: サービスの既定は loopback だけ（`banto-serve` の `0.0.0.0` 既定を本番に持ち込まない）。LAN の listener からの要求には grant を出さない。閲覧公開とログイン不要モードの排他規則はサービスでも同じ判定。サービス host ではログイン不要モード自体を `local_grant` に置き換えることも検討。→ **B2-1 で決めた: REST ではログイン不要モードを読むだけ（変更は `400`）、サービスでは `local_grant` を使う**。
- **LocalSystem による任意パスへの書き込み**: アプリの admin が `data.dir` やバックアップの保存先を変えると権限昇格の経路になる（決定 11）。
- 未署名の配布物: SmartScreen の警告は既知の制約（hub の 2026-08-12 決定と同じ）。

**運用**

- 既存の Tauri バンドル（currentUser）と新しい PerMachine インストーラが二重に入りうる。旧版のアンインストールを案内するか PREINSTALL で検出する。
- ログのローテーションと保持日数（72h soak で確認）。
- サービス接続時はシェルが REST にしか依存しないので、Tauri 専用の機能（Acrylic、フォルダを開く）は使えない（仕様として明記）。
