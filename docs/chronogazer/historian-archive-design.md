# ヒストリアンの 2 段目の保存（締めた日の Parquet と集計）の設計

作成日: 2026-11-24

関連: [#1306](https://github.com/tyaro/banto-industrial/issues/1306)（この設計の検討と測った数字）、[#1232](https://github.com/tyaro/banto-industrial/issues/1232)（帳票）、[#725](https://github.com/tyaro/banto-industrial/issues/725)（警報の置き場）、[#1323](https://github.com/tyaro/banto-industrial/issues/1323)（記録計のメモ）、[#1324](https://github.com/tyaro/banto-industrial/issues/1324)（Hub との接続を OPC UA に）、[#1253](https://github.com/tyaro/banto-industrial/issues/1253)（Hub の記録の保持の期限）、[記録計要件](recorder-requirements.md) §3.4・§3.5、[トレンドの設計](trend-design.md)

## 1. 目的と範囲

ChronoGazer（記録計）が、収集した値を**年単位で**残し、長い期間のトレンドと帳票を軽く読めるようにする。今の時系列の保存（banto-tstore、SQLite の 1 日 1 ファイル）は置き換えず、その後ろに 2 段目を足す。

- 対象: 締めた日の生の値の書き出し（Parquet）、1 分・1 時間の集計、読み分けの規則、締めた日が後から変わったときの扱い、保持と移す、出来事（警報・メモ）の受け皿、外部への出力の境目。
- 対象外: 帳票の中身（#1232）、警報サーバーの中身（#725）、メモの画面（#1323）、OPC UA のクライアント（#1324）、外部の DB への出力の道具（§9）。

## 2. 現場の要求（2026-11-24 オーナーから）

- 現場によっては 1〜5 年残したい。長い場合は外部の NAS に置く。年に一度ポータブル HDD に移す現場もある。
- 前の SCADA では、SQLite の 1 つのファイルに 1 年分がたまって重くなった。そのため PostgreSQL に入れることが多かった（ほかのシステムと SQL でつなぐためではない）。
- DB のバックアップで控えると、後から CSV で欲しいと言われたときに面倒だった。
- SCADA で長い期間のトレンドを開くと、PC が固まるのが問題になった。
- 長く要るのはアラーム・実績・計装値。デジタルツインを考えると、過去の値はなるべく残したい。

今の tstore は 1 日 1 ファイルなので、「1 つのファイルが重くなる」は起きない。足りないのは**圧縮**と**長い期間の読み方**の 2 つで、そこを 2 段目（§4）と集計（§5）で埋める。

## 3. 決定（オーナー決定 2026-11-24）

| #   | 決定                                                                                                                                                                    |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | 2 段目（生の値の書き出し）は要る。締めた日を **Parquet** に書き出す。作ったら変わらないファイルなので、NAS・HDD へはコピーするだけで移せ、アプリが無くても読める        |
| D2  | 集計は**収集側**で作る（帳票専用にしない）。1 分ごと・1 時間ごとの 2 段。長い期間のトレンドと帳票の両方が使う                                                           |
| D3  | 長く残す対象は、全部のタグを既定で残し、**外す印**を付けられるようにする                                                                                                |
| D4  | 外部の DB（PostgreSQL など）への出力は**記録計の本体の外**に置く。本体が約束するのは「完了の印が付いた Parquet」まで                                                    |
| D5  | 締めた日が後から変わるとき: データはやり直せるように（指紋が合わなければ作り直す）、帳票は勝手に変わらないように（印を出して人が決める）。§7                            |
| D6  | 記録の持ち主は **ChronoGazer**。部品は共通の crate に置き、最初は ChronoGazer だけで有効にする。**Hub は持っても短い期間だけ**                                          |
| D7  | 値とは別に**出来事**（警報・メモなど）の形を最初から用意する。記録計は確認（ack）の要らない上下限だけの警報を持ち、運転の警報は警報サーバー、Hub では判定しない（#725） |

## 4. 全体の形

```text
収集 ──► 1 段目: tstore（SQLite、1 日 1 ファイル）── 直近の値・今日のトレンド
              │
              │ 締める（D 日を翌日 1 時に。§4.1）
              ▼
         2 段目: 締めた日の Parquet（生の値）＋ 1 分・1 時間の集計（Parquet）＋ 完了の印
              │
              ├─► 長い期間のトレンド・帳票（集計から読む）
              ├─► CSV の出力（ChronoGazer の画面から、控えたファイルも含めて）
              └─► 外部の道具（DuckDB・Python・外部の DB への出力。本体の外）
```

部品は新しい共通の crate（仮の名前は `banto-tarchive`）に置く。tstore（書く）・tsquery（読む）と同じく、Hub と ChronoGazer のどちらからも使える形にするが、有効にするのは ChronoGazer だけ（D6）。

### 4.1 締める時刻

- D 日を締めるのは、**翌日の 1 時**（猶予 1 時間、定数）。NTP の補正などで少し戻った時計の書き込みは、この猶予の間に D 日のファイルへ入り終わる。
- 締める処理は、日付が変わるたびに走る今の保持期間の削除（`chronogazer_core::retention`）と同じ場所から、別のタスクとして呼ぶ。起動の時にも、締め残した日（完了の印が無い・指紋が合わない日）を拾う。
- 書き出しは収集を止めない。1 日分の書き出しと集計で約 2 秒（§11）。

### 4.2 ファイルの形と置き場

- **生の値は横持ち**（1 行 = 1 時刻、列 = タグ）の **zstd** の Parquet。測った限り SQLite の約 1/11 で、縦持ちより 4 倍小さい（§11）。
- **tstore の 1 日・1 ファイル・1 グループと 1 対 1**にする。構成の変更で tstore のファイルが連番で分かれたら、Parquet も同じく分かれる。列の組が途中で変わる問題は起きない。
- **ファイルだけで意味がわかるようにする**: 列名はその日のタグ名、Parquet の key-value のメタデータに、タグの id・名前・単位・型・グループ・元のファイル名を入れる。何年か後にアプリやタグの登録が無くても読める（tstore の `tstore_columns` の考え方と同じ）。
- 集計は小さい（1 時間で 1 日 0.19 MB）ので**縦持ち**（時刻・タグ id・統計量の列）でよい。
- 置き場は ChronoGazer のデータの置き場の下に、`archive/<年>/<月>/` の形で日付ごとに置く（名前は実装の時に決める）。

### 4.3 完了の印

- Parquet と集計を一時の名前で書き終えてから名前を替え、最後に**完了の印**（小さな JSON）を書く。印が無いファイルは読み手が使わない。
- 印に持つもの: 元の tstore のファイル名と**指紋**（大きさ・更新時刻・行数・`ptime` の最小と最大）、書き出したファイルの一覧と大きさ・ハッシュ、書いた版、書いた時刻。

## 5. 集計

- **1 分ごと**（数日〜数か月のトレンド用）と **1 時間ごと**（年単位のトレンドと帳票用）の 2 段。
- タグごとに持つ統計量: 最小・最大・平均・最初・最後・件数（欠測を除く）。
- **積算**: #1232 の「集計の種類（平均か積算か）」をタグの属性として持つ。カウンタは区間の差分（巻き戻りを考える）、流量などの率は時間で足し合わせた値。属性の置き場は、しきい値と同じく記録計の側の設定（`recorder_tag_settings` の考え方）にするかを実装の時に決める。
- bool のタグは、区間の中で 1 だった割合と、切り替わりの回数を持つ（運転時間の積算に使える）。
- 1 時間の集計は、今の日報の読み出しの口（`GET /api/collect/daily-report`、1 時間ごとの最小・最大・平均・件数）の裏づけにも使える。
- 今日（締める前）の分は、tstore の生の値からその場で集計する（1 日分なら軽い）。

## 6. 読み分けの規則

日ごとに次の順で決める。書き出しが遅れても失敗しても、読む側は破綻しない。

1. 有効な完了の印がある日 → 2 段目（Parquet・集計）
2. 印が無いが tstore のファイルがある日 → 1 段目（SQLite）
3. どちらも無い日 → 欠測

長い期間のトレンドは、表示の幅に合わせて読む先を替える（目安: 数時間までは生の値、数日〜数か月は 1 分の集計、それより長いものは 1 時間の集計。境目は実装の時に測って決める）。

## 7. 締めた日が後から変わったとき（D5）

tstore は時計が戻ると、過去の時刻を上書きする（壁時計を正とする upsert、`banto-tstore` の lib.rs 冒頭）。なので締めた日も変わりうる。

- 小さな巻き戻り（NTP の補正）は、締める時刻の猶予（§4.1）で吸収する。
- 完了の印の**指紋**（§4.3）を、締める処理のたびに、tstore のファイルが残っている日について見直す。合わなくなった日は、Parquet と集計を作り直す。**tstore のファイルが残っている間は tstore が正**。
- tstore のファイルが保持の期限で消えた後は、**Parquet が正で、もう変わらない**。
- **完成した帳票は書き換えない**。元のデータが後から変わった日を含む帳票には「元のデータが後から変わった」印を出し、作り直すかは人が決める（帳票の側の約束。#1232 の設計に引き継ぐ）。

## 8. 保持と移す

- **tstore（1 段目）**: 今の保持期間（既定 90 日、設定できる）のまま。ただし、**完了の印が無い日は消さない**（書き出す前に消えないように）。今の「書き手が開いている日付は消さない」と同じ形の除外にする。
- **Parquet（2 段目）**: 年単位の保持期間を別に持つ（既定は無期限か年数かは実装の時に決める）。
- **外す印**（D3）: 外したタグは Parquet と集計に載せない。tstore には今までどおり残る。
- **NAS・HDD へ移す**: 2 段目は手元に書いてから、移す先（NAS のパスなど）へコピーする形をすすめる。SQLite を NAS に置くのは鍵の扱いで危ういが、変わらないファイルならコピーで済む。コピーの失敗は記録に影響させない。移す先を設定で持つか、手順書で案内するかは未決（§13）。

## 9. 外部への出力（D4）

- 本体は外部の DB へ書かない。外部の DB への出力は、完了の印が付いた Parquet だけを読む**別の道具**の役目にする。印が付いたファイルは変わらないので、何度やり直しても同じ結果になる。
- 最初は手順書で足りる（DuckDB の CLI で Parquet を読んで PostgreSQL へ入れる、CSV に出す）。DuckDB は製品に入れない（§11）。需要が固まってから、専用の道具（サービス）にするかを決める。
- 外部の DB に入るのは、早くても翌日。もっと早く外へ流したい現場には、Hub の API・ストリームを使ってもらう。
- ChronoGazer の画面の CSV の出力（§3.5 の期間 CSV）は、2 段目の日も読めるようにする（控えたファイルから期間とタグを選んで CSV にする）。

## 10. 出来事（警報・メモ）の受け皿（D7）

- 値とは別に、**出来事**を 1 日 1 つの Parquet で持つ。完了の印・保持・移すは値と同じ規則。
- 持つもの: 時刻（とメモなら期間）、発生元（記録計の警報・警報サーバー・接続・メモなど）、種類（発生・復帰・確認・記入など）、タグ、値、判定に使ったしきい値、文言、書いた人。
- **記録計の警報**: 今の記録計のしきい値（H・HH・L・LL、#532、`tag_thresholds.rs`）と、そのイベント（§3.5 のイベント一覧。ACK はしない）が、D7 の「確認の要らない上下限だけの警報」に当たる。これを出来事として長く残す。トレンドの管理線（7a）との関係（管理線を設定値に使うか）は #725 で決める。
- **運転の警報**: 警報サーバー（#725）。その履歴を ChronoGazer が受けて長く残すか、警報サーバー自身が同じ形の Parquet を書くかは #725 で決める。どちらでも、この節の形を使う。
- **メモ**: #1323（トレンドの上の付箋）。出来事の 1 種類として持つ。
- 今の出来事（接続の切断と復帰、収集の開始と停止など）も同じ形に乗せる。

## 11. 測った数字（2026-11-24、#1306）

製品のコードに入れずに測った。合成データ（300 タグ × 1 秒 × 31 日、値は乱数）なので、**圧縮率は実データの代表ではない**。時間は OS のキャッシュに載った状態のもの。詳細は [#1306 のコメント](https://github.com/tyaro/banto-industrial/issues/1306#issuecomment-7123986457)。

| 測ったこと                         | 結果                                                                                                  |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 1 日分の大きさ                     | SQLite 177.5 MB、Parquet 横持ち zstd 15.9 MB（約 1/11）、縦持ち zstd 68.5 MB                          |
| 1 日分の書き出しと集計             | 横持ち zstd の書き出し 0.53 秒、SQLite の読み 1.32 秒、1 分・1 時間の集計 0.17 秒                     |
| 月報（31 日 × 300 タグ）           | SQLite の生の値から 55.9 秒、1 時間の集計から 0.022 秒（Rust）                                        |
| 1 タグ × 31 日を 1000 区間に       | SQLite の生の値から 3.90 秒、1 分の集計から 0.11 秒（Rust）                                           |
| 集計の大きさ                       | 1 分は 1 日 6.8 MB、1 時間は 1 日 0.19 MB                                                             |
| ビルド・バイナリ（空から release） | rusqlite だけ 17.5 秒 / 1.95 MB、+parquet・arrow 67.5 秒 / 7.29 MB、+duckdb 約 10 分 50 秒 / 46.96 MB |

ここから決めたこと:

- 製品の読み書きは Rust の `parquet` クレートだけで行い、**DuckDB は製品に入れない**（+40 MB・+9 分に見合わない）。DuckDB は、利用者がアプリの外で読む道具として案内する。
- 生の値は横持ちの zstd（§4.2）、集計は縦持ち（§5）。

## 12. 段取り（banto v8 の後）

1. 共通の crate の骨組み: Parquet の書き出し（横持ち・メタデータ）・完了の印・指紋・読み分けの判断（純関数と単体の試験）。
2. 集計（1 分・1 時間）の作成と読み出し。積算の属性。
3. ChronoGazer の締める処理（翌日 1 時・起動時の拾い直し・指紋の見直し）と、tstore の保持の削除が印の無い日を残すこと。
4. 長い期間のトレンドの読み先の切り替え（§6）と、日報の口の裏づけ（§5）。
5. 期間 CSV の 2 段目への対応（§9）。
6. 出来事の Parquet（§10）。
7. 外部の道具の手順書（DuckDB で読む・CSV にする・PostgreSQL へ入れる）。

各段は PR を小さく分ける。実データでの圧縮率と、冷えたディスクからの読みの時間は、1〜2 の段で測り直す。
