## 1. 目的と範囲

ChronoGazer のトレンドを、記録計としての使い方（時刻の軸、実時間と過去の連続、多数のペン）に合う形で作り直し、temp-scada（SCADA）の画面の中でも同じ部品と同じ問い合わせの口で使えるようにする。

- 対象: 監視（リアルタイム）・ヒストリカル・ハイブリッドのトレンド、固定グループのトレンド画面と自由トレンド画面、ペンの表示属性、SCADA との共通の単位。
- 対象外（別の部品として後で設計する。§7）: 時間ごとの集計の棒グラフ（目標・実績・予測、累積）、デマンド監視。
- 対象外（今の要件のまま）: 汎用の画面エディタ（[記録計要件](recorder-requirements.md) §7）。統計表示（移動平均・σ・ローソク足）は[画面改善案](chronogazer-ui-improvement-proposal.md) §3.3 の検討中のまま、ここでは決めない。

## 2. 決まったこと（2026-11-20 オーナー決定）

1. **トレンドのチャートは banto-industrial 側で作る。** banto の `LineChart`（`@banto/charts`）は使わない。
   - 理由: banto の `LineChart` は横軸が点の番号（表示範囲も番号の窓、`core/viewport.ts`）で、点を等間隔に置き、縦軸は全系列で共通。記録計のトレンドは、欠測や間隔の違う値を時刻どおりに置き、メモリの細かい直近の値と DB の間引いた過去の値をつなぎ（ハイブリッド）、系列ごとの縦軸・2 軸・管理線の色替え（#1231）を持つ。これは banto の汎用チャートの性質を変える変更になり、banto の他の使い道（業務アプリの集計グラフ）には今の形の方が合う。
   - banto が公開している純粋な関数とテーマは使う（`linearScale`・`niceTicks`・`linePathSegments`・`seriesColorVar`・`--banto-chart-N` など）。二重に持つのはチャートの組み立てだけにする。
   - 「重複実装は banto に寄せる」方針の例外として扱う。記録計に特有の性質（時刻の軸・ハイブリッド・SCADA の要件）が理由。
2. **トレンド画面を 2 種類に分ける**（現場の分け方に合わせる）。
   - **固定グループのトレンド**: 今の表示グループ（[記録計要件](recorder-requirements.md) §3.2）。定義を変えるのは editor 以上。運転員は期間・送り・拡大・カーソルを操作するだけで、定義は変えない。
   - **自由トレンド**: 登録されたタグから、運転員がペンを選び、線の属性を変え、名前を付けて保存する。
3. **自由トレンドは全員で共有する名前付きのものにする**（利用者ごとにしない）。全員が開けて、変えられる・消せるのは作った人と editor 以上。壁掛けの端末（認証を無効にした表示専用）でも、保存されたものを開ける。

## 3. 2 種類の画面

| 項目             | 固定グループのトレンド                          | 自由トレンド                                                       |
| ---------------- | ----------------------------------------------- | ------------------------------------------------------------------ |
| ペンの組の持ち主 | 表示グループ（`display_groups`）                | 自由トレンドの保存（新しい表。§5）                                 |
| 定義を変える人   | editor 以上（表示グループのページ）             | 作った人と editor 以上（トレンドの画面の中で）                     |
| 新しく作る人     | editor 以上                                     | viewer 以上（ログインしている全員。§9 Q1）                         |
| 開ける人         | viewer 以上・認証無効の端末                     | 同じ                                                               |
| 運転中の操作     | 期間・送り・拡大・縮小・日時指定・カーソル 2 本 | 同じ。加えてペンの選び直しと線の属性の変更（保存するまでは下書き） |
| 上限             | 1 グループ 16 ペン、グループは 36（§6）         | 1 つ 16 ペン、保存は全体で 200 まで（§9 Q2）                       |
| 描く部品         | 共通のトレンドの部品（§4）                      | 同じ                                                               |

- 2 つの画面の違いは「ペンの組をどこから受け取るか」と「だれが保存できるか」だけで、描く部品・ペンの属性の語彙・問い合わせの口は同じものを使う。
- 自由トレンドの下書き（保存前の変更）は端末ごとに持ち（localStorage）、保存しないまま閉じれば消える。
- 固定グループのトレンドで運転員が変えた期間などは、今の時間窓と同じく端末ごとに持ち、グループの定義には書かない。
- 固定グループのペンの組を元に自由トレンドを作る（「この組を自由トレンドとして保存」）は入れる。逆向き（自由トレンドを表示グループにする）は editor の操作として後で考える。

## 4. 部品の作り

### 4.1 置き場所

- 描く部品は共通のパッケージ `packages/trend`（§9 Q3）に置く。ChronoGazer の監視・ヒストリカル・自由トレンドと、temp-scada の画面の両方がこれを使う。`pnpm-workspace.yaml` に `packages/*` を足す。
- temp-scada からは、banto のパッケージと同じく GitHub のパスとタグで参照する（`github:tyaro/banto-industrial#<tag>&path:packages/trend`）。
- パッケージは表示だけを持ち、データの取り方は持たない（取り方は利用側が関数で渡す。§4.3）。ChronoGazer の `collectAdmin.ts`・Tauri の呼び出しや、SCADA の History API の型を部品の中に入れない。

### 4.2 層

1. **時刻の軸と表示範囲**: 表示範囲を時刻（UTC のミリ秒、`[startMs, endMs)`）で持つ。拡大・縮小・パン・日時指定・期間の候補（10 分・30 分・1・2・4・8・12 時間・1 日・7 日・31 日）・前へ・次へは、この範囲を変える純粋な関数にする。「追従中」（右端が今）かどうかも状態として持つ。
2. **ペンと縦軸**: ペンごとに縦軸の最小・最大（未設定なら工学値レンジ → データの範囲の順に決める。データの範囲には管理線の値を含める）と、左右どちらの軸か（2 軸）を持つ。目盛りは左右それぞれ 1 本ずつで、その側の先頭のペンの範囲で描く。ほかのペンは自分の範囲で描き、凡例に範囲を出す。
3. **データの窓**: 表示範囲に要る区間（bins）を利用側の取得関数で読み、区間の最小・最大で包絡（MIN/MAX）を描く。直近はメモリのリングバッファ（監視の現在値）から足す。§8 のハイブリッド。
4. **描画**: まず SVG。描画の層は差し替えられる形にし、16 ペン × 2000 区間で重ければ Canvas に替える（[plan.md](../plan.md) の性能対策の第 2 段）。
5. **重ねる表示**: 管理線（HiHi・Hi・Lo・LoLo）と、越えた区間の線の色替え、bit の帯（タイムチャート）、カーソル 2 本と凡例の値、イベントの印（後で）。

### 4.3 データの受け取り

- 部品は「時刻の範囲・ペン・区間の数」を渡すと区間ごとの値を返す関数（非同期・取り消し可能）と、現在値の流れ（購読）を受け取る。
- **共通の契約は「区間の始まりの時刻・最小・最大」だけにする**（今の `GET /api/collect/history` の `HistoryPoint { tMs, min, max }` と同じ形）。最小・最大が両方 `null` の区間は欠測で、線をつながない。平均・件数は共通の契約に入れない（トレンドは MIN/MAX の包絡で描くので要らない。平均・件数は日報・CSV が `read_binned_stats` から別に読む）。統計表示（移動平均など）を後で足すときに、要る値を契約に足す工程を別に設ける。
- ChronoGazer は `GET /api/collect/history`（Tauri は同じ口）と監視の現在値のポーリングをつなぐ。SCADA は自分の History API（`banto-tsquery` の上）と Hub の購読をつなぐ。
- 区間の数は表示の横幅（ピクセル）から決める（幅 ÷ 1 前後、上限 2000）。

## 5. ペンの属性の語彙

表示グループのペン（今は `tagId` と `colorSlot` だけ）と自由トレンドのペンに、同じ語彙を足す。項目を足すのは「語彙を広げる」ことで、[記録計要件](recorder-requirements.md) §3.7.3 の閉じた項目の集合の考え方のまま、自由な式や任意の HTML は持たない。

| 項目       | 値                                                                      | 既定             |
| ---------- | ----------------------------------------------------------------------- | ---------------- |
| 色         | 系列色の枠 1〜16（テーマに追従。§9 Q4）                                 | ペンの位置 + 1   |
| 線種       | 実線・破線・一点鎖線・二点鎖線・線なし                                  | 実線             |
| 線幅       | 1〜4 px                                                                 | 1.5 px           |
| マーカー   | なし・丸・四角・三角・ひし形、大きさ 2〜8 px                            | なし             |
| 小数の桁   | 0〜6                                                                    | タグの設定       |
| 凡例の名前 | 文字列（64 文字まで）                                                   | タグの名前       |
| 単位       | 文字列                                                                  | タグの単位       |
| 縦軸       | 最小・最大、左・右                                                      | 工学値レンジ、左 |
| 管理線     | 有効・無効。値はタグのしきい値（H/HH/L/LL）を使うか、ペンで上書きするか | 無効             |
| bit の表し | 段差・帯（太さ。縦の位置は下から自動で積む、§10 の 7c）                 | 段差             |

- 管理線を有効にしたペンは、HiHi・Hi・Lo・LoLo の線を引き、越えた区間の線の色を変える。値の既定はタグのしきい値（`tag_thresholds`）で、ペンで上書きした値は表示だけに使い、しきい値のイベント（§3.5）は変えない。
- 今の「しきい値の帯を選んだ 1 ペンだけに描く」は、管理線の表示に置き換える。

## 6. 上限

| 項目                  | 今                           | 新しい上限                                        |
| --------------------- | ---------------------------- | ------------------------------------------------- |
| 1 表示グループのペン  | 8（`MAX_PENS_PER_GROUP`）    | 16                                                |
| 表示グループの数      | 16（`MAX_DISPLAY_GROUPS`）   | 36。グループの束（切り替えの単位）を足す（§9 Q5） |
| 履歴の口の 1 回のタグ | 8（`HISTORY_MAX_TAGS`）      | 16                                                |
| 履歴の口の点の合計    | 8000（`HISTORY_MAX_POINTS`） | 32000（16 ペン × 2000 区間）。応答はおよそ 1.3 MB |
| 1 系列の区間          | 2000（`HISTORY_MAX_BINS`）   | 変えない                                          |
| 期間                  | 31 日                        | 変えない                                          |

- [画面改善案](chronogazer-ui-improvement-proposal.md) §3.4 の「1 グループに 32 ペンを登録し、1 面に 16 ペン」は検討中のまま採らない。まず 16 にそろえ、32 は使ってみてから決める。
- **期間 CSV と日報の上限は 8 本のまま変えない。** 今は履歴・期間 CSV・日報が同じ `HISTORY_MAX_TAGS` を使っている（Rust の `history.rs`・`export.rs`・`daily_report.rs`、画面の `historyLogic.ts`・`dailyReportLogic.ts`）。16 ペン化の PR で、期間 CSV と日報にそれぞれの定数（`EXPORT_MAX_TAGS = 8`・`DAILY_REPORT_MAX_TAGS = 8`）を分け、トレンドの履歴の口だけを 16 に上げる。日報を 8 本に留めるのは、1 枚の横幅（24 行 × タグの列）に収めるため。
- **9 本以上のペンを持つグループを CSV・日報に出すときは、黙って落とさない。** 画面に「CSV・日報は 8 本までです。出すペンを選んでください」と出し、ペンのチェックの一覧（既定はグループの先頭から 8 本）から選ばせる。8 本を超えては選べない。口に 9 本以上を渡したときは、今と同じく誤りで断る。
- 1 時間を超える読み出しの同時 2 本・待ち 30 秒（#1207 PR1）は変えない。点の合計を 4 倍にするので、16 ペン × 31 日の読み出しの時間を実データで測ってから上限を確定する。

## 7. 棒グラフ・デマンド監視・小さな実時間トレンド

- **時間ごとの集計の棒グラフ**（目標・実績・予測、当日と前日、累積、目標の線）と**デマンド監視**（30 分の枠、目標・実績・予測・警報の線、残り時間）は、トレンドの拡張ではなく**別の部品**にする。時刻の軸・目盛り・テーマはトレンドの部品と同じ土台（§4.2 の 1）を使い、集計は日報と同じ `read_binned_stats` の土台に乗せる。
- 目標・予測の値の出どころと、デマンドの業務の決まり（時限・警報の判定）は SCADA の中身として扱う。部品は industrial に置き、画面の組み立ては SCADA 側で行う。設計は別に行う（この文書の段取りに入れない）。
- 機器の小窓の中の小さな実時間トレンド（PV・SV・MV の 3 本）は、トレンドの部品の小さい表示（追従だけ・凡例を畳む）で賄う。

## 8. ハイブリッド

- 1 つの画面で、追従中は右端を今に合わせて動かし、左へパン・縮小すると過去へ途切れずにつながる。右端へ戻す（または「最新へ」）と追従を再開する。追従をやめている間も収集・記録は止めない。
- データは 2 つを合わせる。
  - **直近**: メモリのリングバッファ（現在値の流れ）。長さは追従の窓の 2 倍か 30 分の長い方。
  - **過去**: 履歴の口の区間（最小・最大）。表示範囲が変わったら、止まってから 200 ms 待って読み直し、前の読み出しは取り消す。読んだ区間は範囲と区間の幅ごとに少しだけ覚えておく。
  - **つなぎ目はペンごとに決める。** ペンごとに、リングバッファが途切れなく持っている範囲の始まり（購読を始めた時刻、または最後に途切れた後の最初の値の時刻）を `liveFrom` とする。`liveFrom` より前は履歴の区間で、`liveFrom` 以後はリングバッファで描く（リングバッファの値を同じ区間の幅で最小・最大にまとめる）。「履歴の最後の区間」を境にしない。履歴の最後の区間は、記録がまだ保存されていない最新の時刻や、そのタグの欠測で、リングバッファの値を隠してしまうため。
  - `liveFrom` は「いまリングバッファが現に持っている範囲の始まり」で、購読を始めた時刻に固定しない。古い値が追い出されたら、`liveFrom` もそれに合わせて進める（追い出した範囲は履歴で描く）。
  - **境界をまたぐ区間は取り直す**: 履歴の区間が `liveFrom` をまたぐとき（例: 区間が 10:00〜10:05、`liveFrom` が 10:03）、区間の始まりだけを見て履歴を残すと 10:03 以後の値が混ざり、丸ごと落とすと 10:00〜10:03 の値が消える。この区間は履歴を `[区間の始まり, liveFrom)` の範囲で読み直して最小・最大を出し、同じ時刻の値を両側で集計しない。
  - **重ねない**: 両方に値がある時刻（`liveFrom` 以後の履歴）は、リングバッファだけを使い、2 本の線にしない。
  - **本当の欠測は線でつながない**: 履歴の区間が欠測（最小・最大とも `null`）、またはリングバッファに値が無い（品質が悪い・現在値が `null`・購読が途切れた）時刻は、線を切る。つなぎ目そのもの（`liveFrom` の前後）では、どちらにも値があれば線をつなぐ。
  - 受け入れ（ハイブリッドの PR で試験にする 5 つ）: (1) **末尾が未保存** — 履歴の最後より新しい値がリングバッファにだけあるとき、その値が描かれる。(2) **欠測** — 履歴の途中とリングバッファの途中の欠測が、どちらも線を切って描かれる。(3) **重複** — `liveFrom` 以後の時刻が履歴とリングバッファの両方にあるとき、線が 1 本だけ描かれる。(4) **境界をまたぐ区間** — 履歴の区間が `liveFrom` をまたぐとき、`liveFrom` より前の値は履歴から、後の値はリングバッファから、どちらも 1 回だけ集計される。(5) **追い出し** — リングバッファの古い値が追い出された後も、追い出した範囲が履歴で欠けずに描かれる。
- 実装の細部（4a で決めた。2026-11-20）: 境界の区間の読み直しが届く前は、その区間を欠測にして線を切る（履歴のまま残すと二重に数え、落とすと縦軸がずれる。読み直しは 200 ms ほどで届く）。リングバッファの追い出しは、持っている長さが保持時間の 1.1 倍を超えたときだけ保持時間まで一度に行う（`liveFrom` がサンプルのたびに動いて読み直しが毎秒走るのを避ける）。リングバッファは履歴の区間の幅をサンプル間隔の 1.5 倍以上になるまで整数倍に広げた格子でまとめる（間隔のゆらぎで値の無い区間ができて線が細切れにならないように）。失敗した読み直しは、要求が変わる（`liveFrom` が進む・履歴を読み直す）まで繰り返さない。
- 追従中の 1 時間以下の窓は今の監視と同じで、初期窓を履歴で埋めた後は現在値で伸ばす（#1207 PR1 の「1 時間以下は絞らない」のまま）。

## 9. 細部の決定（2026-11-20 オーナー決定。推奨どおり）

- **Q1 自由トレンドを新しく作れる人**: viewer 以上（ログインしている全員）。運転員が使うものなので。認証を無効にした端末は開けるだけで、作れない（だれが作ったかを残せないため）。
- **Q2 自由トレンドの保存の数**: 全体で 200 まで。名前は重ならないようにする。
- **Q3 パッケージの名前**: `packages/trend`（npm の名前は `@banto-industrial/trend`）。
- **Q4 9 本目以降の色**: banto の系列色は 8 枠（`--banto-chart-1`〜`8`、`MAX_CHART_SERIES = 8`）。industrial のテーマに `--bi-chart-9`〜`16` をライト・ダークの両方で足す。線種の違いと合わせて見分ける。

     - 自由トレンドのペンが使うタグの削除は、表示グループと同じ所（`delete_tag_unless_referenced`）で自由トレンドの名前つきで断る（欄 `freeTrends`。両方から使われていれば両方の誤りを並べる）。
     - REST `/api/free-trends`（GET 一覧・POST・GET/PUT/DELETE `{id}`）はキーを通す集まりに入れ（読み取りのため）、OpenAPI に載せる。Tauri は `free_trends_list`・`_get`・`_create`・`_update`・`_delete`。フロントは型と呼び出しの薄い層 `lib/banto/freeTrendsAdmin.ts` だけ。監査は `resource: "free_trends"`。
