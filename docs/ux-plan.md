## 1. T9: 接続単位のシミュレーションモード

**目的**: 実機 PLC がなくても、接続〜収集〜外部 IF（REST/WS/MQTT/gRPC）〜
書き込みゲートまでの全経路を開発・検証できるようにする。

**設計決定（2026-08-06）**:

- **フラグの置き場所**: `plc_connections` に `simulation` 列（既定
  `false`）を追加する（マイグレーション1本）。`protocol` とは独立 —
  「開発→実機の切り替えがチェックボックス1つ」が体験の核であり、
  `protocol: "simulation"` という別プロトコル案は接続の作り直しが
  発生するため不採用
- **方式**: in-process シミュレータ（`banto-plc` の Modbus/SLMP
  シミュレータ、実バイト列）を localhost の実 TCP で起動し、収集
  エンジン・broker・書き込みゲートは**本物と同一のコードパス**を通す。
  「シミュレーションで動いたのに実機で動かない」を最小化する、この
  リポジトリのテスト思想（in-process + 実バイト列）の踏襲
- **値生成**: まずランプ波1種（アドレス毎の単調増加ラップアラウンド、
  T5-4 ソークと同じ手法）。固定値では on_change 系（WS/MQTT）が発火せず
  開発用途に不十分なため。サイン波/ランダムウォーク等のパターン追加は
  需要が出てから
- **事故防止（最重要課題）**: 「本番でシミュレーションのまま運用」を
  防ぐため、(a) 管理 UI の接続一覧・タグモニタに目立つバッジ、
  (b) `GET /api/v1/status` と catalog（`GET /api/v1/tags`）に
  `simulation` を露出（外部クライアントも判別可能）、(c) 起動時ログに
  シミュレーション接続を必ず列挙、の3点を必須とする
- **非スコープ**: スタンドアロンシミュレータ（別 exe 配布）は運用が
  重くなる割に in-process との差分が小さいため、需要が出るまで見送り

**スライス**:

| スライス | 内容                                                                                                                           |
| -------- | ------------------------------------------------------------------------------------------------------------------------------ |
| T9-1     | レジストリ + 収集層: `simulation` 列（マイグレーション）、banto-collect のシミュレータ起動・接続差し替え・ランプ波生成、テスト |
| T9-2     | hub 配線 + UI: status/catalog への露出、起動ログ、管理 UI の接続フォームのチェックボックス + 一覧バッジ、E2E                   |

## 2. T10: ライブタグモニタ

**目的**: 管理 UI に「今の値」を見る画面を追加する。タグ登録直後の動作
確認を、API を叩かずに UI で完結させる。

**設計方針**:

- 既存の WS 購読（`/api/v1/stream`、管理 UI セッションで認証可能）を
  消費する一覧画面。現在値・品質（good/bad/stale の色分け）・時刻を表示
- relay-wright のタグモニタの UI パターンを流用する
- 接続・グループでのフィルタ。シミュレーション接続のバッジ表示（T9 連携）
- 書き込み操作は**付けない**（管理 UI からの手動書き込みは設計 §6-8 の
  将来スライスのまま。モニタは読み取り専用）

## 3. T11: タグの一括登録（連続登録 + CSV インポート/エクスポート）

**目的**: タグの一括登録・構成のバックアップ/複製/レビュー。

**連続登録の追加（2026-08-06 オーナー発案・採用）**: PLC 設計では
基本的に連続領域でデバイスを使用する（例: D3000〜D3099 を一区画として
割り当てる）ため、開始アドレス + 点数 + 名前パターンから連続タグを
一括生成する「連続登録」を T11 に統合する。連続アドレスのタグ群は
収集エンジンの read プランナが元々1回のワード一括読みにまとめる設計の
ため、UX と収集効率が同じ方向を向く。

**設計方針**:

- **共通基盤: 一括登録 API**（連続登録と CSV の両方が使う）。UI から
  1件ずつ `POST /api/tags` を繰り返すと T7 の部分再構成がタグ追加の
  たびに走る（100点で100回）ため、サーバー側に一括 API（検証 →
  all-or-nothing 適用 → 再構成1回）を設ける。実装順は連続登録が先
  （CSV より小さく、基盤 API の最初の消費者として適切）
- **連続登録**: タグ登録フォームに「連続登録」モードを追加。入力は
  名前パターン（例: `temp{n}`、`{n}` は開始番号からの連番）・開始
  アドレス・点数・共通設定（データ型・単位・スケーリング等）。
  アドレスの増分はデータ型から自動決定（i16/u16 = +1 ワード、
  i32/f32 = +2、string = +string_length。ビットデバイス M 等は +1）。
  適用前に生成されるタグの一覧をプレビュー表示する
- エクスポート: 現行タグ定義を CSV でダウンロード。Excel 想定のため
  **UTF-8 BOM 付き**で出力
- CSV インポート: CSV アップロード → 検証結果（行番号付きエラー一覧）を
  先に表示 → 確認してから適用、の2段階（dry-run 必須）。部分適用は
  しない（all-or-nothing、`rebuild`/`apply_config` の規律と揃える）
- CSV 書式は列名ヘッダ付き・タグ登録フォームの項目と1:1対応。接続・
  グループは名前で参照（存在しなければエラー。自動作成はしない —
  暗黙の副作用を避ける）

**スライス**:

| スライス | 内容                                                                                 |
| -------- | ------------------------------------------------------------------------------------ |
| T11-1    | 一括登録 API（検証 + all-or-nothing 適用）+ 連続登録 UI（**実装済み・2026-08-07**）  |
| T11-2    | CSV エクスポート + インポート（T11-1 の一括 API を消費）（**実装済み・2026-08-07**） |

**T11-1 実装メモ（2026-08-07）**:

- API: `POST /api/tags/batch`（`{ tags: TagInput[], dryRun: bool }` →
  `{ ok, dryRun, count, errors: [{ index, fieldErrors }], tags? }`、常に
  HTTP 200 — `ok: false` は「1件以上のエラーで全体拒否」という通常の応答
  であって例外ではないという判断。認証/権限/DB エラーは従来どおり非2xx +
  `ErrorBody`）。実体は `banto_tags::TagService::create_batch`（検証 →
  全件 or 何もしない → 単一トランザクション INSERT）を
  `apps/banto-hub/core/src/rest.rs::tags_batch` が呼び、成功時のみ
  `rebuild` を1回だけ実行する。
- パターン展開（名前パターン・連続アドレス生成）はクライアント側 TS
  （`apps/banto-hub/src/lib/banto/continuousRegistration.ts`）に実装 -
  プレビューに出た内容がそのまま送信内容になる。
- `{n}` の無い名前パターンは入力エラーにせず末尾に連番を付与する判断
  （UI として自然、かつプレビューで確認できるため）。
- ビット指定アドレス（`D100.5` 等）の連続登録は v1 非対応（繰り上げ規則が
  自明でないため）。
- 16進デバイス番号（SLMP の X/Y/B/W/SB/SW/DX/DY）の連続登録も v1 非対応
  （2026-08-07、監査で検出・修正: 10進増分では番号がたまたま10進数字
  だけに見える範囲でガードをすり抜け、16進の桁境界で採番が不連続になる
  静かなバグがあったため、明示的に非対応とした）。
- 運用手順は
  [banto-hub-operations.md §15](banto-hub-operations.md#15-タグの連続登録)
  参照。

**T11-2 実装メモ（2026-08-07）**:

- 新規ファイル `apps/banto-hub/src/lib/banto/tagCsv.ts`（依存なしの純
  関数群、`continuousRegistration.ts` と同じ設計）。RFC4180 の CSV
  パース/シリアライズ（`parseCsv`/`serializeCsv`/`stripBom`）と、タグの
  エクスポート/インポート（`exportTagsCsv`/`parseTagsCsv`）を実装。
- **外部 CSV ライブラリを追加せず自前 RFC4180 実装**（判断: 依存追加は
  この機能のためだけには見合わない。引用符付きフィールド・埋め込み
  カンマ/改行・`""` エスケープの3点で十分小さいため）。不正な入力
  （未終端の引用符など）でも例外を投げず、可能な範囲で読み取ってエラー
  行として報告する設計。
- CSV 列: `connection, group, name, address, dataType, stringLength,
unit, decimals, rawLo, rawHi, engLo, engHi, thresholdH, thresholdHh,
thresholdL, thresholdLl, enabled, writable, tagKind, expression,
retain`（`TagInput` の全フィールドと1:1対応、`collectionGroupId` だけ
  `connection`+`group` の名前参照2列に置き換え）。
- **接続/グループは名前参照、自動作成しない**の決定どおり実装
  （`parseTagsCsv` が名前解決に失敗したら行番号付きエラーを返す）。
- **新規登録専用・upsert 非対応**（T11-1 の一括登録 API 自体が INSERT
  専用のため、CSV インポートもそれを引き継ぐ）。
- **エクスポート直後の再インポートは全行重複エラーになるのが正しい
  挙動**（CSV は新規登録専用のバックアップ/複製用途であり、同一環境への
  再インポートを意図した機能ではないため）。
- UI はタグ登録画面（`apps/banto-hub/src/routes/(app)/tags/+page.svelte`）
  に「CSVインポート」モードを追加（連続登録と同じ「プレビュー → 検証
  (dry-run) → 登録」の2段階フロー）。エクスポートは「一覧」セクションの
  ボタンから（`canWrite` でガードしない — 閲覧者でも実行可）。
- 運用手順は
  [banto-hub-operations.md §16](banto-hub-operations.md#16-タグの-csv-インポートエクスポート)
  参照。

## 4. T12: PLC 接続テストボタン

**目的**: 接続の保存前に疎通確認できるようにする。

**設計方針**:

- 管理 REST に接続テスト API（例: `POST /api/plc-connections/test`、
  保存不要でホスト/ポート/プロトコルを受け取る）
- TCP 接続だけでなく、**実プロトコルで軽い読み出し1回**（SLMP/Modbus
  各クライアントで先頭デバイス1点）まで行う — ポートは開いているが
  プロトコル不一致、という誤設定も検出するため
- タイムアウトは短め（数秒）に固定。結果は成功/失敗 + 失敗理由を返す

**実装メモ（2026-08-07）**:

- API: `POST /api/plc-connections/test`（editor+・CSRF、既存の
  `/api/plc-connections/*` と同じ管理系の流儀）。リクエストは
  `{ protocol, host, port, unitId, simulation, connectionId? }` — 設計時の
  想定に加え `simulation`（フォームのチェックボックスの現在値）を明示的に
  送らせる形にした。理由: 保存済み行の `simulation` を見るだけだと、編集中
  にチェックボックスを ON にしたがまだ保存していない状態を検出できない
  ため。応答は `{ ok, elapsedMs, error: { kind, message } | null }`、常に
  HTTP 200（`ok: false` は「疎通確認の結果が失敗だった」という通常の応答
  であって例外ではないという判断 — T11-1 の一括登録 API と同じ設計判断）。
  `kind` は `"tcp" | "timeout" | "protocol" | "device" | "unsupported"` の
  5分類（運用手順は
  [banto-hub-operations.md §17](banto-hub-operations.md#17-plc-接続テスト)
  参照）。
- **実機 R08ENCPU の SLMP は対象ポートにつき同時1接続まで（実測）への対策**:
  保存済み接続（`connectionId` あり）をテストする際、その接続の broker
  セッションが既に生きていれば新たにダイヤルせず**既存セッション経由で
  読む**（`apps/banto-hub/core/src/broker_glue.rs::HubSessions::handle_for`
  — 新規セッションを起動しない読み取り専用の覗き見として追加）。無ければ
  直接ダイヤルにフォールバックし、この場合と未保存接続のテストの両方で、
  SLMP の失敗メッセージに対象ポートが使用中の可能性がある旨の注意文言を
  付ける。Modbus は同時接続数の制約が緩い機種が多いため常に直接ダイヤル
  するが、失敗時には同種の（軽い）注意文言を付けている。
- **`/api/plc-connections/*` は意図的に OpenAPI（utoipa）の対象外のまま**:
  utoipa がドキュメント化しているのは `/api/v1/*`（機械クライアント向け
  タグ空間 API）のみで、管理系の create/update/delete も元々対象外だった
  ため、この方針を維持した（新規にドキュメント対象を広げなかった）。
- OpenAPI 上記の理由で変更なし。テストは
  `apps/banto-hub/core/tests/t12_connection_test.rs`（Modbus/SLMP 成功・
  失敗、broker 経由の既存セッション再利用、virtual/simulation 拒否、RBAC）。
- UI: 「PLC接続」ページの作成・編集フォーム（共通の `connectionFields`
  スニペット）に接続テストボタンを追加。編集フォームのみ `connectionId`
  を送る。作成/編集で独立したテスト実行状態を持ち、多重クリックを防止。

## 4b. T13: 画面レイアウト刷新（ツリーナビゲーション + ドロワー）

**採用(2026-08-08 オーナー決定)**: FHD 環境で「上に設定フォーム・下に
リスト」の縦積みレイアウトはリストが 300px 程度に潰れて使いづらい
(オーナー指摘)。タグの外部名がそのまま「接続.グループ.タグ」の3階層で
あることを活かし、次の master-detail 構成へ刷新する。

**設計決定**:

- **左ペイン: ツリーナビゲーション**(約260〜300px): 接続 → 収集
  グループの2階層。calc/mem 予約接続・シミュレーションバッジ・タグ数の
  表示。選択で右ペインのリストをフィルタ。GX Works / FA-Server 系の
  「左ナビゲータ + 右詳細」という PLC エンジニアの慣習に合わせる意図
- **右ペイン: 全高リスト**: ツールバー(新規登録・連続登録・CSV・検索)+
  画面全高の BantoGrid(固定ヘッダ)。FHD でリスト表示領域が約3倍になる
- **フォームはドロワー(右スライドオーバー)**(2026-08-08 オーナー決定、
  モーダル・インライン展開は不採用): 縦長フォームと相性が良く、リストの
  文脈が背後に残る。新規登録・行クリック編集・連続登録・CSV インポートの
  全フローを同じドロワーに収める
- **実装の置き場所(2026-08-08 決定)**: banto テンプレート側ではなく
  **まずアプリ側(banto-hub)で実装**し、2番目の消費者(将来の SCADA 等)が
  現れた時点で汎用部品(Drawer・SplitPane・Tree ウィジェット)を
  `@banto/*` へ昇格する — banto-broker が relay-wright W3-A → 共有
  クレート I6 と辿ったのと同じ「1アプリで実証してから抽出」の規律。
  昇格を安くするため、汎用部品は `src/lib/components/` にアプリ固有の
  結合なしで切り出しておく(データを流し込む「接続ツリー」はどのみち
  アプリ側に残る部分なので分離して実装)
- **スコープの護り**: 対象は tags ページと monitor ページの2画面。
  接続・グループの管理ページは現状維持(ツリーからの右クリック作成等は
  需要を見てから)

**スライス**:

| スライス | 内容                                                                                                              |
| -------- | ----------------------------------------------------------------------------------------------------------------- |
| T13-1    | 汎用部品(Drawer/SplitPane/Tree)+ tags ページの master-detail 化(フォームのドロワー化)（**実装済み・2026-08-08**） |
| T13-2    | monitor ページへのツリー適用(ドロップダウンフィルタ置換)+ 仕上げ                                                  |

  一切依存しない）: `Drawer.svelte`（右スライドオーバー、Esc/オーバー
