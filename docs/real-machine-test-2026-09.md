## 1. 事前準備

### 1.1 機材

| 用途        | 機材                | 状態                                                   |
| ----------- | ------------------- | ------------------------------------------------------ |
| A（SLMP）   | 三菱 R08ENCPU       | 利用可。**1ポートあたり1接続**。複数ポート開放済み     |
| B（Modbus） | Modbus TCP スレーブ | **本 PC 上で稼働、`127.0.0.1:502`**（2026-09-01 用意） |

**SLMP で安全に書き込んでよいアドレス**: `D3000`〜`D4999`、`M1000`〜`M2000` 付近。**この範囲を外れないこと。**

Modbus スレーブは本 PC 上の擬似機器なので、書き込み対象の制限は無い。ただし §3.3 の隙間試験では**生のレジスタ値を直接確認・設定できること**が必要なので、スレーブ側にその手段（UI かツール）があることを先に確かめる。

### 1.2 起動（使い捨て構成・原状復帰しやすい）

```bash
cargo build -p banto-hub-core --bin banto-hub
```

バックエンド（DB をスクラッチパッドへ隔離）— 以下の環境変数で `target/debug/banto-hub.exe` を実行:

```
PORT=8722
BANTO_ALLOW_SETUP=1
BANTO_BIND=127.0.0.1
BANTO_DB=<scratch>/hub-smoke.sqlite3
BANTO_HUB_DATA=<scratch>/hub-smoke-data
```

フロント: `pnpm --filter banto-hub dev`（vite 5173、`/api` を 8722 へ proxy）。ブラウザで `http://localhost:5173`。

**後片付け**: ポート 8722 / 5173 のプロセスを kill し、`hub-smoke*` を削除。

### 1.3 ハマりどころ（既知）

- **素の `banto-hub` バイナリは収集停止で起動する**。Web 管理 UI に収集開始ボタンは無い。開始/停止は `POST /api/collection/start`（`RunMode::Configured` = 実機）/ `POST /api/collection/stop`。
- 管理 REST の認証は **localStorage `banto.auth.token` の Bearer** ＋ CSRF 固定ヘッダ **`X-Banto-Client: banto`**（Cookie ではない）。UI に無い操作は、ブラウザの認証済みコンテキストからこの2ヘッダを付けて `fetch` すれば叩ける。
- **収集稼働中のレジストリ変更は 202 で pending queue に入り**即時反映されない。status ページの「Pending changes」で適用するか、**収集停止中に設定を済ませる**。
- monitor のライブ表示は **vite dev が WebSocket を proxy しない**ため「再接続中」になる（開発プロキシの制約で、製品バグではない）。値の確認は `GET /api/v1/values/{external_name}` か status ページで行う。
- 試運転モード（loopback のみ・ログイン不要）を使うと設定作業が速い。**ロックダウン後は元に戻せない**点に注意。
- 管理者セットアップ（`POST /api/auth/setup`）はアカウント作成とパスワード設定を伴うため、**オーナーが実施する**。

## 2. A. SLMP 回帰テスト（#130）— 最優先

**なぜやるか**: #130 は broker の読み書き実行経路を `BrokerSession` trait の裏へ作り替えた。CI では既存テスト23件が無改変で通っているが、**実機の SLMP セッションで従来どおり動くこと**は未確認。

### A-1. 読み取り

1. 収集停止のまま、PLC 接続を作成（protocol = `slmp`、**タッチパネルが占有していないポート**を選ぶ）
2. 収集グループを作成（周期は既定でよい）
3. タグを登録: `D3000`（`i16`）、`M1000`（`bool`）
4. `POST /api/collection/start`（`RunMode::Configured`）で収集開始
5. `GET /api/v1/values/{external_name}` で値を取得

外部名は `{接続名}.{グループ名}.{タグ名}`。

**合格条件**: `q: "good"` かつ `value_source: "real"`。

> `value_source` が `sim` なら実機に繋がっていない。接続設定かシミュレーション設定を見直す。

### A-2. 書き込み

1. `D3000` のタグを **`writable = true`** にする（収集停止中に行うか、pending を適用）
2. API キーを作成（`POST /api/api-keys`）し、**`write:{外部名}` スコープ**を付与（**完全一致**。ワイルドカード不可）
3. 書き込み受付を有効化: `POST /api/write-control/enable`
4. `POST /api/v1/values/{外部名}` で書き込み（API キー認証）
5. `GET /api/v1/values/{外部名}` で読み戻す

**合格条件**: 200 が返り、読み戻した値が一致する。**GX Works 等で実機側の `D3000` も直接確認できるとなおよい**（Hub 内で完結した確認より強い）。

### A-3. 再接続（セッション断からの復帰）

1. A-2 の状態でセッションを切る（ケーブルを抜く、ポートを塞ぐ等）
2. 書き込みを試みる → **失敗すること**を確認
3. 接続を復旧し、しばらく待つ
4. 再度書き込み → **成功すること**を確認

**なぜやるか**: #130 で `ConnState` / backoff / `Err` 契約を作り替えた。「**接続断で Backoff に戻り、復旧後に再びセッションが張られる**」という中核の挙動が実機で効くかを見る。

**合格条件**: 断中は明確なエラー、復旧後は自動で書けるようになる。**エラーのまま復帰しないなら退行。**

### A-4. 読み書きが同一セッションを共有していること

1. 収集を動かしたまま（＝定期的に読み取りが走っている状態で）A-2 の書き込みを数回行う
2. 収集の値が乱れないこと、書き込みが失敗しないことを確認

**なぜやるか**: broker の存在理由は「1接続 = 1セッションを read と write が共有し、ワイヤ上で交錯させない」こと。**R08ENCPU は1ポートあたり1接続**なので、もし read と write が別セッションを張ろうとすれば**2本目が約1秒でタイムアウトして失敗する**。この試験はそれを直接暴く。

**合格条件**: 収集が継続したまま書き込みが成功する。

## 3. B. Modbus 書き込みテスト（#131 / #219）

スレーブは本 PC 上の `127.0.0.1:502`。実機器ではないので、**壊す心配なく境界値まで攻められる**。

### 3.1 接続とタグの準備

1. PLC 接続を作成: protocol = **`modbus-tcp`**、ホスト `127.0.0.1`、ポート `502`、`unit_id` はスレーブの設定に合わせる
2. 収集グループを作成
3. タグを登録（**アドレスは Modbus リファレンス番号**）:

| タグ     | アドレス | 用途                                   |
| -------- | -------- | -------------------------------------- |
| `hr1`    | `40001`  | ホールディングレジスタ（FC6 / FC16）   |
| `hr2`    | `40002`  | 隣接（結合の確認）                     |
| `hr_gap` | `40005`  | 離れた番地（**隙間試験**）             |
| `coil1`  | `00001`  | コイル（FC5 / FC15）                   |
| `di1`    | `10001`  | ディスクリート入力（**書けない確認**） |

> **ここで確かめること**: `di1`（`10001`）や入力レジスタ（`3xxxx`）に **`writable = true` を付けようとすると登録が拒否される**（オーナー決定A、2026-09-01）。**拒否されなければ退行。**

### 3.2 単一書き込み（FC6 / FC5）

1. `hr1` と `coil1` を writable にし、API キーに `write:` スコープを付与、受付を有効化
2. `hr1` に数値、`coil1` に真偽値を書く
3. 読み戻して一致を確認。**スレーブ側でも直接確認する**

**合格条件**: 200 が返り、値が一致する。

### 3.3 隙間を跨がないこと（最重要）

**なぜやるか**: FC15/FC16 は**範囲書き込み**なので、離れた番地を1リクエストにまとめると**間の番地を意図せず上書きする**。実装は「厳密に隣接する場合のみ結合」だが、**実スレーブで本当にそうかを確かめる価値が最も高い**。

1. `40003`（`hr1` と `hr_gap` の**間**にある、**タグ登録していない**番地）に、スレーブ側で**目印の値**を書いておく（例: `12345`）
2. `hr1`（40001）と `hr_gap`（40005）を**同時に**書き込む
3. **`40003` が `12345` のまま**であることをスレーブ側で確認する

**合格条件**: `40003` が不変。**変化していたら重大な欠陥**（呼び出し元が指定していない番地を書いている）。

### 3.4 word_order（32bit 値）

**なぜやるか**: **Modbus 読み取り側の既定は `HighLow`** で、**SLMP の既定 `LowHigh` とは逆**。取り違えると 32bit 値だけが化ける。

1. `i32` または `f32` のタグを 2 レジスタにまたがる形で登録
2. 既知の値を書いて読み戻す
3. **スレーブ側の生レジスタ2本の並び**が、設定した word_order どおりか確認する

**合格条件**: 書いた値がそのまま読み戻せ、生レジスタの並びが設定と一致する。

### 3.5 デバイス例外でセッションが落ちないこと

**なぜやるか**: Modbus の例外応答を「接続致命的」と誤分類すると、**通常のデバイスエラーのたびにセッションを捨てて再接続ループに入る**。実装では個別失敗として畳んでいる。

1. スレーブが**例外を返すアドレス**（範囲外など）へ書き込みを試みる → 失敗する
2. **直後に** `hr1` へ書き込み、**成功すること**を確認

**合格条件**: 例外の後も**セッションが生きており**、次の書き込みが即座に成功する。再接続待ちになったら退行。

### 3.6 数量上限付近

**なぜやるか**: 書き込みの上限は **FC16 = 123 レジスタ / FC15 = 1968 コイル**で、読み取りの 125 / 2000 とは**異なる**。境界で分割が正しいか。

1. 連続する **124 個以上**のホールディングレジスタタグを登録し、一括で書く
2. 全件が正しく書けていることを読み戻して確認

**合格条件**: 上限をまたいでも全件正しく書ける。

### 3.7 未対応種別が全体を巻き添えにしないこと

**なぜやるか**: String とビット・イン・ワードは #131 のスコープ外で、**個別の失敗**として返す設計。これを「接続致命的」にすると、1件の未対応でバッチ全体とセッションが巻き添えになる。

1. String タグと `hr1` を**同一バッチ**で書く
2. String は失敗し、**`hr1` は成功する**ことを確認

**合格条件**: 部分成功になる。全体が失敗したら退行。

### 3.8 SLMP と Modbus の同居

**なぜやるか**: #130 のドライバ選択が実環境で正しく効くか。

1. A の SLMP 接続と B の Modbus 接続を**同時に有効**にして収集を動かす
2. 双方へ書き込む

**合格条件**: 互いに干渉せず、それぞれ正しく読み書きできる。

## 4. C. banto-tagclient（#123）

**前提**: A が通っていること（実 Hub が動いている）。

1. 実 Hub から catalog を取得できる
2. **安定 ID**で読み取り・購読ができる
3. `write_tag` で書き込みができる
4. **LAN 越し**（別マシンから）でも同じことができる
5. **403 と 503 を区別できる**ことを確認:
   - `writable = false` のタグへ書く → **403**
   - 受付を無効（`POST /api/write-control/disable`）にして書く → **503**

**なぜやるか**: 403 は**設定の問題**、503 は**一時的な状態**で、現場での対処が違う。ここが潰れていると「なぜ書けないのか」が分からない。

**合格条件**: 上記が期待どおり。加えて**配布サイズの実測**と **release tag での固定**を検討する（#123 の残スコープ）。

## 5. 拒否コード早見表（切り分け用）

書き込みが弾かれたとき、**どのゲートで落ちたか**を HTTP コードから判断する。ゲートは上から順に評価される。

| #   | ゲート             | 拒否時  | 意味                                                          |
| --- | ------------------ | ------- | ------------------------------------------------------------- |
| 1   | catalog 解決       | 404     | タグ名が違う（外部名は `{接続}.{グループ}.{タグ}`）           |
| 2   | `writable`         | **403** | タグが writable でない（**設定の問題**）                      |
| 3   | 実効 enabled       | 409     | タグまたは親が無効                                            |
| 4   | シミュレーション中 | 503     | SIM 中の PLC タグには書けない                                 |
| 5   | プロトコル未対応   | **501** | broker にドライバが無い（#131 以降 slmp / modbus-tcp は通る） |
| 6   | 受付トグル off     | **503** | `POST /api/write-control/enable` が必要（**一時的な状態**）   |
| 7   | レート制限         | 429     | キーが trip。`POST /api/api-keys/{id}/clear-trip`             |
| 8   | 値の型・範囲       | 400     | bit タグに数値、数値タグに bool 等（暗黙変換はしない）        |
| —   | スコープ不足       | 403     | `write:{外部名}` の**完全一致**が必要                         |
| —   | セッション token   | 403     | `/api/v1/*` は**API キー専用**。管理セッションでは書けない    |
| —   | 収集停止中         | 503     | 収集が動いていないと書けない                                  |

## 8. 検証不能だった項目と、その意味

### 8-1. 複数要素のバッチ書き込みは banto-hub からは発生しない

`apps/banto-hub/core/src/write_path.rs` は **`handle.write(vec![request])`** と、常に**1リクエストだけ**を broker へ渡す。`/api/v1/values` は **GET のみ**で、書き込みは `POST /api/v1/values/{tag}` の単一タグのみ（設計 §6 の「1書き込み = 1リクエスト = 1監査行」に対応）。

したがって:

- **タグを跨ぐ結合（隙間問題）は現時点の製品経路では起こり得ない**。B-3.3 が「検証不能」なのは欠陥ではなく、**その経路が存在しない**ため。
- ただし **32bit タグは 1 リクエストで 2 レジスタ**になるため **FC16 は到達可能**で、B-3.4 で実機確認できた。
- 複数要素の経路を使うのは、将来 relay-wright を Modbus 対応にした場合や SDK からのバッチ利用。**その時に本項目の実機確認が必要になる**。CI ではシミュレータで被覆済み（`writes_never_merge_across_a_gap` と、飛ばした番地の不変を確認する統合テスト）。

### 8-2. このスレーブは Modbus 例外を返せない

全アドレス範囲で正常応答し、数量上限も強制せず、unit_id 不一致は無応答（タイムアウト）だった。よって「例外応答を接続致命的にしない」ことの実機確認はできない。CI のシミュレータでは例外を注入して被覆済み。

**例外を返せるスレーブが手に入ったら再試験する価値がある。** ここを取り違えると、通常のデバイスエラーのたびに再接続ループへ入る。

### 8-3. スレーブのアドレス空間が重なっている（機材の性質）

このスレーブは**コイル空間とホールディングレジスタ空間が同じ記憶域を共有**している。生 FC5 でコイル 1 を ON にすると 40001 が 0xFF00 になる。

**banto を通さない生 Modbus でも同じ挙動だったため、これは機材の性質であって製品の不具合ではない。** 独立検証の手段（生 Modbus）を用意していなければ、製品バグと誤認するところだった。**コイルとレジスタを混ぜた試験はこの機材では意味を持たない。**
