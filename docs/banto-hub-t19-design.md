## 1. 背景と狙い

2026-09-02 のオーナー所感を起点とする。中心にあるのは次の一点である。

> **タグ登録画面から接続先・収集グループ・タグを作れるのに、PLC 接続画面と収集グループ画面が別にある。経路が多すぎて迷う。**

同じオブジェクトを複数経路から作れる状態は、利用者を迷わせるだけでなく**実装上も危うい**。経路ごとに同じ検証・pending queue 処理・202 の扱いを持つ必要があり、片方だけ修正される事故が起きる。T19 の第一の狙いは**設定操作の入口を一本化する**ことである。

残りは、開発・試運転工程での摩擦を減らす小さな改善と、独立した機能追加である。

## 3. 設計上の注意点

### 3.1 画面の廃止は「機能の移設 → 削除」の順で行う

PLC 接続画面・収集グループ画面にしか無い機能（接続テスト、シミュレーション切替、`word_order`、ポート、`unit_id` 等）を**先にタグ画面側へ移し**、移設が済んでから画面を消す。同時に行うと機能が失われる。

**E2E は画面遷移に依存していない**（§7.2 で確認。該当箇所はすべて REST API への参照で `page.goto('/plc-connections')` は0件）。したがってページ削除だけでは E2E は壊れない。ただし**新しい導線を通る経路の被覆は追加する**。

### 3.2 作成と編集で提示を変える理由

作成は前後関係を必要としない一方向の作業なので、中央モーダルで集中させる。編集は一覧を見ながら直す作業なので、右ペインで並置した方が速い。**同じ「ドロワー」実装を使い回さず、用途で分ける。**

### 3.3 `writable` 既定 ON は条件付きでなければ壊れる

**グローバルに既定 ON にすると登録が失敗するタグがある。**

- **computed タグ**は `writable` にできない（`crates/banto-tags/src/tag.rs`、「値は式が決まります」）
- **Modbus の読み取り専用領域**（`1xxxx` / `3xxxx`）は登録時に拒否される（オーナー決定A、2026-09-01）

したがって既定の適用は「**PLC タグかつ書き込み可能な領域のときのみ**」とする。UI 側で条件判定し、該当しない場合は既定を適用せず、その旨が分かる表示にする。

**8段ゲートは撤去しない。** 変わるのはゲート2（`writable`）の**既定値**だけで、API キーのスコープ完全一致・書き込み受付トグル・レート制限・監査はそのまま効く。

### 3.4 親の削除は「定義のみ・履歴は残す」

接続・グループを削除しても **tstore の履歴は消さない**。削除確認では**消える定義の件数**（タグ N 件）を明示する。履歴が残ることも明示する。

孤児となった履歴は UX-39 の保持期間で自然に消える。

### 3.5 一括削除と pending queue

**収集稼働中のレジストリ変更は 202 で pending queue に入る。** 一括削除でキューを溢れさせないよう、**まとめて1件の pending として扱う**か、稼働中は一括削除を抑止するかを設計時に決める。

**決定（2026-09-03、S2-c1 着手時の調査）: まとめて1件の pending として扱う。稼働中の抑止はしない。**
既に `tags.batch_create`（T11-1）と `tags.batch_update`（T18-3b）が**この形で実装済み**だった
（`execute_pending_apply` の分岐がバッチ payload をそのまま1件として受ける）。新しい方式を
持ち込むより既存の型に合わせるほうが、`rest.rs` の骨格・all-or-nothing 契約・catalog commit
1回という既存の性質をそのまま引き継げる。**一括削除は `tags.batch_delete` として同型で追加した。**

### 3.6 試運転モードを常時表示しない根拠

現在は起動時 WARN と UI 表示で「認証なし」を告知している。UX-45 でこれをやめるが、**安全性は損なわれない**。試運転モード中は**非 loopback バインドが構造的に拒否される**ため（`enforce_loopback_when_commissioning`）、ネットワークへ露出したまま無認証になることがない。

ただし**状態を知る手段は残す**。警告としてではなく、サーバー状態画面に事実として表示する（UX-46 と同じ画面）。

### 3.7 MCP は既存ゲートを通す

MCP からの書き込みも `POST /api/v1/values/{tag}` と同じ経路を通し、**MCP 専用の抜け道を作らない**。これにより「本番で使うなら自己責任」という判断が、実際にはゲートに守られた状態になる。

### 3.8 タグの無い接続はセッションを張らない

**現状は収集側と書き込み側で挙動が違う。**

- **収集側**: タグの無い接続は**タスクもソケットも持たない**（`crates/banto-collect/src/config.rs:520-525`「reading nothing from a PLC is pointless」）
- **書き込み側**: セッション同期は `c.enabled && is_supported_protocol(...)` で絞るだけ（`apps/banto-hub/core/src/hub.rs:1218`）で、**タグが1つも無くてもセッションを張りにいく**

結果、開発時に「形だけ」登録した到達不能な接続が、状態画面に `reconnecting` を出し続ける。

**設定（`enabled` の既定 OFF 等）を増やす案は採らない。** 利用者が理解して使い分けねばならない設定が増えるのは UX の後退であり、そもそも**アプリ側で判断できる**（2026-09-02 オーナー判断）。

**当初この節には「書き込み要求時に `ensure_connection` がその場でセッションを張るので機能は失われない」と書いていたが、これは誤りだった**（2026-09-03 訂正）。T15-4 以降、書き込み経路は `write_broker_handle_peek`（生成しない覗き見）だけを使い、セッションが無ければ `WriteRejection::WriteFailed` で fail closed する（`write_path.rs:587`）。

**実際の挙動**: セッションは **`rebuild()` 時**（収集の開始・再起動）と、**カタログ変更時（稼働中のみ、S2-a 案B）**に同期される。

**カタログ変更時の同期は、現時点では REST から到達しない防御である**（2026-09-03 確認）。レジストリの編集は稼働中だと 202 で保留され（`require_collection_stopped` / `queue_pending_registry_change`）、**pending の適用は `Stopped` を要求する**（`rest.rs:4062`）。したがってカタログを変える経路はすべて停止を経由し、次の開始時の `rebuild()` でセッションが同期される。「タグを足したのに書けない」状態には**到達しない**。

それでも実装したのは、**述語の根拠がカタログにある以上、カタログが変わった時点で評価し直すのが振る舞いとして正しい**ためである（2026-09-03 オーナー判断）。`legacy_live_reconfigure` が有効な環境や、将来 稼働中編集を許す変更が入った場合にも破綻しない。

**同期は `CollectionController` の `transition` ロック（`try_lock`）で start/stop と直列化し、`Running` のときだけ行う。** これは T15-4 が塞いだ危険（**止めたはずの PLC へダイヤルしてしまう**）を別経路で再現しないための措置である。`CollectorManager::stop()` は `rebuild_lock` を取らないため、`commit_catalog` 側の排他だけでは防げない。

**UI 上の帰結**: タグの無い接続は状態画面で `connected` / `reconnecting` を示さなくなる。「未使用」に相当する表示を与えるかは実装時に決める。

**注意**: これは #130 / #131 で整えた経路に触れる。ロジック自体は1箇所（上記 `hub.rs:1218` の絞り込み）だが、**実機での再確認**（`docs/real-machine-test-2026-09.md` の A-1/A-2 相当）を完了条件に含める。

### 3.9 状態画面から現在値を外す

状態画面は現在 **`GET /api/values`（全タグ現在値）を3秒ポーリング**して表示している（2026-08-31 オーナー決定「案A」）。現在値は**タグモニタが担う**ため、状態画面からは外す。

UX-30 と同じ理屈である。同じ情報を複数画面が持つと、利用者はどちらを見ればよいか迷い、実装側も表示規約（品質・値源・鮮度の出し方）を二重に維持することになる。

**副次的な効果**として、状態画面を開いている間の**全タグ 3 秒ポーリングが無くなる**。`current_values` を読むだけなので PLC への負荷は元々無いが、タグ数が多い環境では応答量が減る。

状態画面に残すのは、**接続状態・pending 変更・サービス状態・CPU/メモリ**（UX-46）といった「サーバーの状態」に属する情報である。

### 3.10 削除の取り消しは「作り直し」ではなく「遅延実行」で実現する

**UX-40 の素朴な実装（削除してからトーストの取り消しで作り直す）は採れない。** 履歴の
キーが**レジストリの主キー由来**だからである。`crates/banto-collect/src/config.rs` の
`connection_key`/`group_key`/`tag_key` は `conn:<id>`/`grp:<id>`/`tag:<id>` を返し、
banto-tstore はこのキーで `tstore_groups`/`tstore_columns` を書く（`TsReader::read_range`
も `group_key` で引く）。名前ではなく id を使うのは意図的で、「名前は編集できるが定義が
変わっていなければ同じ config hash になり、無用なファイル rotation が起きない」ためである。

そして `tags`/`collection_groups`/`plc_connections` の主キーは **`AUTOINCREMENT`** なので、
SQLite は**削除した id を再利用しない**。つまり削除 → 作り直しでは必ず新しい id になり、
新しい `tag:<id>` は**過去の履歴に到達できない**。S2-b で「親を消しても履歴は残る」と
保証した直後に、取り消し操作がその履歴との結び付きを**黙って切る**ことになる。

**決定（2026-09-03）: 取り消しは削除の遅延実行で実現する。** 削除操作は数秒間サーバーへ
送らず、UI 上だけ消えた状態にしてトーストに取り消しを出す。取り消されなければ実行し、
取り消されたら何も起きない。id が変わらないので取り消しが**本物の取り消し**になる。

- 却下: **soft delete（`deleted_at` 列）**。id は保てるが、共有クレート `banto-tags` の
  全一覧クエリに絞り込みを足すことになり、relay-wright を巻き込む。S2-b で回避した
  「共有クレートの契約を変える」危険を、数秒の取り消しのために自ら踏むことになる。
- 遅延実行の失敗方向は**安全側**である。取り消し猶予中にタブを閉じるなどして実行され
  なかった場合、結果は「削除されていない」であって、データが失われる側には倒れない。
  ただし利用者にとっては「消したのに残っている」なので、**画面遷移・再読込・次のレジストリ
  操作の直前には猶予を打ち切って即実行する**こと。

**適用範囲は当面タグの削除（単票・一括）に限る。** 接続・収集グループの削除は S2-b で
件数付きの確認ダイアログを入れており、カスケード削除を遅延させるほうがかえって
分かりにくい（猶予中の一覧に何を出すかが自明でない）。親の削除にも取り消しを付けるかは
S2-c2 の実装後に改めて判断する。

**実装時に判明した重要な前提の誤り（本節の元の記述で私が書いた誤り）**: 「書き込み要求が来た時点で
`ensure_connection` がその場でセッションを張る」という記述は T15-4（`crate::write_path`）以降は誤り
だった。事実は逆で、書き込み経路は `CollectorManager::write_broker_handle_peek`（非スポーンの覗き見、
セッションが無ければ `WriteRejection::WriteFailed` で fail closed）だけを使い、`ensure_connection`
ベースの `write_broker_handle` は現状どこからも呼ばれていない（T15-4 が意図的にそうした - 収集停止
との競合で実機へ意図しないセッションを張るレースを防ぐため）。

**案B で解消済み（2026-09-03、オーナー決定）**: 上の誤りに起因して、初回実装は「タグの無かった
接続にタグを追加しても、次の rebuild/apply_run（実務的には収集の再起動）までその新しいタグへの
書き込みが fail closed になる」という制約を残し、対応せずテストで挙動を固定するにとどめていた。
**この制約は解消した**: `crate::rest::commit_catalog_and_notify`（登録変更のたびに呼ばれる、catalog
コミットの唯一の入口 - CRUD ハンドラと `execute_pending_apply` の両方がここを通る）が、catalog
コミット成功後に `CollectionController::resync_sessions_for_catalog_change` を呼ぶようになった。
このメソッドは `start`/`stop` と同じ `transition` ロックを `try_lock` し、**取れなければ何もせず**
（start/stop 自身が同じ仕事をするため割り込む必要がない）、**状態が `Running` のときだけ**
`CollectorManager::resync_broker_sessions`（内部は既存の `sync_slmp_sessions_from` をそのまま再利用）
を呼んでセッションを同期し直す。`CollectorManager::stop` は `rebuild_lock` を取らないため、
`transition` ロックでの直列化が無いと「意図して止めた PLC へ、カタログ変更同期が直後にセッションを
張り直してしまう」という T15-4 と同型のレースを再導入しかねない - `resync_sessions_for_catalog_change`
がまさにこれを防ぐために `transition` ロックを使う設計になっている（詳細は同メソッドの doc comment、
`apps/banto-hub/core/src/controller.rs`）。**唯一の既知の残存ギャップ**: この resync は稼働中の
`Collector` 本体には一切触れないため、SLMP 接続（収集読み取りが broker 経由の唯一のプロトコル）で
最後の有効グループが消えたタイミングでは、旧設定のまま読み取りを続けている collect タスクが読んでいる
セッションを止めてしまう可能性がある（read エラーとして現れ、次の rebuild/apply_run で自己解消する -
パニックや書き込み側のハザードではない）。Modbus TCP 接続はこの影響を受けない（収集読み取りは
broker を経由しないため）。詳細は `CollectorManager::resync_broker_sessions` の doc comment参照。

**S2-b（UX-38、§3.4・§7.5）: 完了（2026-09-03）。** 当初案の「既存の
`delete`/`delete_tx`（拒否）を書き換える」ではなく、**新しいメソッド

猶予を打ち切る場所は **`tagRegistryAdmin.ts` の `httpRequest` 1箇所**にした。変更系
（`method !== 'GET'`）の直前だけで `flush()` する。19 ある画面側の変更ハンドラに flush を
撒くと漏れるため。**GET では flush しない** - 猶予中の行は画面が id でフィルタして隠すので
再読込で復活せず、逆に GET でも flush すると `(app)/+layout.svelte` の3秒ポーリングが
猶予をほぼ即座に潰す。flush が必要な理由は、猶予中に別の変更を送るとサーバーにまだ存在する
タグのせいで矛盾が起きるから（特にタグ名はグループ内で一意なので、消したはずの名前で
新規作成すると弾かれる）。

**レビューで見つけて直した不具合**: 取り消しトーストの表示時間を猶予より長く（+1秒）して
いたため、猶予切れ後の1秒間だけ「取り消し」ボタンが押せるのに何も起きず、それでも
「削除を取り消しました」と成功を報告していた。`undo()` が実際に取り消せたかを返すようにし、
実行された瞬間にトーストを dismiss し、表示時間も猶予を超えないようにした。

**取り消しの対象はタグの削除（単票・一括）のみ**で、接続・収集グループの削除は S2-b の
件数付き確認のまま（§3.10 末尾の方針どおり）。既存の `window.confirm` も残している -
単票削除の confirm は「削除対象を参照している演算タグ」を列挙しており、取り消しでは
代替できない情報だから。

## 5. 実装上の既知事実

### 5.1 履歴保持の基盤は既にある

`crates/banto-tstore` に **`retention_days`（日数保持）が実装済み**で、`store_config` 経由の設定も存在する。UX-39 は**配線と UI で足りる**見込み。

**件数上限は tstore に無い**（監査ログ側には `retention_rows` がある）。UX-39 では日数のみとする。産業用途では「何日分残っているか」が運用の会話に乗りやすく、件数はタグ数で意味が変わるため。

**S2-d（UX-39）: 完了（2026-09-04）。** 見込みどおり配線と UI で足りた（剪定エンジン
`prune_once` と保存 `store_config` は既存）。追加したのは admin 限定の REST 3本
（`GET/PUT /api/store-settings`、`POST /api/store-settings/prune-preview`・`prune-now`）と
設定画面の「データ保持」セクション。オーナー決定（2026-09-03）を2点反映した:

1. **保存は方針のみ・非破壊。剪定は別ボタンで即時実行。** `PUT` は日数を保存するだけで
   履歴ファイルに触れない（次の24h周期／再起動で自然に効く）。「今すぐ古い履歴を削除」は
   保存済み方針で `prune-preview`（`banto_tstore::plan_prune` の dry-run）→ 件数つき確認 →
   `prune-now` の順で実行する。`PUT` が削除しないことはテストで固定した
   （`store_settings_put_never_deletes_history_files`）。
2. **無制限（削除しない）を選べる。** `StoreSettings.retention_days` を `i64` から
   `Option<i64>`（`None`＝無制限）に変え、監査ログ設定と同じ `parse_retention`／`None→"0"`
   規約に揃えた。`prune_once` は `None` のとき `prune_files` を一切呼ばない。**意味の変化**:
   以前は素の `i64` で `prune_files` が 0 を「当日のみ」と解釈していたが、今回から非正値は
   無制限になる。store 保持を 0 にする UI はこれまで無かったため実挙動の退行は無い。

`plan_prune` は `prune_files` と同一の削除判定を共有する（`prune_files` は `plan_prune` の
結果の `deleted` だけ実際に削除する薄いラッパーにリファクタした）ので、プレビューと実削除の
判断がずれない。

## 6. 見送るもの

**汎用の UNDO/REDO**（当初案の項目11）は採らない。レジストリには**楽観ロック（revision）と pending queue** が既にあり、汎用 UNDO はすべての変更に逆操作を定義したうえで「取り消そうとしたら他者が同じ行を変更済み」という競合を安全に扱う必要がある。費用が突出して大きい。

痛みの大半は誤削除なので、**削除の取り消しトースト**（UX-40）で実利の大半を取る。足りなければ改めて設計する。

### 8.2 UX-43「固定」の定義 → **案C・banto-hub のみに決定**（2026-09-02）

**真の固定（sticky ヘッダー・固定サイドバー）と狭幅対応（≤900px のオフキャンバス）の両方**を行う。対象は **banto-hub のみ**とし、chronogazer / relay-wright への横展開は行わない。

**上流の移植ではなく自前実装**になる。上流にレイアウトコンポーネントは存在せず（§7.7）、参照実装の `apps/admin-template` もデスクトップ幅では固定していないため、**移植しても目的は達成されない**。自分のレイアウトを所有しているので、ヘッダーに `sticky`、本文に専用スクロール領域を与える形で直接実装する。狭幅対応は admin-template のパターン（オフキャンバス + オーバーレイ）を参考にする。

**z-index の再設計が要る**。既存は `CommissioningBanner`=10 / Drawer=900 / CommandPalette=1000。狭幅オーバーレイを足すと衝突しうる。なお `CommissioningBanner` は UX-45 で撤去されるため、その分は単純になる。

### 8.3 読み込みのトランザクション化 → **不要と決定**（2026-09-02）

**トランザクション化はしない。** 開発時は「形だけ接続先を先に登録しておく」使い方があり、**空の接続・グループは無害**なので、読み込みが途中で中断して残っても危険はない。

この前提は技術的に裏付けられている。収集側は **「タグの無い接続はタスクもソケットも持たない」** と明示的に除外している（`crates/banto-collect/src/config.rs:520-525`）。

ただし**書き込み側は揃っていなかった**ため、UX-48 で是正する（§3.8）。
