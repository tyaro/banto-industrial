## 1. 背景と狙い

2026-09-02 のオーナー所感を起点とする。中心にあるのは次の一点である。

> **タグ登録画面から接続先・収集グループ・タグを作れるのに、PLC 接続画面と収集グループ画面が別にある。経路が多すぎて迷う。**

同じオブジェクトを複数経路から作れる状態は、利用者を迷わせるだけでなく**実装上も危うい**。経路ごとに同じ検証・pending queue 処理・202 の扱いを持つ必要があり、片方だけ修正される事故が起きる。T19 の第一の狙いは**設定操作の入口を一本化する**ことである。

残りは、開発・試運転工程での摩擦を減らす小さな改善と、独立した機能追加である。

## 3. 設計上の注意点

### 3.1 画面の廃止は「機能の移設 → 削除」の順で行う

PLC 接続画面・収集グループ画面にしか無い機能（接続テスト、シミュレーション切替、`word_order`、ポート、`unit_id` 等）を**先にタグ画面側へ移し**、移設が済んでから画面を消す。同時に行うと機能が失われる。

E2E は `plc-connections` / `collection-groups` を参照しているため、**同じ PR でテストも更新する**。

### 3.2 作成と編集で提示を変える理由

作成は前後関係を必要としない一方向の作業なので、中央モーダルで集中させる。編集は一覧を見ながら直す作業なので、右ペインで並置した方が速い。**同じ「ドロワー」実装を使い回さず、用途で分ける。**

### 3.3 `writable` 既定 ON は条件付きでなければ壊れる

**グローバルに既定 ON にすると登録が失敗するタグがある。**

- **computed タグ**は `writable` にできない（`crates/banto-tags/src/tag.rs`、「値は式が決まります」）
- **Modbus の読み取り専用領域**（`1xxxx` / `3xxxx`）は登録時に拒否される（オーナー決定A、2026-09-01）

したがって既定の適用は「**PLC タグかつ書き込み可能な領域のときのみ**」とする。UI 側で条件判定し、該当しない場合は既定を適用せず、その旨が分かる表示にする。

**8段ゲートは撤去しない。** 変わるのはゲート2（`writable`）の**既定値**だけで、API キーのスコープ完全一致・書き込み受付トグル・レート制限・監査はそのまま効く。

### 3.4 親の削除は「定義のみ・履歴は残す」

接続・グループを削除しても **tstore の履歴は消さない**。削除確認では**消える定義の件数**（タグ N 件）を明示する。履歴が残ることも明示する。

孤児となった履歴は UX-39 の保持期間で自然に消える。

### 3.5 一括削除と pending queue

**収集稼働中のレジストリ変更は 202 で pending queue に入る。** 一括削除でキューを溢れさせないよう、**まとめて1件の pending として扱う**か、稼働中は一括削除を抑止するかを設計時に決める。

### 3.6 試運転モードを常時表示しない根拠

現在は起動時 WARN と UI 表示で「認証なし」を告知している。UX-45 でこれをやめるが、**安全性は損なわれない**。試運転モード中は**非 loopback バインドが構造的に拒否される**ため（`enforce_loopback_when_commissioning`）、ネットワークへ露出したまま無認証になることがない。

ただし**状態を知る手段は残す**。警告としてではなく、サーバー状態画面に事実として表示する（UX-46 と同じ画面）。

### 3.7 MCP は既存ゲートを通す

MCP からの書き込みも `POST /api/v1/values/{tag}` と同じ経路を通し、**MCP 専用の抜け道を作らない**。これにより「本番で使うなら自己責任」という判断が、実際にはゲートに守られた状態になる。

### 3.8 状態画面から現在値を外す

状態画面は現在 **`GET /api/values`（全タグ現在値）を3秒ポーリング**して表示している（2026-08-31 オーナー決定「案A」）。現在値は**タグモニタが担う**ため、状態画面からは外す。

UX-30 と同じ理屈である。同じ情報を複数画面が持つと、利用者はどちらを見ればよいか迷い、実装側も表示規約（品質・値源・鮮度の出し方）を二重に維持することになる。

**副次的な効果**として、状態画面を開いている間の**全タグ 3 秒ポーリングが無くなる**。`current_values` を読むだけなので PLC への負荷は元々無いが、タグ数が多い環境では応答量が減る。

状態画面に残すのは、**接続状態・pending 変更・サービス状態・CPU/メモリ**（UX-46）といった「サーバーの状態」に属する情報である。

## 4. スライス構成

依存関係の順に並べる。**S1 は分割せず1つの設計として扱う**。ばらばらに実装すると同じ画面を二度動かすことになる。

### S1: 設定 UI の再編（UX-30/31/32/33/34/35/36/44/45）

タグ画面を設定の単一の入口にする。中央モーダルでの作成、グループ選択起点のタグ登録、詳細設定の格納、初回セットアップの廃止までを含む。**接続・グループ画面の削除は機能移設の完了後**（§3.1）。

**移設が必要な機能は §7.1 の表が作業リスト**である。特に **calc/mem 配下のグループ操作**と **viewer ロールの閲覧手段**は、手当てしないと機能が失われる。

**完了条件**: 接続・グループ・タグのすべてをタグ画面から作成・編集でき、**§7.1 の「必須」がすべて解消**していること。

### S2: 削除まわり（UX-37/38/39/40）

一括削除、親の削除（定義のみ）、履歴保持期間の設定、削除の取り消しトースト。

**UX-38 は Rust 側の拒否ロジックと DB 制約の両方を変更する**（§7.5）。既存の単体テストも前提が変わるため更新する。**virtual 接続（calc/mem）の削除禁止は維持する。**

**完了条件**: タグを複数選んで消せる。タグを持つ接続を消しても履歴が残る。誤削除を数秒以内に戻せる。

### S3: レイアウトとサーバー状態（UX-43/46/47）

上流 banto のヘッダー・左ペイン固定を採用。サーバー状態に各種サービスの状態と CPU/メモリを表示し、**全タグ現在値の表示は外す**（§3.8）。

**`system_info` は banto v1.4.0 で追加済み**（2026-08-30 に追従済み）なので、CPU/メモリは配線で足りる見込み。

### S4: 構成の保存・読込（UX-42）

**機能は実装済み**（§7.6）。作業は導線改善が中心で、§8.1 / §8.3 の判断に依存する。

### S5: MCP（UX-41）

独立した機能。他スライスと依存しない。

## 5. 実装上の既知事実

### 5.1 履歴保持の基盤は既にある

`crates/banto-tstore` に **`retention_days`（日数保持）が実装済み**で、`store_config` 経由の設定も存在する。UX-39 は**配線と UI で足りる**見込み。

**件数上限は tstore に無い**（監査ログ側には `retention_rows` がある）。UX-39 では日数のみとする。産業用途では「何日分残っているか」が運用の会話に乗りやすく、件数はタグ数で意味が変わるため。

### 5.2 収集周期の現行既定

現行は `ALLOWED_PERIOD_MS[0]` = **100ms**。UX-32 で 1s へ変更する。

## 6. 見送るもの

**汎用の UNDO/REDO**（当初案の項目11）は採らない。レジストリには**楽観ロック（revision）と pending queue** が既にあり、汎用 UNDO はすべての変更に逆操作を定義したうえで「取り消そうとしたら他者が同じ行を変更済み」という競合を安全に扱う必要がある。費用が突出して大きい。

痛みの大半は誤削除なので、**削除の取り消しトースト**（UX-40）で実利の大半を取る。足りなければ改めて設計する。

## 7. 調査結果（2026-09-02 実施）

§7 の要調査3件は完了した。**S1 の前提が2つ崩れた**ので、着手前に手当てが要る。

### 7.1 旧画面を消すと失われる機能（S1 の作業リスト）

`ConnectionDrawer` / `CollectionGroupDrawer` は T18-6 で既にタグ画面へ配線済みで、**フィールド単位の欠落は無い**（接続テスト・シミュレーション切替・`word_order` はすべて Drawer 側にある）。失われるのは**到達手段**である。

| 失われるもの                                        | 原因                                                                                                                                                                                       | 対応                                                                 |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| **calc/mem 配下の収集グループの作成・再設定・削除** | ツリーは virtual 接続ノードで右クリックメニューを出さない（`tagTreeContextMenu.ts:85-86, 94-95`）。旧画面のドロップダウンは virtual を含んでいた（`CollectionGroupDrawer.svelte:359-364`） | **必須**。タグ画面から calc/mem 配下のグループを操作できるようにする |
| **viewer ロールからの接続・グループ詳細の閲覧**     | ツリーの右クリックが `canWrite` 限定（`tags/+page.svelte:3080`）で Drawer を開けず、`host`/`port`/`unit_id`/`word_order`/`period_ms` を表示する場所がタグ画面に無い                        | **必須**。閲覧専用の参照手段を用意する                               |
| 常時表示の「新規作成」入口                          | 旧画面には常設ボタンがあった。タグ画面の接続・グループ作成は**右クリックのみ**が入口                                                                                                       | **要検討**。UX-33 のタグ登録導線と併せて設計する                     |
| 一覧での `enabled` の一目確認                       | ツリーはアイコン・SIM バッジ・周期のみ表示（`ConnectionTree.svelte:123-145`）                                                                                                              | 優先度低                                                             |
| virtual 接続の編集不可理由のトースト                | 旧画面は理由を説明していた。ツリーは無反応                                                                                                                                                 | 優先度低                                                             |

**列ソート・リサイズ・フィルタ**（BantoGrid 由来）はツリーに無いが、接続・グループは母数が少ないため**移設不要**と判断する。

### 7.2 E2E は画面遷移に依存していない（§3.1 の前提を訂正）

`e2e/tests-banto-hub/` の該当箇所は**すべて REST API（`/api/plc-connections` 等）への参照**で、`page.goto('/plc-connections')` のような**画面遷移は1件も無い**。API は維持されるため、**ページ削除だけでは E2E は壊れない**。

§3.1 の「E2E も同じ PR で更新する」は、**画面遷移の書き換えではなく、新しい導線を通る経路の追加**として読み替える。

### 7.3 ナビゲーションからの除去は2行で済む

`apps/banto-hub/src/lib/navigation.ts:24-25` の2エントリを消せば、**サイドバーとコマンドパレットの両方から消える**（`commands.ts` は `navItems` から自動生成）。

### 7.4 `/status` の初回セットアップが旧画面に依存している

`status/+page.svelte:628-646` のチェックリストが `href: '/plc-connections'` 等を直接埋めている。**UX-44 でチェックリストごと撤去する**ため、リンク修正ではなく本体撤去で解消する。

### 7.5 UX-38 は Rust 側の変更を伴う

現在は**アプリ層で明示的に拒否**している。

- 接続: 収集グループが参照していると拒否（`crates/banto-tags/src/plc_connection.rs:577-586`）
- グループ: タグが参照していると拒否（`crates/banto-tags/src/collection_group.rs:284-293`）
- DB 側も `ON DELETE RESTRICT`（`migrations/0002_collection_groups.sql:11`、`0011_tags_unique_name_per_group.sql:43`）

UX-38 では**この拒否ロジックと制約の両方**を変更する。既存の単体テスト（`delete_refuses_when_a_collection_group_references_it` 等）も**前提が変わるため更新が要る**。

**virtual 接続（calc/mem）の削除・編集禁止はそのまま維持する**（`plc_connection.rs:561-568, 438-458`）。自動プロビジョニングされる予約接続であり、UX-38 の対象外。

### 7.6 構成の保存・読込は実装済み（UX-42）

**export/import は T17-5 として実装済み**で、設定画面の「構成パッケージ」から使える。秘密情報の除外、収集稼働中の二重ガード、差分プレビュー、テスト7件がある。サーバー専用 API は無く、**既存 CRUD API をクライアントで組み合わせている**。

未整備なのは次の2点。

- **コマンドパレットに未登録**（`commands.ts` に該当コマンドが無い）
- **読み込みがトランザクションでない**。接続→グループ→タグを逐次適用するため、**中断すると適用済みの分が残る**（`configPackageAdmin.ts:180-271`）

**「プロジェクト単位」の意味が未確定**（§8）。

### 7.7 上流にレイアウトコンポーネントは存在しない（UX-43）

**`@banto/admin-core` はヘッドレスで `.svelte` を1つも持たない。** `@banto/theme` が提供するのは CSS 変数のみ（`--banto-shell-header-height` 等）。

ヘッダー・サイドバーを実装しているのは上流の **`apps/admin-template`**（`"private": true`、配布されない）。しかも**デスクトップ幅では固定していない** — `position: fixed` は **900px 以下でサイドバーをオフキャンバス化するときだけ**使われ、通常幅ではページ全体がスクロールする。

**v1.2.0 → v1.4.0 でレイアウト関連の差分はゼロ**（該当ファイルはバイト単位で同一）。「最新版で固定した」という変化は起きていない。

**3アプリすべてが同じ独自レイアウト**を使っており、banto-hub だけが取り残されているわけではない。

**UX-43 の「固定」の定義が未確定**（§8）。

## 8. 未決事項（オーナー判断待ち）

### 8.1 UX-42「プロジェクト単位」の意味

- **案A**: 現行の単一 JSON export/import の**導線改善**（コマンドパレット追加、配置の見直し）。実装追加はほぼ不要

あわせて **banto-hub 単体で行うか、3アプリ共通化するか**も要判断。

### 8.3 UX-42 に読み込みのトランザクション化を含めるか
