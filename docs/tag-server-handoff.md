## マニュアル直接参照の状況（オーナーへの報告事項）

`*.roboticsware.com` の許可リスト追加は**このセッションでも効いていない**:

- コンテナからの curl: プロキシが CONNECT に 403
  （`gateway answered 403 to CONNECT (policy denial)` — 環境のネットワーク
  ポリシー側で拒否。docs / www 両ホストとも）
- WebFetch: サイト側ボット対策で 403（前セッションと同じ、許可リストと無関係）
- web.archive.org 経由: これもポリシー拒否

→ **環境設定のネットワークポリシーに `*.roboticsware.com` が実際に
入っているか再確認が必要**。それでも WebFetch 経路は別問題（ボット対策）
なので、確実なのは**オーナーがブラウザで該当ページを保存して
リポジトリに置く**（または貼り付ける）方法。優先度は高くない —
下記のとおり、スニペット調査で設計判断に必要な材料はほぼ埋まった。

## 第2セッションの調査結果（設計 doc 反映済み）

検索スニペットで判明し、doc へ反映した事実:

- タグパス区切りは `.`（Unit.Folder.Tag）— 本設計の外部名と一致
- タグ種別: スタティック / アクティブ（`#` 前置の直接アドレス指定）/
  ネットワーク / エイリアス。アクティブタグ相当（キャッシュ迂回の
  オンデマンド読み）は本設計では意図的に非対応と明記（§1.1）
- ネットワークタグは旧方式で、現行後継は「IPLink サーバーユニット」
- 初版 §1.1 の「Panel IF」の正式名は **IPLink**（同社独自 TCP/IP
  プロトコル。FA-Panel / VB アプリのタグアクセス経路）— 対応表を修正済み
- サーバー側演算は SC1（VB互換演算子）/ SC2（if/for・ユーザー定義関数）/
  演算式構文の3系統で「アクション」として実行される → 本設計の
  純関数・最小文法の対比を §4.2 に追記
- FA-Server 本体機能: ロガー・日報集計・FTP 転送・タグブリッジ・
  外部アプリ実行・SQL 呼び出し・スクリプト（→ 本設計の非スコープ判断
  §2 と整合、変更不要）

## オーナー決定済み（再確認不要）

1. タグサーバーを独立アプリとして設計先行する（実機に依存しない期間の作業）
2. 外部 IF は REST / WebSocket / MQTT / gRPC。OPC UA は後回し、OPC DA/DDE は追わない
3. ロガー・日報・帳票機能は作らない（記録は ChronoGazer の専管）
4. **中央レジストリ構想**: 今後の関連アプリ（SCADA 等)は自前でタグ定義せず、
   タグサーバーの catalog をバインドして使う
5. アクション機能（スクリプト・メール等）は不要
6. **演算タグ・内部タグはタグサーバー側で一元実装**（クライアント各自ではなく）
7. **オンライン動的変更**を FA-Server との差別化要件とする
   （FA-Server は稼働中の構成変更ができない、というのがオーナーの不満点）
